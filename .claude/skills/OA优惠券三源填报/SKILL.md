# OA 优惠券三源填报

> **状态**：业务流程与交互合同；服务端实现、正式白名单/黑名单模板、OA 字段映射完成前不得宣称已可提交原生 OA。
> **关联 PRD**：[三源优惠券 OA 填报 PRD v1](../../../docs/oa-ticket-reimbursement-materials/specifications/coupon-oa-three-source-workflow-prd-v1.md)
> **唯一字段字典**：[references/fields.md](references/fields.md)
> **边缘规则**：[references/edge-cases.md](references/edge-cases.md)

## 1. 目标与边界

本 Skill 规定一笔“优惠券申请”的业务过程：业务员上传已有的三类源材料，系统先确认它们的业务含义和映射，再从同一份标准数据生成标准附件与 OA 预填内容。

```text
原始配券表 + 原始白名单 + 原始黑名单（或确认无黑名单）
  → 标准数据包
  → 标准配券表 / 标准白名单 / 可选标准黑名单
  → OA 预填确认单
  → 业务员第二次确认
  → 仅服务端创建并回读飞书原生 OA
```

**本 Skill 不做：**

1. 不把任意格式源文件直接作为 OA 正式附件；OA 只能使用确认后的标准生成文件。
2. 不把“没有上传黑名单”“黑名单文件为空”“黑名单解析失败”视为同一件事。
3. 不默认为白名单或黑名单优先；重叠必须由业务员决定。
4. 不从不完整的文件、自由文本或模型猜测中补造业务事实。
5. 不通过本地脚本、Shell 或 Skill 直接调用飞书 OA API。创建原生 OA 只能由已实现、受认证、可审计的服务端在第二次确认后完成。
6. 不支持未登记的券型、未登记的标准模板、未知 ID 维度或未确认字段映射。

## 2. 前置条件

开始生成或提交前必须同时满足：

- 已登记本次券型对应的标准配券模板版本；
- 已提供并登记正式白名单模板与黑名单模板，或 PRD 已明确该场景无需黑名单模板；
- OA 字段映射、审批定义、附件控件与权限已完成服务端验证；
- 本次业务属于 PRD 已批准的券型、限品维度和渠道范围；
- 当前业务员没有与本流程互斥的活动优惠券 OA 草稿或旧 Excel 试点。

如果正式白/黑名单模板尚未登记，系统可以收集材料、输出待确认项，但必须阻断标准附件生成和“确认并发起 OA”。

## 3. 业务材料与事实来源

| 材料                | 是否必传 | 业务地位                                     | 不符合时的处理                                                                       |
| ------------------- | -------- | -------------------------------------------- | ------------------------------------------------------------------------------------ |
| 原始配券表`.xlsx` | 是       | OA 字段和券规则的第一来源                    | 无法识别字段或券型时，展示候选并要求业务员确认                                       |
| 原始白名单`.xlsx` | 是       | 本单纳入范围的第一来源                       | 缺失、不可解析或 ID 维度不明确时阻断                                                 |
| 原始黑名单`.xlsx` | 否       | 本单排除范围的第一来源                       | 未上传时必须由业务员点击确认“本次无黑名单”；文件错误不能代替缺省确认               |
| 具体满减测算图片    | 是       | OA 的必传附件；不作为三源字段事实            | 仅登记、展示和上传；首期不解读图片内容                                               |
| 业务员补充文本      | 条件必需 | 补充配券表没有的 OA 字段、确认映射或显式覆盖 | 与配券表冲突时展示差异，不能静默覆盖                                                 |
| 飞书身份            | 系统提供 | 最终申请人和可用部门候选                     | 申请人以最终确认人身份为准；系统自动取其唯一主部门，无法唯一确定时要求该用户明确确认 |

### 3.1 配券表优先规则

```text
配券表中有明确且已确认的值
  → 作为默认业务值

配券表没有该 OA 字段
  → 向业务员追问补充

配券表与业务员补充内容冲突
  → 展示原值、补充值和来源
  → 只有业务员显式选择覆盖并说明原因后，才使用补充值
```

每个进入标准数据包的字段必须保留：来源文件、Sheet、单元格/行列、原始值、标准化值、映射版本；显式覆盖还必须保存覆盖人和原因。

## 4. 用户流程

### 4.1 发起与材料接收

业务员发送 `/OA优惠券三源填报` 后，Bot 说明需要：

```text
1. 原始配券表（必传，.xlsx）
2. 原始商品白名单（必传，.xlsx）
3. 原始商品黑名单（可选，.xlsx；不上传时需确认“本次无黑名单”）
4. 具体满减测算图片（OA 当前表单必传；只登记和上传，不解读图片内容）
```

文件可以乱序到达。系统对每份文件只做接收、hash、工作簿结构检查和候选角色识别；文件名只能作为候选提示，不能单独决定文件角色。

系统应主动完成以下识别，不要求业务员预先说明源表格式：

```text
- 识别工作簿中的 Sheet、合并单元格、表头候选、说明行和数据行；
- 基于字段别名、列名、单元格类型、样例值和计算关系识别配券字段候选；
- 识别名单候选列及其可能的 SKU / SPU / 商家 ID 维度；
- 识别商品名、价格、链接等非 ID 的附加列，并排除为名单主列；
- 检查公式、空值、重复、单元格内多 ID、数值格式和前导零风险。
```

AI 可以提出候选映射与原因；确定性规则负责验证格式、公式、计算和 ID 约束。只有一个候选可被已发布规则唯一证明时才自动采用；存在多个合理候选、字段冲突或业务语义无法证明时，系统只问业务员确认该项，不要求提供预先格式化的源表或重新填写完整表单。

### 4.2 解析、映射和第一次确认

系统读取源表的 Sheet、表头、样例、数据类型和候选列，并向业务员展示：

- 配券表字段与标准字段的候选映射；
- 白名单/黑名单使用哪个 Sheet、哪一列、什么 ID 维度；
- 配券表中没有但 OA 必填的字段；
- 配券表与补充文本之间的冲突；
- 黑名单状态：已上传、待确认无黑名单或无效。

业务员完成以下第一次确认后，系统才可生成：

1. 配券表的字段映射和必要的显式覆盖；
2. 白名单的 Sheet、列和 ID 维度；
3. 黑名单的 Sheet、列和 ID 维度，**或**“本次无黑名单”；
4. 每个缺失 OA 字段的补充值。

### 4.2.1 二轮审核与补充返回

当本地草稿已生成但存在“草稿可展示、不能确认”的活动文案问题时，二轮对话必须输出两部分，不能只在底稿的 blockers 中静默记录：

```text
【异常提示】
- 检测到的源券档 / 文案策略 / 型号映射差异及其影响。

【请补充 / 确认】
- 每个缺少字段的 key、业务可读名称和最小化补充问题。
```

例如，背景已列出四档券但 `2000-20` 未有已确认的型号/券额策略时：

- 异常提示：活动背景草稿已写入，但配券表存在“满2000减20”，当前没有对应策略；
- 缺少字段：`couponTierStrategies.2000-20`，要求确认其适用型号，或明确该券档的通用适用规则。

此状态可以保留活动背景候选供业务审核，但不得将候选标为 `selectedValue`，也不能进入“确认并发起 OA”。二轮返回必须绑定当前 candidate hash、revision 与源文件 hash；源文件或上下文变化后重新生成。

### 4.3 白黑名单重叠决策

只有两份名单均已确认相同 ID 维度并完成标准化后，系统才能计算交集。

发现重叠时，系统必须展示数量、样例和完整冲突清单，随后要求业务员选择：

```text
○ 白名单优先：重叠项从标准黑名单中排除
○ 黑名单优先：重叠项从标准白名单中排除
○ 返回修改源文件后重新上传
```

“保留在两边”不是默认选项；只有业务 Owner 另行批准后才能出现。任何文件、映射或决策发生变化时，之前的重叠决策立即失效。

### 4.4 生成标准产物与 OA 预填

第一次确认完成后，系统从同一份标准数据包生成：

- 标准配券信息表；
- 标准商品白名单；
- 已上传黑名单时的标准商品黑名单；
- 未上传黑名单时的“本次无黑名单”记录；
- OA 预填快照。

生成前后的文件均需进行结构验证与 SHA-256 记录。源文件只读保留，绝不被系统覆写或直接作为 OA 标准附件。

### 4.5 第二次确认与原生 OA

最终确认页必须一次展示：

- 所有 OA 字段及其来源；
- 标准附件名称、模板版本、行数和 hash；
- 黑名单状态；
- 白黑名单重叠及处理决定；
- 系统计算的金额、比例、ROI、时长等结果；
- 所有警告和未解决阻断项。

按钮文案固定为：**“确认并发起 OA”**。

该按钮只有当前草稿 owner 在当前 revision 中可以点击。服务端应重新校验 owner、revision、源/产物 hash、模板版本、映射和审批定义；通过后立即创建飞书原生 OA 并回读核对。不得增加第三次用户提交确认。

## 5. 字段读取原则

### 5.1 当前 OA 页面可见字段

| OA 字段           | 首选来源                         | 缺失或冲突时                        |
| ----------------- | -------------------------------- | ----------------------------------- |
| 部门              | 飞书身份/组织配置                | 由业务员确认允许的部门              |
| 申请人            | 最终确认业务员                   | 不从配券表冒充其他人                |
| 申请类型          | 当前固定“优惠券申请”           | 非申请场景另立流程                  |
| 业务模式          | 配券表；缺失时业务员补充         | 必须明确选择                        |
| 活动名称          | 配券表                           | 缺失时追问                          |
| 活动背景          | 配券表；缺失时业务员补充         | 必须明确填写                        |
| 活动点位(%)       | 需由已批准映射规则确定           | 不能仅凭名称默认等于优惠比例        |
| 平台承担比例(%)   | 配券表的承担比例                 | 缺失时追问                          |
| 是否超扣点/原因   | 配券表；缺失时业务员补充         | “是”时原因必填                    |
| 预估 GMV          | 配券表                           | 缺失时追问                          |
| 预估费用          | 已批准模板公式重算并与来源值核对 | 不一致时要求确认                    |
| ROI               | 已批准公式或 OA 公式             | 不要求业务员随意填写                |
| 配置渠道          | 配券表                           | 按已登记渠道文案映射                |
| 活动开始/结束时间 | 已批准映射或业务员补充           | 不得直接将可领/可用时间混作活动日期 |
| 时长（天）        | 开始/结束日期派生                | 与日期不一致时阻断                  |

### 5.2 不可伪造的回填字段

配券模板中的 `活动ID`、`批次Id`、`putKey`、PC/M 领券链接是建券后或配置后回填字段。它们在 OA 预填和标准生成阶段保持空白，系统和 AI 均不得编造。

### 5.3 活动名称与活动背景候选

活动名称和活动背景仍遵守“配券表第一来源”。当配券表没有可直接采用的活动背景，或业务要求按统一格式生成名称/背景时，系统可以生成**待确认候选**，但不得把候选冒充为源表事实或直接写入 OA。

生成前必须记录以下业务上下文，并标为 `user_provided_context`：

```text
业务标签：如“寄卖”
展示品类：如“苹果手机”
活动配合语境：如“超品活动”
“预计券率”的确认值及其业务口径来源
型号 / 券额策略及其业务来源
```

候选生成规则：

1. 期间、券档、门槛、面额和折扣比例只能从已确认配券表提取；示例文字不得覆盖源表，例如源表是 `2000减20` 时不得套用示例中的 `3000减20`。
2. 白名单中的 `型号`、商品类别和工作表券档关系只能作为辅助元数据；Sheet 名、型号别名、价格段和跨档商品存在歧义时必须显示冲突。
3. “预计券率”不能自动等同于预计领用率、预计使用率或折扣比例；未确认语义时不得写入背景。
4. DeepSeek 只能提出品类标签、型号别名和型号分组候选，且每一项必须带源文件 hash、Sheet、表头/单元格和原文证据；AI 不生成最终确认结论，不补造活动主题、年份、业务模式或财务口径。
5. 标题/背景候选必须分别保存 `sourceCandidate`、`generatedCandidate`、context hash、facts hash、AI request/response/proposal hash、状态和 blockers。存在 blockers 的 `needs_confirmation` 候选仍可写入**待审核草稿**，但不能成为 `selectedValue`；只有无 blockers 的候选才可由业务员以当前 candidate hash 显式确认。
6. 即使本地确认候选，草稿仍受其他 OA 必填字段、附件、金额口径和第二次确认门禁约束；本 Skill 不直接提交 OA。

建议格式：

```text
活动名称：{期间}{业务标签}{展示品类}优惠券申请
活动背景：本期申请{期间}{业务标签}{展示品类}优惠券，本期配置{源表券档}，{已确认券率表述}；配合{活动语境}，{已确认型号/券额策略}。
```

## 6. 产物与审计记录

每个 revision 至少记录：

```text
workflowId、owner、revision、schemaVersion
三份源文件的文件名、角色、hash、字节数、Sheet/列映射
配券表字段的来源定位、标准化值和显式覆盖
黑名单状态与确认人/确认时间
白黑名单交集、overlap hash、完整决策及决策人
模板 ID、版本和 fingerprint
每份标准产物的文件名、行数、hash、存储引用
活动文案的 sourceCandidate、context/facts/candidate hash、AI 审计 hash、blockers、选择人与确认时间
OA 预填快照、审批定义 hash
第一次确认和第二次确认的操作者、时间、revision
原生 OA instance code、链接、回读结果和差异
```

## 7. 必须阻断的情况

- 缺少配券表或白名单；
- 黑名单既未上传也未明确确认“无黑名单”；
- 文件不是可安全解析的 `.xlsx`；
- 文件角色、Sheet、列、ID 维度或配券字段映射存在歧义；
- 白名单和黑名单的 ID 维度不同；
- 名单中出现空值、公式、多 ID 单元格、前导零风险、未解决重复或未解决重叠；
- 模板未登记、版本/fingerprint 不匹配或不能生成可重新打开的文件；
- OA 必填字段缺失、字段冲突未决定或费用/ROI/date 计算无效；
- 旧 revision 卡片、非 owner 操作或确认快照已过期；
- 审批定义变化、附件 hash 不一致或无法确认上一次提交是否已经创建实例。
