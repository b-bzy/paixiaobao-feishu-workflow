# OA优惠券填报（P1 填单底稿助手）

对应 [优惠券 OA 智能提单 MVP PRD v1.2](../../../docs/oa-ticket-reimbursement-materials/specifications/coupon-oa-mvp-prd-v1.2.md) 的 P1 阶段。

**当前边界**：飞书 OA 的获授权写入 API 与表单字段标识尚未确认（PRD 第 8 节前置门槛）。因此本 skill 的产物是**填单底稿 + 结构化 fields.json**，由业务员据此在飞书 OA 原生表单中人工填写、核对并提交。未来 API 就绪后，由服务端接管「写入」步骤，本交互流程不变。

每次运行必须遵守：

1. 不代替业务员提交 OA，不调用任何 OA/审批/表单写入 API。
2. 不生成 Excel（P2 范围）；配券信息表必须由业务员提供文件。
3. 不识别、不判断「具体满减测算图片」的内容，只登记路径与哈希（案例 202609240455 中该图模糊不可转写，属正常情况）。
4. 不从自由文本推断业务事实；无法确认的字段标「待确认」，绝不猜测填入。
5. 校验只报告、给选项，不擅自改数；口径分歧必须由业务员拍板。

## 字段口径

唯一字段口径见 [references/fields.md](references/fields.md)（schemaVersion: `coupon-oa-p1-fields v1.0`）。字段增删改必须先更新该文件并经业务与流程 Owner 确认。

## 交互流程

### 第 1 步：触发与字段提示

用户输入 `/OA优惠券填报` 或等价说法后，**先只回复引导提示，不开始解析**。回复使用以下模板：

```
【OA 优惠券填报】请按下面模板回复文本字段；三份材料把文件拖进对话即可（给我路径）。

申请类型：优惠券申请（P1 固定）
部门：
申请人：
业务模式：
活动名称：
活动背景：
是否超扣点（是/否）：
预估GMV（元）：
预估费用（元）：
ROI：可留空，默认按 GMV÷费用 计算
配置渠道：
活动开始日期（YYYY-MM-DD）：
活动结束日期（YYYY-MM-DD）：

三份材料：
1）具体满减测算图片 —— 拖入文件（只登记，不解读内容）
2）配券信息表（.xlsx，按模板填写）—— 拖入文件，不要用截图代替
3）商品明细白名单（.xlsx）—— 拖入文件，不要用截图代替

可以分多条消息、乱序发送，也可以现在一次性全发；我会先解析回显再生成底稿。
```

用户如果跳过模板直接发材料或发一段描述，直接进入第 2 步，不要坚持让对方重填模板。

### 第 2 步：收集

- **文本字段**：接受粘贴文字；若用户发的是 OA 表单截图，转写字段值并在回显中标注「来自截图，请核对」。
- **Excel**：必须拿到文件路径（拖入对话即得）；用户只发表格截图时，要求改发文件，不得凭截图填写表格数据。
- **测算图片**：登记文件即可。
- 每收到一份材料回执一句「已收到 X，还缺 Y」，**只追问缺失项**，不重复罗列已有项。
- 用户说「取消」则终止会话，不写任何文件。

### 第 3 步：解析与校验

用 [scripts/parse_xlsx.py](scripts/parse_xlsx.py) 读取 Excel（仅标准库，任何机器可运行）：

```bash
python3 .claude/skills/OA优惠券填报/scripts/parse_xlsx.py "文件.xlsx"                    # 预览（默认前 60 行）
python3 .claude/skills/OA优惠券填报/scripts/parse_xlsx.py "文件.xlsx" --all              # 全部行
python3 .claude/skills/OA优惠券填报/scripts/parse_xlsx.py "文件.xlsx" --sheet 100减1     # 指定工作表
python3 .claude/skills/OA优惠券填报/scripts/parse_xlsx.py "文件.xlsx" --agg 'SKUID:unique_count'
python3 .claude/skills/OA优惠券填报/scripts/parse_xlsx.py "文件.xlsx" --agg '链接状态:value_counts'
python3 .claude/skills/OA优惠券填报/scripts/parse_xlsx.py "文件.xlsx" --agg '预计费用:sum' --header-row 1
```

**配券信息表校验**：

1. 识别说明行（如整行只有「平台承担100%」、无券档数据的行），不作为券批次。
2. 券批次 = 同时有「用券渠道」和「优惠券名称」的行；校验每行只含一个渠道（一行一渠道、一行一批次）。
3. 汇总：按渠道分组合计「预计费用」「预计引入GMV」，再算全渠道合计；ROI = GMV ÷ 费用。
4. **口径硬校验（必须执行）**：业务员填写的 预估GMV/预估费用/ROI 必须等于「某一单渠道合计」或「全渠道合计」之一；都对不上时，列出两套汇总值，要求业务员选择口径或填写差异说明，禁止静默取任一值。（案例 202609240455：OA 数值 = 单渠道合计，全渠道合计是两倍——此差异必须显式呈现。）
5. 派生校验：时长(天) = 结束日期 − 开始日期 + 1；ROI ≈ GMV ÷ 费用（取整比对）。不一致只报告并给修正建议，待业务员确认后落稿。
6. 回填区字段（活动ID、批次Id、putKey、领券链接）为空属正常（建券后回填），报告为「待建券回填」。

**商品明细白名单校验**（参考案例两种模式）：

1. 工作表名 ↔ 券档映射（如 `100减1` ↔ `满100减1`）；映射不到的工作表要报告，不臆测。
2. 对每张表统计：非空行数、SKUID 去重数、链接状态分布；跨档重复 SKUID 只列数量与示例，**不删除、不判错**（是否允许多档命中由业务员确认）。
3. 标准单列 ID 名单模式（单列商家ID/SKU/SPU）同样接受，报告行数与去重数即可。

**附件登记**：三份材料记录 路径、字节数、SHA-256。缺失必填附件则不生成底稿，只出追问清单。

所有无法确认的事项汇总为「待确认清单」，逐条给业务员答复，或由业务员明确表示「带待确认项出稿」。

### 第 4 步：生成底稿并确认

输出目录：`docs/oa-ticket-reimbursement-materials/drafts/<YYYYMMDD-HHmm>-<活动名slug>/`

| 文件 | 内容 |
| --- | --- |
| `oa-form-draft.md` | 按 OA 表单顺序逐字段列出「字段名：值（来源）」；附 附件清单、口径核对结果、待确认清单。业务员照此在 OA 原生表单中填写。 |
| `fields.json` | 机器可读：`schemaVersion`、`generatedAt`、`operator`、`fields`（key→value/source）、`attachments`（path/bytes/sha256/role）、`couponRows`（券批次行）、`aggregations`（单渠道/全渠道汇总）、`openIssues`。未来 OA 写入 API 就绪后由服务端直接消费。 |
| `validation-report.md` | 逐项校验结果（通过/警告/待确认）。 |

生成后在对话中展示 `oa-form-draft.md` 全文，请业务员确认或修改；修改后重新生成文件。

**结束语必须包含**：底稿不会自动进入 OA；请到飞书 OA 原生表单人工填写、核对并提交；附件请以原文件上传。

## 异常处理

| 场景 | 行为 |
| --- | --- |
| Excel 打不开 / 非 xlsx | 请业务员重新导出，不猜内容 |
| OA 数值与两套汇总都对不上 | 口径追问，必须业务员选择或写差异说明 |
| 截图文字模糊 | 该字段标「待确认」，请业务员补文字 |
| 必填字段/附件缺失 | 不生成底稿，只出追问清单 |
| 业务员要求直接提交 OA | 说明当前边界：P1 不具备 OA 写入能力，提交必须人工完成 |
