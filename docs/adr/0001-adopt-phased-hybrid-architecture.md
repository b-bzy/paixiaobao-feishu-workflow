## Context

爱回收需要把现有的报销 POC 演进为一个可由管理员配置、员工在飞书中
调用、审批人处理且结果可追踪的企业 Skill 工作流平台。后续还可能增加优惠券、
业务提单、邮件发送、数据查询以及多 Agent 协同等能力。

当前已经存在三种实现形态：

- 飞书机器人和交互卡片承担员工、审批人的入口。
- Vercel 上的 Nitro/Node.js 服务处理报销逻辑，并读写飞书 Base。
- 妙搭承担管理员控制面，提供飞书身份、组织权限和配置页面。

飞书消息事件改为通过公网 HTTPS 回调直接发送到 Vercel。Vercel 能快速完成 POC，
但中国大陆网络、企业合规、数据驻留和生产可用性尚未完成验证。妙搭适合配置
后台，却不适合单独承担完整事件网关、消息队列和多 Agent 运行时。

本次决策需要同时回答：

1. POC 阶段是否继续使用 Vercel。
2. 妙搭、Base、飞书 CLI 分别处于什么位置。
3. 正式环境如何去除桌面端依赖。
4. 如何避免当前实现阻碍未来多 Skill、多 Agent 和外部数据库接入。

## Decision Drivers

按当前产品目标确定以下优先级：

1. 员工在飞书内完成调用和审批，不额外学习独立系统。
2. 管理员可以配置、发布、回滚和控制 Skill 的适用范围。
3. 事件入口全天在线，不依赖个人电脑。
4. 权限、状态机、幂等和审计由确定性代码控制。
5. POC 上线速度快，且生产迁移成本可控。
6. 支持多 Skill、AI 调用、多 Agent 协同和企业系统集成。
7. 满足中国大陆网络、数据安全与企业合规要求。

## Considered Options

| 方案 | POC 速度 | 飞书实时交互 | 管理员配置 | 多 Skill / Agent 扩展 | 国内生产适配 | 结论 |
|---|---:|---:|---:|---:|---:|---|
| 全部部署在 Vercel | 高 | 高 | 需自研 | 高 | 中低 | 适合 POC，不直接承诺生产 |
| 全部使用妙搭 | 高 | 中低 | 高 | 中低 | 高 | 不满足实时网关与 Agent Runtime 要求 |
| Vercel + 妙搭 + Base | 高 | 高 | 高 | 中高 | 中 | 当前 POC 的最佳组合 |
| 国内云函数 + 独立后端 + 妙搭 + 企业数据库 | 中 | 高 | 高 | 高 | 高 | 正式环境目标架构 |
| 自建服务器或 Kubernetes 全栈 | 低 | 高 | 需自研 | 高 | 高 | 当前复杂度和运维成本过高 |

## Decision

采用“POC 与正式环境分阶段、职责分层”的混合架构，而不把全部能力集中在
Vercel、妙搭或飞书 Base 中。

### 当前 POC

```text
员工 / 审批人
      ↓
飞书机器人、消息、交互卡片
      ↓
Vercel HTTP 回调网关
      ↓
Vercel：Nitro API + 业务规则 + Skill 调度
      ↓
飞书 Base：模板、实例、审批结果

管理员
      ↓
妙搭控制面：模板配置、版本发布入口与运营查看
```

- 保留 Vercel，快速验证报销业务闭环。
- 飞书继续作为员工和审批人的唯一主要入口。
- Base 暂时承担模板和实例存储；妙搭承担管理员配置页面。
- `lark-cli` 只作为开发、调试和运维工具，不进入运行链路。
- 业务代码保持平台无关，不使用只能在 Vercel 运行的核心业务能力。

### 正式环境目标

```text
员工 / 管理员 / 审批人
          ↓
飞书交互层
          ↓
国内云函数 HTTP 实时事件网关
  ├─ challenge / 签名校验
  ├─ 3 秒内快速响应
  ├─ 幂等、重试、入队
  └─ 统一事件格式
          ↓
业务后端 / Agent Runtime
     ┌────┼─────────┐
     ↓    ↓         ↓
模板服务  工作流引擎  Skill / Agent 调度
     └────┼─────────┘
          ↓
企业数据库 + 消息队列 + 审计日志
          ↑
妙搭管理员控制面
```

- 国内云函数承担薄事件网关，优先评估腾讯云 SCF，其次阿里云 FC；最终选择需
  结合爱回收现有云账号、网络和采购标准确认。
- 网关只做鉴权、快速响应、去重、入队和转发，不执行耗时 AI 推理。
- 独立业务后端承担模板解析、确定性工作流、权限、审计及外部系统集成。
- 妙搭承担配置、角色权限、运营页面和人工处理入口。
- Vercel 对管理操作再次鉴权，并负责版本发布和任务执行。
- 妙搭不承担实时事件网关，也不形成第二套事实源。
- Agent 负责意图识别和 Skill 路由；确定性代码负责审批路径、金额阈值、状态
  变化、幂等和最终写入。
- 正式数据进入企业批准的 PostgreSQL/MySQL。Base 可保留为 POC 数据源或运营
  视图，但不与企业数据库长期双写。

## Component Ownership

| 层级 | 选型 | 核心职责 | 明确不负责 |
|---|---|---|---|
| 飞书交互层 | 机器人、消息、Card 2.0 | 发起、审批、通知、查询 | 核心状态与规则 |
| 实时事件网关 | POC 为 Vercel HTTP 回调；生产可迁国内云 | 验签、快速 ACK、幂等、入队 | AI 推理和长业务事务 |
| 业务后端 | TypeScript/Node.js | 规则、权限、API、外部集成 | 管理页面搭建 |
| 模板配置 | 妙搭控制面 + Vercel 管理 API | 草稿、版本、发布、适用范围 | 运行时自由修改历史实例 |
| 工作流引擎 | 早期自研状态机 | 状态转换、审批任务、补偿、审计 | 由大模型自主决定审批结果 |
| Agent / Skill | 独立运行时与注册表 | 意图、路由、工具调用、协同 | 绕过权限和业务校验 |
| 数据存储 | POC 为 Base；生产为企业数据库 | 模板快照、实例、事件、审计 | 依赖三方长期双写 |
| 开发运维 | 飞书 CLI、日志、监控和密钥服务 | 调试、发布、告警、回放 | 依赖开发者桌面常驻 |

## Migration Triggers

出现以下任一情况时，应从当前 Vercel POC 进入国内生产架构迁移：

- 开放给测试团队以外的真实员工使用。
- Vercel 回调在中国大陆的可用性不能满足业务目标。
- 涉及真实财务、客户或其他受监管数据。
- 回调三秒超时、跨境网络或 Vercel 可用性影响验收。
- 日事件量、AI 任务量或外部系统调用需要队列和弹性扩缩容。
- 企业安全、法务或 IT 要求数据驻留在指定国内云。

在正式迁移前，必须由企业补充确认：首选云厂商、数据分级和驻留要求、预计并发
与事件量、可用性目标、现有数据库/OA/财务系统接口，以及允许使用的模型供应商。
这些信息影响具体产品与容量选择，但不改变本 ADR 的分层边界。

## Consequences

### Positive

- 当前可继续复用已工作的 Vercel POC，减少重复开发。
- 员工和审批人的体验始终留在飞书内。
- 妙搭发挥低代码配置优势，同时避免承担不擅长的实时基础设施职责。
- 生产事件入口不再依赖个人电脑或本地 CLI。
- 业务规则、数据和渠道解耦，后续可以新增优惠券、提单、邮件和数据查询 Skill。
- 多 Agent 只新增调度与执行能力，不破坏审批、权限和审计边界。

### Negative

- POC 和正式环境存在两套部署形态，需要提前保持接口和业务层可迁移。
- 混合架构比单一平台多出网关、配置同步和监控边界。
- 从 Base 迁往企业数据库需要数据模型迁移和对账。
- 国内云厂商尚未根据企业现有基础设施最终确认，迁移预算仍需评估。
- 妙搭、业务后端和数据库之间必须定义清晰 API，避免形成双事实源。

## Validation

POC 通过以下条件后，才视为本阶段架构有效：

- 管理员发布模板后，员工调用的是最新已发布版本。
- 一次提交只产生一个流程实例，重复事件和点击不会重复处理。
- 只有配置的审批人可以通过或驳回。
- 历史实例永久绑定发起时的模板版本。
- 申请人可以收到结果，管理员可以查询完整状态和审计记录。
- 至少完成 20 次端到端测试，包括重复、越权、模板升级和失败重试。
