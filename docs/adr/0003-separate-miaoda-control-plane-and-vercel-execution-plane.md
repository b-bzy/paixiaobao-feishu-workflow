# 0003. 妙搭承载管理控制面，Vercel 承载任务执行面

Date: 2026-09-27

## Status

Accepted

## Context

平台需要同时满足两类不同需求：

- 管理员需要使用飞书身份、组织架构、人员与部门选择器，配置并发布 Skill。
- 员工通过飞书调用后，系统需要可靠处理回调、工作流、Agent、审批和外部系统。

妙搭在飞书内部身份、应用可见范围、业务角色和低代码管理页面方面更方便；Vercel
更适合承载标准 HTTP API、事件回调、任务执行、AI/Agent 和外部系统集成。把所有
能力集中在任一平台都会放大其短板。

同时，当前存在飞书 Base 和妙搭 PostgreSQL 两套体验数据。如果妙搭、Base 和
Vercel 后端分别保存正式模板或流程状态，将产生多事实源、版本漂移和审批状态
不一致。

## Decision

采用控制面与执行面分离的混合架构：

```text
管理员
  ↓
妙搭管理控制面
  ├─ 飞书登录与组织身份
  ├─ Skill / 模板草稿
  ├─ 表单与审批规则配置
  ├─ 人员、部门和适用范围
  ├─ 发布、回滚入口
  └─ 运行状态与异常展示
          ↓ HTTPS 管理 API
Vercel 执行面
  ├─ 管理员身份和业务权限复核
  ├─ 飞书 HTTP 回调网关
  ├─ 配置校验与版本发布
  ├─ 工作流引擎
  ├─ Agent / Skill 调度
  ├─ 异步任务与重试
  └─ 飞书消息、卡片和外部系统调用
          ↓
统一事实数据库
  ├─ 已发布 Skill 与不可变版本
  ├─ 模板快照
  ├─ 任务与审批实例
  ├─ 事件幂等记录
  ├─ 执行与通知记录
  └─ 操作审计
```

### 妙搭的职责

- 承载管理员页面和飞书内访问体验。
- 管理应用可见范围和页面级角色。
- 提供飞书人员、部门和群组选择能力。
- 编辑 Skill、表单、审批规则和适用范围。
- 发起发布、回滚、重试和人工补偿操作。
- 展示 Vercel API 返回的任务、日志、指标和异常信息。

妙搭不能直接决定最终业务权限，也不直接推进工作流状态。

### Vercel 的职责

- 接收飞书消息、卡片和审批事件回调。
- 对妙搭发起的管理操作执行身份、角色和数据权限复核。
- 校验草稿，生成不可变的已发布版本。
- 创建任务实例并绑定提交时的配置版本。
- 执行工作流、Agent、Skill、AI 和外部系统调用。
- 实现幂等、异步队列、重试、死信、审计和通知。
- 向妙搭提供稳定、版本化的管理 API。

Vercel 是计算与服务托管平台，不作为业务数据库。函数本地磁盘、进程内存和
进程内队列不得保存关键状态。

### 数据归属

| 数据 | 权威存储 | 说明 |
|---|---|---|
| 页面偏好、筛选条件 | 妙搭数据库 | 非关键数据 |
| 未发布草稿 | 妙搭数据库或统一数据库 | 必须带草稿版本和所有者 |
| 已发布 Skill | 统一数据库 | Vercel 校验并写入 |
| 模板版本快照 | 统一数据库 | 发布后不可变 |
| 任务和审批实例 | 统一数据库 | 唯一事实源 |
| 事件、执行、通知、审计 | 统一数据库/日志系统 | 可查询、可追踪 |
| Base POC 数据 | 飞书 Base | 迁移前的临时数据源 |

POC 可以继续使用飞书 Base，但目标是迁移到独立 PostgreSQL。妙搭 PostgreSQL
不保存正式任务状态，也不与统一数据库长期双写。

### 发布合同

```text
管理员在妙搭编辑草稿
          ↓
点击发布
          ↓
妙搭携带可验证的用户身份调用 Vercel 管理 API
          ↓
Vercel 复核管理员角色、校验配置、生成版本号
          ↓
写入统一数据库中的不可变版本
          ↓
员工下一次调用开始使用新版本
```

已运行的任务永久绑定创建时的版本快照，不受后续发布或回滚影响。

### 安全边界

- 妙搭页面隐藏按钮不等于后端授权，所有写操作必须由 Vercel 再次鉴权。
- 不使用一个永久共享密钥代表所有管理员；Vercel 必须能识别实际操作者。
- 管理 API 使用短期身份凭证、防重放和细粒度权限。
- 发布、回滚、终止、重试和人工补偿必须写入审计日志。
- Secret 仅保存在受控环境变量或密钥服务中，不写入妙搭表单和业务数据库。

### 当前 POC 管理端实现

管理员前端源码位于主仓库的 `apps/miaoda-admin/`，作为可独立构建的妙搭页面包维护。它调用 Nitro 的 `/api/admin/*` 完成模板草稿保存、发布和流程查询；该 API 继续读写飞书 Base POC，而非原妙搭项目的 PostgreSQL。

本地联调可通过 `ADMIN_AUTH_MODE=development` 和 `ADMIN_DEV_OPEN_IDS` 显式模拟管理员身份。该方式只在非生产环境允许，生产环境必须 fail closed；妙搭正式部署前仍须实现可验证的身份透传、后端角色复核和审计操作者记录。本段记录的是当前 POC 的实现约束，不取代本 ADR 对正式短期身份凭证与细粒度权限的要求。

## Consequences

### Positive

- 利用妙搭的飞书身份、组织权限和管理页面能力，减少后台基础开发。
- Vercel 保留复杂工作流、多 Skill、多 Agent 和外部集成的扩展自由。
- 管理界面与执行引擎通过 API 解耦，未来可以替换任一侧。
- 员工和审批人继续在飞书中工作，不需要进入管理员系统。
- 统一数据库避免模板、任务和审批状态出现多份冲突记录。

### Negative

- 妙搭、Vercel 和数据库形成跨平台链路，故障定位与监控更复杂。
- 必须设计身份传递、管理 API、跨域、超时和接口版本兼容。
- 草稿与已发布版本位于不同存储时，需要清晰的发布事务和失败反馈。
- 正式 PostgreSQL、持久化队列、日志和备份需要独立选型与成本。

成本预算和阶段性组合见
[总体架构选型的成本估算](../architecture-decision.md#16-架构组合成本估算)。成本属于
可变运营数据，不在本 ADR 中固化具体供应商报价。

## Validation

- 未加入妙搭管理范围的人员不能进入管理页面。
- 绕过妙搭直接调用管理 API 时，Vercel 仍能拒绝越权请求。
- 发布后统一数据库产生唯一、不可变的新版本和操作者审计记录。
- 妙搭下线或管理员退出登录不会中断已发布 Skill 的员工调用。
- Vercel 重启或扩缩容不会丢失任务、审批和重试状态。
- 同一个任务只存在一个权威状态，Base 和妙搭数据库不承担正式双写。
