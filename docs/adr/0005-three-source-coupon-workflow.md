# ADR-0005：三源优惠券 OA 采用配券表优先与两次确认提交模式

- **状态**：提议中；待业务、流程、模板与技术 Owner 批准
- **日期**：2026-10-08
- **关联**：[三源优惠券 OA 填报 PRD v1.0](../oa-ticket-reimbursement-materials/proposals/three-source/coupon-oa-three-source-workflow-prd-v1.md) · [ADR-0004](0004-bot-confirmed-submit-for-coupon-oa.md)

## 背景

当前 P1 Excel 试点仅支持受限的常规满减券与单列 SKU 白名单；旧 `OA优惠券填报` Skill 则只能生成供业务员手工录入原生 OA 的底稿。新的业务流程需要消费三类任意布局源表：配券表、白名单和可选黑名单，并让业务员在正式发起 OA 前明确确认来源映射、黑名单缺省和白黑名单重叠。

飞书不提供可 API 写入的客户端草稿箱。按照 ADR-0004，系统必须先保存自有业务草稿；创建原生审批实例即发生真实提交，必须在明确最终确认后进行。

## 决策

采用独立的“三源优惠券 OA”工作流：

```text
源配券表（字段第一来源）
+ 源白名单（必传）
+ 源黑名单（上传或显式确认无）
  → 版本化标准数据包
  → 第一次确认：映射、缺省确认、重叠决策
  → 标准附件 + OA 预填快照
  → 第二次确认：确认并发起 OA
  → 创建并回读飞书原生 OA
```

### 决策规则

1. 配券表是业务字段的第一来源；业务员文本仅用于补充缺失字段或经明确记录的覆盖。
2. 白名单必须上传；黑名单未上传必须由业务员明确确认“本次无黑名单”。文件错误、空表或解析失败不能作为缺省确认。
3. 白名单与黑名单交集不得静默处理。业务员必须选择白名单优先、黑名单优先或修改源文件；决定绑定当前 source hash 和 overlap hash。
4. 源文件不可变、不可直接作为 OA 标准附件。OA 只使用从同一 canonical revision 生成、冻结、重新下载并 hash 校验的标准产物。
5. 标准白名单、黑名单模板必须先经业务 Owner 确认、版本化并登记；未登记时流程 fail closed，不能创建 OA。
6. 新流程采用拟议的唯一触发口令 `/OA优惠券提报`、专用存储和功能开关；在服务端路线获批前，不覆盖旧手工 OA 路径或当前 P1 Excel 试点。
7. 第二次确认的服务端回调复用 ADR-0004 的系统草稿、审批定义 hash 守卫、确定性幂等键和创建后回读。无第三次用户确认。

## 理由

- 同一份标准数据包同时生成标准附件和 OA 快照，避免重复录入后的口径漂移。
- 明确的无黑名单和重叠决策把商品范围责任交给业务员，避免系统在不可逆业务选择上猜测。
- 保留源文件 provenance、模板版本和 hash，使提交后能追溯 OA 中每个附件和关键字段的来源。
- 使用独立流程允许现有 P1 试点继续运行，并在正式迁移前进行灰度和回归验证。
- 复用当前审批提交安全边界，避免重建既有的 definition hash、附件上传与回读止损能力。

## 后果

### 正向

- 业务员可用任意布局的源表完成受控提单；
- 标准附件、OA 预填和最终提交保持同 revision；
- 黑名单缺省、冲突处置、人工覆盖均可审计；
- 新券型和模板可通过版本化 manifest 逐项扩展。

### 约束与成本

- 需要新的专用 Base 表、卡片交互、数据模型、测试 fixture 和功能开关；
- 需要业务 Owner 提供正式白名单/黑名单模板和映射规则；
- 需要维护两套流程一段时间，直到迁移批准；
- 不能把“任意布局”扩大解释为“不受限的券型和业务公式”。

## 不采用的方案

| 方案 | 不采用原因 |
| --- | --- |
| 直接把三份源表传为 OA 附件 | 不能保证格式、口径、名单冲突和 OA 字段一致性 |
| 黑名单缺失时自动当作无黑名单 | 可能因漏传产生商品范围风险，且不可审计 |
| 固定黑名单优先或白名单优先 | 属于业务决策，未获授权时不能由系统默认 |
| 在现有 Excel 试点状态机上继续叠加 | 当前试点范围、输入来源和状态含义均不同，增加回归风险 |
| 由本地 Claude Skill 直接创建 OA | 缺少服务器凭证、身份、审计、幂等和回读保护，不符合 ADR-0004 |
