# 爱回收飞书工作流 POC 架构基线 v1.0

> 状态：当前 POC 已采用（Architecture Baseline v1.0）  
> 更新日期：2026-09-28  
> 当前案例：员工财务报销  
> 产品目标：管理员配置模板，员工通过飞书调用，审批结果可追踪  
> 适用范围：本文件只描述当前已实施或已确认用于 POC 的架构，不构成正式生产技术栈承诺。  
> 规模假设：POC 测试人员不超过 10 人；后续首批正式上线人员约 30 人。

## 1. 决策摘要

当前 POC 采用分层混合架构：

1. **飞书**是员工发起、审批人处理和结果通知的主要交互入口。
2. **妙搭**是管理员控制面，提供飞书身份、组织权限体验和配置页面。
3. **Vercel Hobby（免费版）**托管开发测试环境的 Nitro/Node.js 服务，接收飞书 HTTP 回调并执行报销 POC 业务逻辑；正式上线前切换至付费正式版本或企业批准的执行环境。
4. **飞书 Base** 暂存已发布的模板、流程实例和审批结果。
5. **飞书 CLI**只用于授权、调试和运维，不参与线上运行链路。
6. 权限、模板版本、审批状态和最终数据写入由确定性业务代码控制；AI 不得自主决定审批结果。

当前 POC 只验证报销闭环，不将国内云函数、正式企业数据库、持久化队列或多 Agent 运行时视为已采用组件。这些项目进入后续阶段前，必须按照[后续技术选型决策](future-technology-selection.md)完成评估。

## 2. 当前 POC 架构

```text
管理员
  ↓
妙搭管理员控制面
  ├─ 飞书登录与组织权限体验
  ├─ 模板配置与发布入口
  └─ 流程状态与异常查看
          ↓ 管理接口（逐步完善）

员工 / 审批人
  ↓
飞书机器人、消息与交互卡片
  ↓ HTTPS POST
Vercel Hobby（开发测试）的 Nitro 服务
  ├─ 飞书 challenge 与 Token 校验
  ├─ 消息、表单和审批回调处理
  ├─ 模板版本校验
  ├─ 报销实例与审批状态变更
  └─ 飞书卡片和消息发送
          ↓
飞书 Base（POC 数据源）
  ├─ 已发布模板
  ├─ 报销实例
  └─ 审批结果
```

员工和审批人不需要进入妙搭页面；妙搭只提供管理员配置和运营体验。Vercel 是 POC 的计算和 API 承载平台，不是数据库。

## 3. 组件职责与边界

| 层级 | 当前 POC 选型 | 核心职责 | 明确不负责 |
|---|---|---|---|
| 交互层 | 飞书机器人、消息、Card 2.0 | 发起报销、填写表单、审批、通知 | 保存核心状态、执行审批规则 |
| 管理控制面 | 妙搭 | 管理员身份体验、模板配置入口、组织范围和运营查看 | 最终业务授权、推进正式流程状态 |
| 回调与业务服务 | 开发测试：Vercel Hobby + Nitro/Node.js；正式上线：付费正式版本或企业批准执行环境 | 接收 HTTP 回调、校验、业务规则、版本校验、审批状态和飞书 API 调用 | 依赖函数内存或本地磁盘保存关键状态 |
| POC 数据存储 | 飞书 Base | 模板、实例和审批结果的 POC 存储 | 正式财务系统的长期主库、复杂事务处理 |
| 开发运维工具 | 飞书 CLI、日志和环境变量 | 授权、调试、资源管理和故障定位 | 线上事件消费或个人电脑常驻服务 |

妙搭的页面可控制谁能进入管理体验，但不能替代 Vercel 对管理操作和流程操作的后端鉴权。

## 4. 当前业务链路

### 4.1 员工发起报销

```text
员工发送“发起报销”类消息
  ↓
飞书向 POST /api/feishu/process 发送事件
  ↓
Nitro 校验 Token 并识别报销意图
  ↓
读取 Base 中当前已发布的模板
  ↓
向员工发送报销表单卡片
```

### 4.2 提交与审批

```text
员工提交表单卡片
  ↓
飞书回调 POST /api/feishu/process
  ↓
校验模板版本并创建 Pending 实例
  ↓
向配置的审批人发送审批卡片
  ↓
审批人通过或驳回
  ↓
更新 Base 中的实例状态并通知申请人
```

当前实现的入口文件是 `server/api/feishu/process.post.ts`，业务事件处理位于 `server/lib/feishu/events.ts`。根路由 `server/routes/index.get.ts` 仅返回服务健康状态，不处理报销业务。

## 5. 已接受的 POC 技术约束

### 5.1 HTTP 回调作为统一入口

飞书事件和卡片回调统一使用公网 HTTPS 发送到 Vercel，不依赖本地电脑或 CLI 长连接。回调端点须处理 URL challenge 和 Token 校验，并对不支持的事件返回明确结果。

### 5.2 开发测试与正式上线的 Vercel 边界

开发测试阶段使用 **Vercel Hobby（免费版）**，仅面向不超过 10 名测试成员和测试数据，用于验证回调、模板、提交和审批闭环。Hobby 环境不承载真实财务生产数据，也不作为对正式员工开放的稳定性或合规承诺。

首批正式上线前，必须切换到 Vercel 的付费正式版本，或完成[后续技术选型决策](future-technology-selection.md)并迁移到企业批准的执行环境。约 30 名正式用户的预估流程量仍属低量级，但不能以用户数量小为由跳过数据、审计、可靠性和企业合规检查。

### 5.3 异步处理边界

### 5.4 版本、权限与幂等

- 员工提交时使用模板版本；模板更新后，历史实例仍绑定原版本。
- 只有配置的审批人可以改变审批结果。
- 创建实例和处理事件必须逐步补齐唯一业务键、事件去重和条件状态更新，防止重复回调或重复点击产生多笔申请。
- 已发布模板、实例和审批结果在 POC 阶段以飞书 Base 为事实源；不得再创建未协调的第二份正式状态。

### 5.5 安全与配置

- 飞书 Verification Token、App Secret 等 Secret 只保存在 `.env.local` 或受控部署环境变量中。
- `.env.local` 不提交 Git；`.env.example` 只提供变量名称和非敏感示例。
- 服务端应记录必要的失败日志，但不得在日志中写入 Secret 或不必要的敏感业务数据。

### 5.6 管理端实现与开发身份

- 妙搭管理员前端以 `apps/miaoda-admin/` 的独立 Vite 包与 Nitro 服务同仓维护、独立构建；它仅提供总览、模板草稿/发布和实例查询，不提供员工提交或审批决策页面。
- `/api/admin/*` 是 Base POC 的唯一管理读写入口。模板与实例继续由飞书事件服务和同一份 Base 数据模型使用，管理端不引入妙搭 PostgreSQL 的第二份状态。
- 当前仅用于本地联调的 `ADMIN_AUTH_MODE=development` 通过显式白名单模拟管理员 Open ID，且生产环境必须拒绝该模式。它不是上线鉴权方案；妙搭部署前必须传递可验证的实际飞书操作者身份，并由后端复核角色和数据权限。

## 6. POC 范围与非目标

### POC 要验证的能力

- 管理员配置并发布报销模板。
- 员工通过飞书机器人打开并提交已发布模板。
- 审批人通过飞书卡片通过或驳回申请。
- 申请人和管理员能够追踪状态、操作人和模板版本。
- 模板升级、重复事件和越权审批能被正确处理或拒绝。

### 当前不承诺的能力

- 正式财务生产数据的长期存储和迁移。
- 企业数据库、队列、对象存储、日志平台或国内云供应商的最终选型。
- 多级审批、复杂 SLA、附件 OCR、多 Agent 协作和全面的死信/重放能力。
- Vercel 在中国大陆的生产可用性、数据驻留或合规保证。

## 7. POC 验收与迁移触发条件

POC 通过以下条件后，才视为本阶段架构有效：

- 管理员发布模板后，员工调用的是最新已发布版本。
- 一次提交只产生一个流程实例；重复事件和点击不产生重复处理。
- 只有配置的审批人可以通过或驳回。
- 历史实例永久保留发起时的模板版本。
- 申请人可收到结果，管理员可查询完整状态和必要日志。
- 至少完成 20 次端到端测试，覆盖重复、越权、模板升级和失败场景。

出现以下任一情况时，应启动后续技术选型，而不是直接把 POC 组件当作生产方案：

- 开放给测试成员以外的真实员工使用。
- 涉及真实财务、客户或其他受监管数据。
- Vercel 回调在中国大陆的可用性、延迟或数据要求不满足业务目标。
- 日事件量、AI 任务量或外部系统调用需要持久化队列、重试、死信和弹性扩缩容。
- 企业安全、法务、IT 或采购要求使用指定云、指定数据库或指定模型服务。

## 8. POC 容量与成本边界

### 8.1 规模与工作量假设

人数不是容量的唯一指标。为便于 POC 验证和成本预估，当前按每位参与者每月最多发起约 10 个报销流程进行保守规划：

| 阶段 | 参与人数 | 规划流程量 | 架构判断 |
|---|---:|---:|---|
| POC 测试 | 不超过 10 人 | 不超过约 100 个报销流程/月 | 当前飞书 + 妙搭 + Vercel + Base 足以验证业务闭环，无需为吞吐量引入 Kubernetes、专用队列或高可用数据库。 |
| 首批正式上线 | 约 30 人 | 不超过约 300 个报销流程/月 | 人数和流程量本身仍属低量级；是否迁移不由吞吐量决定，而由真实财务数据、数据驻留、审计、可靠重试和企业采购要求决定。 |

实际每月报销频次、附件数量、AI 调用和外部系统调用会显著影响调用量与成本；这些假设应在试点开始前按真实数据更新。

### 8.2 POC 与正式上线成本预估

开发测试阶段使用 Vercel Hobby（免费版）+ 飞书 Base。对于不超过 10 名测试成员、约 100 个流程/月的规模，在复用现有妙搭与飞书权益、且不额外购买持久化队列、主数据库和对象存储的前提下，**Vercel 新增基础云资源成本按 ¥0/月估算**。

首批正式上线约 30 人、约 300 个流程/月时，切换至 Vercel 付费正式版本的基础资源可按 **¥144–180/月** 粗略预算。这个量级的成本仍以计划订阅和受控服务的最低消费为主，流程量从 100 增加到 300 不会让函数调用成本线性显著增长。

如选择腾讯云等国内正式执行面，也使用相同的容量假设：每位参与者每月最多约 10 个流程，约 30 人即约 300 个流程/月。此规模下，函数调用量通常不是主要成本，预算主要受数据库、队列、日志、对象存储和高可用要求影响；具体候选组合及估算见[后续技术选型决策](future-technology-selection.md)。

以上预算不是正式报价。供应商价格、地域、合同、流量、日志保留期以及企业现有资源都会改变实际成本。

## 10. 变更规则

- 不改变上述 POC 职责边界的实现细节，可直接进入开发任务。
- 会改变事件入口、事实源、核心职责边界或线上部署平台的改动，必须先在[后续技术选型决策](future-technology-selection.md)中完成评估，再新增 ADR 记录最终决定。
- 已接受的 ADR 不直接改写；新决策被接受后再形成下一版架构基线。
