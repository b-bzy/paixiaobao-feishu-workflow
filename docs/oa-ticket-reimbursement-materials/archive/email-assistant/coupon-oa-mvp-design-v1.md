# 优惠券 OA 邮件助手 MVP 设计方案 v1.0

> **归档说明**：历史“邮件草稿助手”方案，仅供决策追溯；当前产品基线为[优惠券 OA 智能提单 MVP PRD v1.2](../../product/coupon-oa-mvp-prd-v1.2.md)。  
> **原状态**：待邮箱草稿能力验证后进入开发  
> **日期**：2026-09-28  
> **范围依据**：[MVP 优先分期实施方案 v1.1](coupon-oa-mvp-phased-delivery-plan-v1.md)  
> **重要边界**：本设计不包含管理员界面、动态字段、附件、Excel、OA 审批直连、多个邮件类型或批量生成；系统只生成邮件草稿，绝不发送邮件。

## 1. 设计目标

业务员在飞书机器人中调用“OA 提单报销”内置模板，填写一段自由提报说明。服务端将说明和固定系统信息填入固定版本的优惠券 OA 邮件模板，在该业务员的授权邮箱中创建一封草稿，并返回可打开的草稿入口。业务员在邮箱内自行检查、编辑和点击发送。

```text
飞书机器人
  └─ 业务员：生成 OA 优惠券邮件
       ↓
单一“提报说明”输入卡
       ↓
Nitro 校验身份、保存草稿修订、渲染固定模板
       ↓
邮件草稿 Gateway 创建草稿（不具备发送方法）
       ↓
飞书结果卡：打开草稿 / 重新生成 / 取消 / 我已发送
       ↓
业务员在邮箱中手动发送
```

### 1.1 MVP 成功定义

- 业务员无需离开飞书即可发起并填写 OA 邮件内容；
- 系统能创建真实、可编辑的邮箱草稿，且主题、正文、收件人、抄送人来自固定模板；
- 任意失败均不丢失提报说明；
- 服务端代码没有任何邮件发送接口或发送能力；
- 业务员可以区分“草稿已生成”“我已发送（人工声明）”和“邮箱已确认发送（若未来有回调）”。

## 2. MVP 范围与非范围

| 范围内 | 非范围 |
| --- | --- |
| 单一内置“优惠券 OA 邮件”模板 | 管理员界面、妙搭配置页、模板编辑器 |
| 一段多行自由提报说明 | 优惠券结构化字段、券档、GMV、ROI、日期和规则校验 |
| 固定收件人/抄送人、主题和正文 | 业务员在机器人内改收件人/抄送人 |
| 创建、打开、重新生成、取消邮件草稿 | 自动发送邮件、批量邮件发送 |
| 草稿和人工发送声明的审计 | OA 审批创建、审批状态同步、建券回传 |
| 飞书机器人交互、Nitro 服务、Base POC 存储 | 图片/Excel/商品名单附件、多邮件类型、批量生成 |

## 3. 固定模板与内部配置

MVP 不建设配置界面。模板内容以代码/受控数据种子维护，变更通过需求评审、代码审查和部署发布完成。建议放在独立模块中，而不是写死在事件处理函数。

```ts
interface CouponEmailTemplateV1 {
  templateId: "coupon_oa_email";
  version: 1;
  invocationPatterns: string[];
  recipientOpenIdsOrAddresses: string[];
  ccOpenIdsOrAddresses: string[];
  subject: string;
  body: string;
}
```

模板只允许使用以下变量：

| 变量 | 值来源 | 说明 |
| --- | --- | --- |
| `{{applicantName}}` | 飞书用户身份；无法取得姓名时使用受控显示名/ID | 不允许由模型伪造。 |
| `{{generatedAt}}` | 服务端 ISO 时间经统一格式化 | 表示草稿生成时间，不代表发送时间。 |
| `{{requestText}}` | 业务员在输入卡填写的原文 | 保留原文，不做业务推断或金额计算。 |
| `{{templateVersion}}` | 固定模板版本 | 用于审计和问题追溯。 |

主题、正文、收件人、抄送人、适用人员范围也在该固定版本中维护。P0 不做自然语言生成或润色；这样可保证生成内容可复现，避免模型修改业务事实。

## 4. 业务员交互设计

### 4.1 发起

业务员向机器人发送以下任一关键词：

- `生成 OA 优惠券邮件`
- `调用 OA 提单报销`
- `发起优惠券 OA 邮件`

机器人只为该 Open ID 创建一份新的 `CouponEmailDraft` 修订，回复输入卡：

```text
标题：生成优惠券 OA 邮件
说明：请填写本次优惠券 OA 提报说明。系统将据此生成邮件草稿，
      不会发送邮件；请在邮箱内复核后手动发送。

[多行输入：提报说明]
[生成邮件草稿]
[取消]
```

### 4.2 填写与生成

1. 业务员填写一段 `requestText` 并点击“生成邮件草稿”。
2. Nitro 校验：调用人存在、文本去除空白后非空、长度未超过受控上限、操作卡属于本人和当前草稿修订。
3. 服务端保存输入快照和内容哈希，渲染模板并创建草稿。
4. 生成成功后发送结果卡；失败则保留输入并发送失败卡。

P0 不追问券种、活动、金额、附件或日期；这些能力从 P1 起逐步引入。

### 4.3 结果卡

```text
标题：OA 邮件草稿已生成
状态：待人工发送

模板：优惠券 OA 邮件 v1
草稿生成时间：2026-09-28 14:25
提报说明摘要：……

[打开邮件草稿] [重新生成] [取消草稿]
[我已在邮箱中发送]

提示：系统不会发送邮件。“我已发送”只记录你的确认；
若邮箱未提供状态回调，系统不能证明邮件已实际送达。
```

- **打开邮件草稿**：只跳转由邮件服务返回的草稿深链；若邮件系统不支持深链，显示草稿所在邮箱/文件夹及唯一草稿标识。
- **重新生成**：基于同一输入和模板版本请求草稿；服务端按幂等策略复用已有草稿，或明确记录为新草稿版本，不能静默产生未知重复。
- **取消草稿**：只取消系统内待处理状态，不删除业务员邮箱中的草稿；卡片提示业务员自行删除邮箱草稿。
- **我已在邮箱中发送**：只写入人工声明和时间，不能调用发送接口。

## 5. MVP 架构设计

### 5.1 组件与职责

```text
业务员
  ↓ 飞书文本消息 / 卡片回调
飞书机器人
  ↓ HTTPS POST /api/feishu/process
Nitro / Node.js 服务
  ├─ 优惠券邮件事件路由
  ├─ 固定模板渲染与字段校验
  ├─ 草稿修订、幂等和状态机
  ├─ Base POC 存储
  ├─ 邮件草稿 Gateway（仅 createDraft / getDraftStatus）
  └─ 飞书卡片通知
       ↓                         ↓
飞书 Base：草稿与审计          企业邮箱：草稿文件夹
```

| 组件 | MVP 职责 | 明确不负责 |
| --- | --- | --- |
| 飞书机器人/Card 2.0 | 发起、收集自由文本、展示结果与提醒 | 保存事实状态、发送邮件、审批判断 |
| Nitro 服务 | 鉴权、渲染、状态机、幂等、调用邮箱草稿能力 | 前端管理配置、直接 OA 审批、邮件发送 |
| 飞书 Base | POC 草稿、修订、草稿引用和审计的事实源 | 正式邮件归档、附件存储、生产主库 |
| 邮件草稿 Gateway | 在授权邮箱创建草稿，返回草稿标识/可选深链 | 发送邮件、修改发送结果 |
| 内部版本化配置 | 保存唯一模板、收件人、正文和调用关键词 | 供业务方在网页上编辑 |

### 5.2 与现有 POC 的复用和隔离

现有入口 `server/api/feishu/process.post.ts` 和事件路由 `server/lib/feishu/events.ts` 可继续作为飞书 HTTP 回调入口。MVP 应新增独立 `coupon-email` 领域模块，而不是在 `expense-poc.ts` 中加入分支：

```text
server/lib/feishu/
├── events.ts                         # 识别报销与 coupon-email 两类入口并委派
├── coupon-email/
│   ├── config.ts                     # 内置模板与调用关键词
│   ├── domain.ts                     # schema、状态、草稿类型
│   ├── cards.ts                      # 输入、成功、失败卡片
│   ├── service.ts                    # 草稿修订、渲染、幂等、业务流程
│   ├── store.ts                      # Coupon Email Drafts Base 表读写
│   └── mail-draft-gateway.ts         # 邮件草稿抽象与具体实现
├── base-store.ts                     # 继续仅服务当前报销 POC
└── expense-poc.ts                    # 保持现有报销能力，不与优惠券草稿共用实体
```

这样可避免优惠券邮件数据写入现有报销模板表或报销实例表，也避免优惠券关键词误触发报销审批流程。

### 5.3 邮件草稿 Gateway

邮箱厂商/API 尚未确认，因此 MVP 先定义能力边界而不假定具体接口：

```ts
interface MailDraftGateway {
  createDraft(input: {
    senderIdentity: { feishuOpenId: string };
    to: string[];
    cc: string[];
    subject: string;
    textBody: string;
    idempotencyKey: string;
  }): Promise<{
    providerDraftId: string;
    draftUrl?: string;
    createdAt: string;
  }>;

  getDraftStatus?(input: {
    providerDraftId: string;
  }): Promise<"Draft" | "Sent" | "Unknown">;
}
```

接口**故意没有** `send()` 方法。代码审查和自动化测试应证明不存在可用的邮件发送路径。

#### 邮箱草稿 Spike：开发前置门槛

在开发飞书业务流程前，先使用测试邮箱验证：

1. 服务能否在正确业务员邮箱中创建草稿，而不是公共/服务账号邮箱；
2. 是否返回可供业务员打开的草稿 URL 或可查询的草稿 ID；
3. 是否支持将飞书 Open ID 映射为邮箱身份，授权有效期如何维护；
4. 是否支持幂等键、草稿状态查询、删除/取消限制和审计；
5. 草稿生成失败时，是否能可靠区分鉴权、限流、参数、网络和邮箱侧错误。

若无法创建真实邮箱草稿，MVP 只可临时演示“生成 `.eml` 文件或可复制邮件文本”，但不得宣布 MVP 闭环完成。

## 6. POC 数据设计

MVP 不使用现有报销实例表，因为其字段和审批状态与优惠券邮件草稿不同。建议在同一 POC Base 新建独立表 `Coupon Email Drafts`，以新环境变量显式引用，避免隐式复用报销表。

| Base 字段 | 类型/示例 | 说明 |
| --- | --- | --- |
| `Draft ID` | `CED-<UUID片段>` | 系统业务主键。 |
| `Submitter Open ID` | 文本 | 权限判定依据。 |
| `Template ID` / `Template Version` | 文本/数字 | 固定为 `coupon_oa_email` / 版本号。 |
| `Revision` | 数字 | 每次修改输入或重新渲染时递增。 |
| `Request Text` | 长文本 | 业务员原始输入。 |
| `Rendered Subject` | 长文本 | 发送前渲染结果。 |
| `Rendered Body Hash` | 文本 | 追溯邮件内容，不必在日志重复落完整正文。 |
| `Recipient Snapshot` / `CC Snapshot` | JSON 文本 | 草稿生成时使用的固定收件人快照。 |
| `Provider Draft ID` / `Draft URL` | 文本 | 邮件服务返回的草稿标识与可选深链。 |
| `Status` | 单选 | 见状态机。 |
| `Manual Sent Declared At` | 日期时间 | 业务员点击“我已发送”的时间。 |
| `Provider Sent At` | 日期时间 | 仅由邮箱回调/查询写入。 |
| `Error Code` / `Error Summary` | 文本 | 失败可见、不可记录 Secret。 |
| `Request Hash` | 文本 | 幂等与内容一致性检查。 |
| `Created At` / `Updated At` | 日期时间 | 审计。 |

建议环境变量使用独立名称，例如 `FEISHU_COUPON_EMAIL_DRAFT_TABLE_ID`。现有报销相关的 Base 表和环境变量不改变。

## 7. 状态机、权限与幂等

### 7.1 状态机

```text
Draft
  → Rendering
  → DraftReady
  → AwaitingManualSend
  → ManualSendDeclared

Rendering → DraftFailed
Draft / DraftFailed / DraftReady / AwaitingManualSend → Cancelled
DraftReady / AwaitingManualSend / ManualSendDeclared → SentConfirmed
  （仅邮箱状态回调或查询确认后进入）
```

- `DraftReady`：邮箱草稿创建成功，尚未进行人工发送。
- `AwaitingManualSend`：已向业务员发出草稿提醒；是默认业务可见状态。
- `ManualSendDeclared`：业务员点击“我已发送”，不是邮箱事实。
- `SentConfirmed`：仅在邮件系统回调/查询返回已发送时使用；若 P0 没有该能力，此状态不出现。
- `Cancelled`：仅取消系统流程，绝不删除邮箱草稿。

### 7.2 权限与防重

1. 只有 `Submitter Open ID` 可打开、重新生成、取消或声明已发送自己的草稿。
2. 文本消息事件使用飞书 `event_id/message_id` 防重；卡片按钮使用 `Draft ID + Revision + action` 作为业务幂等键。
3. 创建草稿使用 `Draft ID + Revision + Request Hash` 作为 `MailDraftGateway` 幂等键。
4. 回调中收到过期修订、非本人操作或状态不允许的动作时，服务端拒绝并要求重新打开当前卡片。
5. 每次状态变更记录操作者 Open ID、动作、时间、前后状态、修订号和错误摘要；不记录邮件服务 Secret 或无必要的完整敏感内容。

## 8. 异常处理

| 场景 | 系统行为 | 业务员看到的结果 |
| --- | --- | --- |
| 未识别调用语 | 不创建草稿 | 说明当前仅支持 OA 优惠券邮件。 |
| 提报说明为空或超长 | 不调用邮箱 API | 定位输入问题并允许修改。 |
| 模板配置缺失/渲染失败 | 保留输入，记录内部错误 | “模板暂不可用，请稍后重试”。 |
| 邮箱身份未授权 | 不创建草稿 | “无法在你的邮箱创建草稿”，显示授权/联系路径。 |
| 邮箱 API 超时 | 状态为 `DraftFailed` 或待对账 | 不提示盲目重试；服务先按幂等键查询/重试。 |
| 同一操作重复点击 | 复用已有结果 | 返回已有草稿入口，不创建未知副本。 |
| 草稿 URL 不可用 | 保留 Provider Draft ID | 卡片说明草稿位置/标识，不将其标为生成失败。 |
| 业务员取消 | 取消系统记录 | 明确提示邮箱中的既有草稿需业务员自行处理。 |

## 9. 开发工作拆分与验收

### 9.1 实施顺序

1. **邮箱草稿 Spike**：先验证 `MailDraftGateway` 的真实可行性、身份映射、草稿链接与错误语义。
2. **领域基础**：固定模板、Zod schema、状态机、Base 草稿表和 store 测试。
3. **飞书入口与卡片**：新增调用关键词、单一输入卡、结果/失败卡，保持报销流程回归通过。
4. **草稿服务**：模板渲染、权限、修订、内容哈希、Gateway 调用、幂等与失败处理。
5. **审计与人工声明**：实现打开草稿、重新生成、取消和“我已发送”。
6. **端到端测试**：使用测试飞书用户和测试邮箱，验证真实草稿创建，全程不发送邮件。

### 9.2 MVP 验收用例

| 编号 | 用例 | 预期 |
| --- | --- | --- |
| AC-01 | 业务员发送调用关键词 | 收到单一“提报说明”输入卡，不触发报销流程。 |
| AC-02 | 提交合法说明 | 在该业务员测试邮箱中创建草稿，返回草稿入口。 |
| AC-03 | 检查草稿 | 主题、正文、收件人、抄送人和固定变量与模板版本一致。 |
| AC-04 | 不点击邮箱发送 | 系统只显示“待人工发送”，没有任何 OA/邮件已受理状态。 |
| AC-05 | 点击“我已发送” | 只记录人工声明；没有调用邮件发送 API。 |
| AC-06 | 同一操作重复点击 | 不生成无法识别的重复草稿。 |
| AC-07 | 他人操作草稿卡 | 服务端拒绝，且不泄露草稿内容或链接。 |
| AC-08 | 邮箱授权/API失败 | 原始说明留存、错误可见、允许按规则重试。 |
| AC-09 | 回归现有报销流程 | 原有“发起报销”入口、模板版本与审批流程不受影响。 |

## 10. MVP 后的衔接

该设计的扩展点只保留在领域模型和版本字段中，不提前实现后续 UI 或业务复杂度：

- **P1**：将 `requestText` 外增加预置的非附件字段 schema；
- **P2**：为草稿修订增加图片 Artifact 引用，并扩展 `createDraft` 输入附件；
- **P3**：增加 Excel 模板资产、列映射和受控计算服务；
- **P4**：将单一 `coupon_oa_email` 扩展为内部类型注册表；
- **P5**：引入批量任务实体和队列，每条记录仍创建独立 `CouponEmailDraft`。

这些阶段完成前，不建设管理员界面；若 P0–P5 已稳定且变更频率、权限治理和运营成本表明有必要，再以独立需求评估管理端。
