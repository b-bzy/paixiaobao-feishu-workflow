# 优惠券 OA 邮件助手：MVP 优先分期实施方案 v1.1

> **归档说明**：历史“邮件草稿助手”分期方案，仅供决策追溯；当前产品基线为[优惠券 OA 智能提单 MVP PRD v1.2](../../product/coupon-oa-mvp-prd-v1.2.md)。  
> **原状态**：当前实现基线，待业务与技术负责人确认  
> **日期**：2026-09-28  
> **重要边界**：P0–P5 **均不建设管理员界面、妙搭配置页或运营后台**。模板、字段、规则和收件人等配置先以版本化的内部配置文件/受控数据种子维护，由技术与业务 Owner 通过评审和部署变更；待全部核心功能验证完成后，再单独评估是否建设管理界面。  
> **关联 PRD**：[优惠券 OA 智能提单 MVP PRD v1.2](../../product/coupon-oa-mvp-prd-v1.2.md)。

## 1. 总体原则

1. 所有阶段都只生成**邮件草稿**，不自动发送。业务员必须在邮箱中核对并手动点击发送。
2. 每阶段只增加一类输入或产物，避免在 MVP 提前引入业务字段、附件、Excel、复杂规则、模板平台或批量任务。
3. P0–P5 使用**内置、版本固定的内部配置**。机器人和 AI 不决定收件人、模板、字段、业务规则或权限；配置变更走需求评审、代码/数据变更和发布流程。
4. “草稿已生成”“业务员确认已发送”和“邮箱已发送”是不同状态；无邮箱状态回调时，业务员确认仅是人工声明。
5. 当前只复用 POC 的飞书机器人、Nitro 服务和飞书 Base。妙搭管理员控制面不在当前开发范围内；真实附件、经营数据或正式员工接入前，再完成生产存储与合规评估。

## 2. 分期总览

| 阶段 | 目标 | 本阶段输入 | 本阶段输出 | 明确不做 |
| --- | --- | --- | --- | --- |
| **MVP / P0** | 验证 OA 邮件模板填写与草稿生成闭环 | 一段自由描述 + 内置身份/时间信息 | 一封可打开、可编辑的 OA 邮件草稿 | 自定义业务字段、附件、Excel、多个邮件类型、批量、管理员界面 |
| **P1** | 让邮件内容由结构化非附件字段驱动 | 预置的非附件字段 | 字段校验后的单封邮件草稿 | 附件、表格、多类型、批量、管理员界面 |
| **P2** | 支持图片证据材料 | P1 字段 + 图片附件 | 带图片附件的单封邮件草稿 | Excel/商品名单、多类型、批量、管理员界面 |
| **P3** | 支持业务表格填写与上传 | P1 字段 + 预置表格模板/表格文件 | 带自动生成或校验后表格的邮件草稿 | 多类型、批量、管理员界面 |
| **P4** | 支持多个 OA 邮件类型 | 选择的预置邮件类型及其规则 | 按类型生成的单封邮件草稿 | 一次生成多封、管理员界面 |
| **P5** | 支持一次生成多封独立草稿 | 多条独立提报记录 | 一条记录对应一封独立草稿 | 系统批量发送、管理员界面 |

> 本文的“表格”优先指配券信息表、商品白/黑名单等 Excel 业务表。若“图表”还包括可视化图表或测算图，应在进入 P3 时补充模板和生成边界。

## 3. MVP / P0：OA 邮件模板填写与生成

### 3.1 目标与用户路径

P0 只验证一个最小闭环：业务员调用内置 OA 邮件模板，提供一段自由提报说明，系统套用邮件内容并创建草稿；业务员在邮箱中自行编辑、核对和发送。

```text
业务员对机器人说“生成 OA 优惠券邮件”
            ↓
机器人收集一段“提报说明”并回显
            ↓
系统以固定版本的内置邮件模板渲染主题、正文、收件人和抄送人
            ↓
系统在授权邮箱创建草稿（绝不发送）
            ↓
机器人返回“草稿已生成”和打开草稿入口
            ↓
业务员在邮箱人工编辑、检查并点击发送
```

### 3.2 内置模板与固定变量

P0 使用一份由技术与业务 Owner 在发布前确认的内置“优惠券 OA 邮件”模板，不提供配置页面。模板仅使用以下固定变量：

| 变量 | 来源 | 示例用途 |
| --- | --- | --- |
| `{{applicantName}}` | 飞书登录身份 | 邮件落款/申请人 |
| `{{generatedAt}}` | 系统生成时间 | 草稿生成时间 |
| `{{requestText}}` | 业务员提交的一段自由描述 | 邮件申请背景与具体请求 |
| `{{templateVersion}}` | 内置模板版本 | 邮件底部追溯信息 |

收件人、抄送人、主题和正文由内置配置固定。业务员不可以在机器人内修改它们；如业务员确需变更，应在邮箱草稿中人工修改，并由邮件发送人承担核对责任。

### 3.3 P0 功能清单

| 编号 | 功能 | 优先级 |
| --- | --- | --- |
| P0-01 | 机器人识别“生成 OA 优惠券邮件”“调用 OA 提单报销”等关键词，创建本人草稿会话。 | Must |
| P0-02 | 机器人以一个多行输入框收集“提报说明”，回显后允许业务员修改。 | Must |
| P0-03 | Nitro 按内置邮件模板渲染主题、正文、收件人和抄送人。 | Must |
| P0-04 | 服务端创建授权邮箱草稿，保存草稿 ID、生成时间、内容哈希、模板版本和状态。 | Must |
| P0-05 | 机器人发送提醒卡，提供“打开草稿”“重新生成”“取消草稿”“我已发送”入口。 | Must |
| P0-06 | “我已发送”只记录人工声明；有邮件回调时，以回调状态为准。 | Should |
| P0-07 | 同一草稿修订重复点击“重新生成”时，按幂等策略复用已有草稿或清晰标识新草稿。 | Must |
| P0-08 | 申请人可查看本人草稿的生成、失败和人工确认记录。 | Should |

### 3.4 P0 明确不做

- 不增加优惠券业务字段，不校验券档、GMV、费用、ROI、时间或规则；
- 不上传图片、Excel、商品白/黑名单或任何附件；
- 不自动填写配券信息表、OA 审批表单或外部业务表；
- 不支持多个邮件类型或一次生成多封邮件；
- 不调用发送接口，不替业务员发送邮件；
- 不建设管理员界面、模板编辑器、规则中心、发布中心或运营看板。

### 3.5 P0 技术实现拆分

| 工作包 | 实现内容 | 依赖/产出 |
| --- | --- | --- |
| 邮件草稿可行性验证 | 验证企业邮箱是否允许应用以**业务员身份**创建草稿、返回草稿 ID/链接、保留审计信息。 | P0 前置门槛。不能创建真实草稿时，`.eml`/复制文本仅是测试降级，不能视为 P0 闭环。 |
| 飞书交互 | 调用意图、单一自由文本卡片、草稿结果卡和状态卡。 | 复用 POC 飞书回调、鉴权和卡片机制。 |
| 内置配置 | 在受版本控制的配置中固定邮件主题、正文、收件人、抄送人、适用组织与版本。 | 不建设配置 UI；变更经评审后随部署生效。 |
| Nitro 服务 | 草稿会话、模板渲染、服务端鉴权、邮件草稿 Adapter、幂等和失败重试。 | 邮件发送能力必须不存在或显式禁用。 |
| POC 数据 | 保存申请人、自由描述、草稿 ID/链接、状态、哈希、时间和审计。 | 飞书 Base 为 POC 事实源。 |

### 3.6 P0 验收标准

1. 业务员输入调用语和一段提报说明后，系统能在目标邮箱中创建可打开的草稿。
2. 草稿主题/正文包含正确的固定变量值和原始提报说明；仅申请人可通过机器人获得该草稿入口。
3. 系统从创建草稿到返回提醒卡的全过程不得调用任何邮件发送接口。
4. 未在邮箱人工发送时，系统状态必须是“待人工发送”，不得显示“已提报”或“OA 已受理”。
5. 草稿接口失败、权限不足或超时时，保留原始说明并展示失败原因，申请人可以重试。
6. 同一修订重复生成时，按幂等策略复用已有草稿或清晰标识新草稿，申请人可追溯全部结果。

## 4. P1：结构化字段（不含附件）

### 4.1 目标

将 P0 的单一自由描述升级为**预置的**非附件字段，让邮件正文由结构化数据可靠填充，但仍只生成一封邮件草稿。

### 4.2 新增能力

- 以内部版本化 schema 预置字段 key、名称、类型（文本、单选、多选、数字、金额、百分比、日期）、必填条件、枚举、默认值和邮件变量映射；
- 业务员通过动态卡片输入/更正字段，机器人仅追问缺失项；
- 字段类型、必填、枚举、格式和基础数值范围校验；
- 字段值写入主题和正文占位符，例如 `{{activityName}}`、`{{businessMode}}`、`{{activityStartAt}}`；
- 变更字段时由技术与业务 Owner 更新 schema 版本并随发布生效，不在本阶段提供字段设计器。

### 4.3 P1 不做

- 不上传附件；
- 不自动生成或解析 Excel；
- 不实现完整优惠券规则、跨表一致性、ROI 公式和商品主数据校验；
- 不支持多个邮件类型、批量生成或管理员界面。

### 4.4 P1 验收

预置字段可在同一模板中完成填写；不合法的类型/必填值无法生成草稿；生成邮件引用当前修订和字段 schema 版本的准确值。

## 5. P2：图片附件上传

### 5.1 目标

在 P1 字段基础上支持图片上传，并将经验证的图片附加到单封 OA 邮件草稿中。首期重点覆盖“具体满减测算图片”。

### 5.2 新增能力

- 在内部 schema 中预置图片字段、必填条件、允许格式、单文件/总大小、最大数量和邮件附件映射；
- 业务员在飞书卡片上传图片，系统保存原文件、校验 MIME/扩展名/大小/访问权限并提供预览；
- 生成草稿时按版本将图片复制或授权挂载为邮件附件；
- 上传失败、文件超限、附件缺失、邮件侧附件失败应清晰定位且阻断草稿生成；
- 保存附件哈希、原始文件引用、生成草稿附件引用和下载审计。

### 5.3 P2 不做

- 不 OCR、识别或判断测算图片内容；
- 不解析 Excel/商品名单；
- 不支持多邮件类型、批量草稿或管理员界面。

### 5.4 P2 验收

业务员能上传一张合规测算图片，草稿邮件中可见正确附件；文件权限、大小限制和失败重试有效；系统绝不以图片上传成功推定业务测算正确。

## 6. P3：表格填写与上传

### 6.1 目标

支持配券信息表、商品明细白/黑名单等 Excel 表格的**填写、生成、上传和邮件挂载**。本阶段才开始进入优惠券业务表格能力。

### 6.2 推荐拆法

1. **P3-A：单一配券模板**。先选定一个已确认模板（建议“常规满减券”），以 P1 字段映射填写受控单元格，生成 `.xlsx` 并附到邮件。
2. **P3-B：商品名单上传**。支持标准单列商家 ID/SKU/SPU 白/黑名单，完成列数、空值、维度混填与组合限制校验。
3. **P3-C：模板矩阵和计算**。逐步接入其余标准模板、费用/ROI 计算、渠道 × 券档配置行及 Excel 公式一致性校验。

### 6.3 P3 关键规则

- Excel 模板资产、列映射、公式和输出文件名以内部版本化资产维护；示意行不得出现在生成文件中；
- 表格写入、邮件正文和结构化字段必须来自同一申请修订；
- 所有金额计算由服务端受控引擎完成，Excel 公式用于导出与复核，不是唯一事实源；
- 当前案例中的多工作表 SKUID 明细在业务确认前只作为 P3-C/P4 的灰度能力，不替代标准单列名单；
- 生成或上传的表格均只作为邮件附件，仍不自动发送邮件；
- 不在 P3 建设模板库或管理页面，模板扩展通过评审后的资产发布完成。

### 6.4 P3 验收

先以一份确认模板完成“字段 → Excel → 邮件附件”的端到端演示；生成文件可由业务打开且格式、公式、行数与预览一致；不合规名单不能生成草稿。

## 7. P4：多个 OA 邮件类型

### 7.1 目标

将单一内置模板扩展为受治理的**内部邮件类型注册表**，例如优惠券申请、优惠券修改、返利提报、广告提报等。每种类型拥有独立字段、附件、表格、规则、收件人和邮件内容。

### 7.2 新增能力

- 由代码/数据配置预置多个邮件类型，包含适用组织、发起关键词、字段组、附件规则、表格模板、校验规则和邮件草稿渠道；
- 业务员在机器人中选择类型，或由明确关键字路由；歧义时必须要求选择，不能由模型猜测；
- 每种类型的版本、权限和历史实例独立绑定；
- 一种类型的一次申请仍只生成一封邮件草稿；
- 不提供类型创建、复制、发布、下线或回滚的管理界面，配置变更通过受控发布流程完成。

### 7.3 验收

两个预置邮件类型可完全独立运行；业务员选择后只能看到对应字段、附件和收件人配置；历史草稿不受后续配置版本影响。

---

## 8. P5：一次性生成多封 OA 邮件

### 8.1 目标

支持一个批量任务包含多条彼此独立的提报记录，每条记录生成一封独立、可单独审计和人工发送的 OA 邮件草稿。

### 8.2 新增能力

- 支持粘贴、上传预置格式表或选择多条记录作为批量输入；
- 逐条解析、校验和生成，展示成功/失败/待补充清单；
- 每条记录独立申请 ID、修订、草稿 ID、附件、预算口径和审计；
- 支持失败单条修复后重试，不重跑已成功草稿；
- 使用后台任务、限流、幂等与可恢复队列，避免函数超时和重复草稿；
- 批量格式、字段映射和额度通过内部版本化配置维护，不建设批量任务管理后台。

### 8.3 严格边界

P5 的“批量”只指**批量生成草稿**：系统不得一键发送多封邮件，也不得把多个独立业务事项错误合并成一封邮件。业务员必须逐封在邮箱中审阅并手动发送。

### 8.4 验收

提交 N 条合法记录后，系统生成 N 封可区分的草稿；部分失败时成功草稿可用、失败项可定位和单独重试；全程不存在批量邮件发送接口调用。

## 9. 依赖、风险与实施顺序

### 9.1 先决事项

| 事项 | 影响阶段 | 结论 |
| --- | --- | --- |
| 企业邮箱草稿创建接口与授权方式 | MVP | 必须先做技术验证；无真实草稿能力时不得承诺 P0 闭环。 |
| 固定收件人/抄送人和邮件模板内容 | MVP | 由业务 Owner 确认后固化进版本化内部配置。 |
| 飞书用户身份与邮箱身份映射 | MVP | 需保证草稿在正确业务员邮箱中创建，或提供合规替代方案。 |
| 附件存储和下载权限 | P2 起 | 真实附件进入前完成数据分级、对象存储和审计评估。 |
| 正式 Excel 模板、字段字典、公式 | P3 起 | 未确认模板不能进入自动填写/计算。 |
| 商品和大促等主数据接口 | P3-C/P4 起 | 作为规则校验外部依赖，不由模型推断。 |
| 批量任务队列与限流 | P5 | 不能依赖 Vercel 单次同步请求完成。 |

### 9.2 建议开发顺序

1. **第 0 步：邮箱草稿 Spike**——验证草稿创建、业务员身份、草稿链接、附件上限、状态回调和权限。
2. **第 1 步：MVP/P0**——完成单模板、单自由描述、单封草稿、人工发送提醒。
3. **第 2 步：P1**——预置结构化字段与邮件变量映射。
4. **第 3 步：P2**——图片上传与附件安全链路。
5. **第 4 步：P3**——先一个 Excel 模板，再扩展商品名单与模板矩阵。
6. **第 5 步：P4**——多个预置业务类型和路由能力。
7. **第 6 步：P5**——批量生成、后台任务和批量处理能力。
8. **后续评估项**——在 P0–P5 功能稳定且有真实运维需求后，独立立项评估管理员界面；不影响既有功能实现。

## 10. 阶段完成门槛

任一阶段只有同时满足以下条件才能进入下一阶段：

- 该阶段验收用例全部通过；
- 生成结果、权限和审计可追溯；
- 没有任何自动发送邮件能力或绕过人工发送入口；
- 失败、重试、重复点击和权限不足场景已完成验证；
- 新增字段/附件/表格/模板已随版本化内部配置发布并完成测试；
- 真实数据与附件接入前完成对应的数据安全和合规确认；
- 未建设或依赖管理员界面作为任何 P0–P5 功能的前提。
