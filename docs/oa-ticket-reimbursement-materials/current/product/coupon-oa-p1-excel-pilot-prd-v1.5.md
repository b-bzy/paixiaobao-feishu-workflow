# 优惠券 OA 智能填报 P1 PRD v1.5（内网试点版）

> **状态**：P1 内网试点方案；优先验证 Excel 自动生成，不按生产级系统建设
> **版本**：v1.5
> **日期**：2026-09-30
> **试点规模**：约 10 名已知业务员、单一优惠券场景、Bot 单聊
> **本次调整**：基于 `配券信息表-常规满减券.xlsx` 的真实列、公式和数据验证补齐首期字段字典与映射；未确认枚举仍需业务 Owner 确认
> **上游参考**：`coupon-configuration-templates-and-fields-v0.md`、现有常规满减券模板、当前优惠券 OA 草稿实现

## 1. 目标

业务员在 Bot 对话中填写活动和常规满减券规则，上传手头已有的白名单 Excel。系统将信息整理成规范数据，自动生成：

1. 一份标准的常规满减券配券信息表；
2. 一份标准 SKU 商品白名单；
3. 一份自动填写的**系统 OA 草稿**：包含可复核字段和两份冻结 Excel 的版本化引用；`draft-only` 阶段绝不创建原生 OA，也不把 source 文件提升为审批附件。

业务员核对生成结果后确认。首期的成功标准是“**少量试点用户可以稳定得到两份格式正确、数据可核对的 Excel，并将其安全接入既有 OA 草稿链路**”，而不是建设全量模板平台或生产级工作流系统。

## 2. 试点边界

### 2.1 试点支持范围

| 项目 | 首期约定 |
| --- | --- |
| 用户 | 约 10 名已知业务员；仅 Bot 单聊；不支持群聊、转发协作、代办或替他人提单 |
| 优惠券场景 | 限品类平台券、常规用户、**常规满减券** |
| 配券模板 | 仅内置 `配券信息表-常规满减券.xlsx` 的业务 Owner 确认版本 |
| 券档 | 一次申请支持一个满减券档；可选择京东和/或拍拍两个渠道，系统按渠道生成一行或两行 |
| 白名单 | 仅 SKU；一个源 Sheet、一列来源 SKU、一个标准输出 Sheet、一列 `SKUID` |
| 源文件 | 仅 `.xlsx`；建议小于 2 MB、有效 SKU 不超过 3,000 条；超过上限走人工处理 |
| 对话 | Bot 先给字段清单，业务员一次性尽量填写；AI 提取后只追问缺项/歧义 |
| 运行方式 | 内网试点、低并发；允许在单次任务中同步解析和生成，但不免除 bridge 鉴权、稳定事件标识、持久去重、恢复与服务端授权要求；这些是进入受控试点的前置门禁。 |
| OA | P1-1 将确认后的冻结 Excel 的版本化引用写入系统 OA 草稿；draft-only 阶段禁止原生 OA 创建和 approval attachment 提升。仅在另行通过原生 OA canary/allowlist 门禁后，才可在后续最终确认路径即时上传批准附件并提交。 |

### 2.2 首期明确不做

- 折扣券、PLUS、兑换券、大促神券、店铺券、黑名单；
- 多券档、多 Sheet 白名单、SKU/SPU/商家 ID 混合处理；
- 商品主数据真实性、质检优品、商家承担比例等外部系统校验；
- 群聊、多人协作、代办、跨人文件、批量提单；
- 分布式锁、持久任务队列、复杂任务恢复、生产级容灾；
- 病毒扫描、深层 OOXML 安全扫描、完整合规治理；
- 自动提交 OA、自动审批、自动撤回。

不在首期范围的输入必须被明确提示“当前内网试点暂不支持”，不能被 AI 静默改写成常规满减券。

## 2.3 内网试点上线阶段

本 PRD 描述 P1-1 的受限产品能力；上线允许范围以 [优惠券 OA 内网试点 rollout 计划](../operations/coupon-oa-internal-pilot-rollout-plan-v1.md) 为准。首发为 `draft-only`：生成文件、系统草稿和人工复核可以开放给严格 allowlist，但任何原生 OA 创建 API 都必须被服务端拒绝。真实 OA 仅可在 bridge 鉴权/去重、权限 E2E、kill switch、原子业务幂等和 `SubmissionUnknown` 对账等 Gate 通过后的 canary/allowlist 阶段，由当前 owner 在当前 revision 明确确认后创建。

## 3. 分阶段交付顺序

| 阶段 | 内容 | 交付结果 |
| --- | --- | --- |
| **P1-1（当前）** | 对话采集、白名单源表映射、常规满减券和 SKU 白名单自动生成、人工确认、系统 OA 草稿自动填写与两份冻结产物引用 | 待用户补充材料并人工确认的系统 OA 草稿；原生 OA 与 approval attachment 提升受 rollout Gate 控制 |
| **P1-2** | 不再单列 OA 自动填写；后续仅按真实试点问题扩展核对、模板或流程能力 | 按需评估 |
| **P1-3** | 向两份生成文件写入“系统生成说明”页 | 带版本化说明的 Excel |
| **后续** | 新模板、批量、主数据、异步任务、生产增强 | 逐项评估，不进入本次试点 |

```text

  ↓

  ↓
AI 提取候选值 + 规则代码校验
  ↓

  ↓

  ↓

  ↓

  ↓
业务员确认映射
  ↓

  ↓
业务员确认输出版本
  ↓
系统从 Drive 重新下载并 hash 校验两份冻结文件，记录系统 OA 草稿引用；只有 native-submit Gate 通过后才可即时上传审批附件库
  ↓

```

```text

活动背景：
业务模式：寄卖 / pop / 严选
OA 活动点位（%）：（按 OA 业务口径明确填写，不等同于优惠比例）
申请人：
活动开始日期：YYYY-MM-DD
活动结束日期：YYYY-MM-DD
用券渠道：京东渠道 / 严选APP及小程序 / 两者
满减门槛（元）：
优惠面额（元）：
总申请数量：
单次到账张数：
每日领取次数：
可领时间：YYYY-MM-DD HH:mm 至 YYYY-MM-DD HH:mm
可用时间：YYYY-MM-DD HH:mm 至 YYYY-MM-DD HH:mm
预计领用率：
预计使用率：
平台承担比例：
预计引入 GMV（元）：
优惠券类型：东券（首期固定）
限品类型：限SKU（首期固定）
领券用户风控：0级以下用户可领（首期固定）
用户领券规则：活动期间仅可领一次 / 活动期间每天可领一次

公开推广渠道：全网推广 / 单品页购物车 / 领券中心 / 公开券池（推广途径为公开时必填，可多选）
是否超扣点：是 / 否
超扣点原因：

```

字段清单中未确认的模板枚举和默认值，由业务 Owner 在正式模板确认时补全；未确认前，Bot 必须要求业务员填写或停止试点，不得自行猜默认值。

### 4.2 AI 与规则代码的分工

| 能力 | AI API | 规则代码 |
| --- | --- | --- |
| 理解“满 100 减 5”“100-5”等表达 | 是 | 规范化后校验 |
| 识别漏填、同一字段冲突、未知文本 | 是 | 最终判定 |
| 判断金额、日期、比例格式是否有效 | 否 | 是 |
| 判断面额小于门槛、数量为正整数 | 否 | 是 |
| 计算名称、费用、ROI | 否 | 是 |
| 选择模板、判断是否支持 | 否 | 是 |
| 映射白名单候选列 | 可提出候选 | 用户确认后生效 |
| 生成 Excel、上传 OA、提交 OA | 否 | 系统流程控制 |

AI 输出必须先被解析为固定字段结构；提取不到、字段矛盾或单位不清时，系统只显示待补充项，不能用模型猜测继续生成。

## 5. P1-1 数据与映射规则

### 5.1 统一业务数据

系统维护一个当前试点版的 `generationInput`，作为配券表、白名单和后续 OA 的共同来源。它至少包含：

- 活动/OA 字段；
- 一组满减券档字段；
- 选中的规范渠道；
- 白名单源文件 hash、来源 Sheet、来源列和确认后的映射；
- 模板版本；
- 服务端计算出的名称、预计费用、ROI 和渠道汇总。

同一份 `generationInput` 生成的两份 Excel 必须使用同一个 `generationRevision`。用户修改字段、替换白名单文件或更换来源列时，旧输出作废，必须重新生成。

### 5.2 渠道映射

Bot 和 OA 使用的渠道文案与配券模板不同，首期采用固定映射：

| Canonical 渠道 | OA 文案 | 配券模板文案 |
| --- | --- | --- |
| `JD` | 京东渠道 | 京东商城 |
| `PAIPAI` | 严选APP及小程序 | 拍拍二手 |

业务员选择两个渠道时，系统复制同一个券档为两行，分别使用 `JD` 和 `PAIPAI`；不允许在同一配券行填两个渠道。

### 5.3 白名单映射

源白名单可以有额外列，如商品名、品牌、价格和链接，但首期仅提取一列 SKU：

1. 系统展示各 Sheet、候选列名、前若干个样例、非空行数和重复数；
2. 业务员确认一个来源 Sheet 和一个来源列；
3. 系统将该列按文本写入标准白名单模板的 `SKUID` 列；
4. 空值、重复 SKU、一个单元格包含多个 SKU、数值型 SKU 导致前导零丢失时，停止生成并提示用户修正源文件；
5. 源文件只用作输入，绝不作为 OA 的正式白名单附件。

首期不自动识别 SKU 是否真实存在；业务员对来源数据准确性负责。

### 5.4 计算和 OA 口径

- 优惠券名称按受控规则生成：`满{门槛}减{面额}`。
- 面额必须小于门槛；金额均以元保存和计算。
- 预计费用、ROI 必须按业务 Owner 确认的常规满减模板公式计算；费用为 0、负数或非有限数时停止生成。
- 业务员必须在字段确认卡中确认 OA 的预估 GMV/费用采用“全渠道合计”还是“单渠道值”；首期默认推荐全渠道合计，但不会静默选择。
- 日期和时间统一按 `Asia/Shanghai` 解释；活动日期、可领时间、可用时间必须在确认卡中回显标准化结果。

## 6. 试点版状态机

试点版只维护当前版本，不建设独立的任务表或完整的双层状态机：

```text
Collecting
  → AwaitingInputConfirmation
  → AwaitingWhitelistMapping
  → Generating
  → AwaitingOutputConfirmation
  → HandingOffToOa
  → GeneratedConfirmed

Collecting / AwaitingInputConfirmation / AwaitingWhitelistMapping
  └─（缺字段、规则错误、文件错误）→ NeedsInput

Generating
  └─（临时生成失败）→ RetryableFailure
  └─（模板或数据错误）→ NeedsInput

任意可编辑状态
  └─（用户修改字段、源文件或映射）→ Collecting（revision +1）
```

| 状态 | 用户看到的内容 | 可执行操作 |
| --- | --- | --- |
| `Collecting` / `NeedsInput` | 字段清单和明确的待补项 | 补充字段、重新提取、上传源白名单 |
| `AwaitingInputConfirmation` | AI 提取后的标准化字段 | 确认字段或返回修改 |
| `AwaitingWhitelistMapping` | 来源 Sheet/列到 `SKUID` 的映射候选 | 确认一列或更换文件 |
| `Generating` | “正在生成，请稍候” | 等待；不允许重复点击生成 |
| `RetryableFailure` | 失败原因与安全重试按钮 | 生成失败时使用原输入重新生成；OA 提升失败时只重试冻结文件提升，不重复创建 OA 草稿 |
| `AwaitingOutputConfirmation` | 两份输出文件、行数、金额、ROI、警告摘要 | 下载查看并确认；确认后自动开始 OA 草稿提升 |
| `HandingOffToOa` | 正在重新下载、校验并提升两份冻结文件 | 等待；不接收新的源白名单或测算图片 |
| `GeneratedConfirmed` | 冻结文件版本、字段快照和已创建的系统 OA 草稿引用 | 按 OA 提示补充手工材料、人工确认或基于当前数据创建新版本 |

每个卡片回调至少携带并校验：草稿 owner、草稿 ID、当前 revision。旧卡片的 revision 与服务端不一致时，只提示用户打开最新卡片，不执行写入。

## 7. 试点版技术约束

### 7.1 现有项目的改造边界

当前项目已具备独立 Excel 试点流程、AI 结构化提取、受控工作簿生成和 Drive/Base 附件引用能力。本节保留的约束是：源白名单不能复用“收到文件即上传 OA 附件”的旧路径；它只可作为解析输入，标准产物必须在确认后生成、冻结并校验。

P1-1 必须新增一个独立的 **Excel 试点流程**；不得复用当前“收到文件即上传 OA 附件”的逻辑。当前逻辑会在文件分类前调用审批附件上传，不能用于源白名单：

```text
源白名单文件
→ 仅下载、解析、保存 source hash
→ 映射确认
→ 生成规范白名单

生成后的规范白名单
→ 用户确认两份输出
→ 从 Drive 下载并校验冻结 hash
→ 上传审批附件库并自动附加到系统 OA 草稿
```

首发使用显式 `draft-only` 阶段，而非依赖笼统的 `excel-pilot`/`production` 命名。环境变量缺失或相互矛盾时必须 fail closed；后续实现需以 launch stage、native-submit kill switch、服务端 allowlist 与批准 approval code 共同控制。

### 7.2 文件与生成约束

试点只做基础防错，不承诺生产级文件安全能力：

- 只接受 `.xlsx`；文件无法正常解析、超出试点大小/行数、没有候选 SKU 列时直接提示重新提供；
- 保留内置配券模板的 Sheet、表头、已有公式、样式和数据验证；
- 生成后至少再次验证：文件可打开、配券行数正确、渠道正确、`SKUID` 行数正确、公式列仍存在；
- 用户文本写入 Excel 时按纯文本写入，避免将活动名称或商品文本当作公式；
- 生成文件必须存放在试点可访问的临时产物位置，并返回可下载引用；技术实现开始前确认采用飞书文件能力还是其他内网临时存储。

### 7.3 试点运行约束

- 仅支持低并发；同一业务员同一时间只保留一个可编辑草稿；
- 单次解析与生成在当前请求链路中完成；超时或临时失败时保留输入，用户手动点击重试；
- 不建设通用持久队列、自动任务恢复、跨实例锁或批量任务；但 bridge 入口仍必须有持久收据/outbox、稳定事件 ID 与重放安全，原生 OA 创建另须原子业务幂等。
- Base 记录至少新增：当前 revision、源文件 hash、来源 Sheet/列、模板版本、生成文件 hash、生成时间、输出确认时间；
- 生成文件和源文件的保留期限按试点人工约定处理；不做自动清理策略。

## 8. 错误与边缘情况

首期只处理会直接导致错误 Excel 的情况：

| 场景 | 处理 |
| --- | --- |
| 文本缺必填字段、字段冲突、日期/金额/比例格式不正确 | `NeedsInput`，指出具体字段 |
| 选择折扣/PLUS/兑换/大促等非试点场景 | 阻断，提示当前仅支持常规满减券 |
| 面额大于或等于门槛、数量/次数不是正整数、费用或 ROI 无法计算 | 阻断，指出券档字段 |
| 用户选两个渠道但尝试写到同一行 | 系统自动拆成两行并在预览中展示 |
| 白名单不是 `.xlsx`、无法打开、过大、无 Sheet、无非空列 | 阻断，要求重新上传 |
| 不知道哪列是 SKU 或存在多个候选列 | 展示候选，等待用户确认 |
| 空 SKU、重复 SKU、一个单元格内有多个 SKU、前导零已丢失 | 阻断，列出样例行，要求源文件修正 |
| 模板文件缺失、模板版本变化、生成文件无法打开 | 停止生成，联系试点维护人 |
| AI 超时或提取失败 | 保留原消息和已确认字段，提示“重新提取”或手动补字段 |
| 生成失败 | 保留字段和映射，提供“重新生成”；不要求用户重新填写 |
| 用户在确认后修改任意字段/源文件/映射 | revision +1，旧文件标注过期，重新生成 |
| 旧卡片/重复点击 | revision 不一致时拒绝动作并引导打开最新卡片 |

错误卡无需展示大批量行级问题。若白名单错误过多，卡片展示数量和前几条样例，业务员修正源文件后重新上传。

## 9. 已纳入 P1-1 的 OA 自动填写边界

确认输出后，P1-1 只消费 `GeneratedConfirmed` 的文件和字段快照：

1. 将活动名称、背景、业务模式、活动点位、平台承担比例、日期、渠道、GMV、费用和超扣点等字段写入既有**系统 OA 草稿**；
2. `draft-only` 阶段只保存生成物的冻结引用、bytes、SHA-256 和 Base 展示副本；当前实现中若存在审批附件库上传，应在进入受控试点前改为仅由最终 native-submit 门禁后的即时上传，源白名单始终不得上传；
3. 展示“Excel 汇总 ↔ OA 字段”的核对卡；
4. 寄卖/pop 必须由业务员上传满减测算图片，随后由业务员二次确认；
5. 当前 P1-1 的 `GeneratedConfirmed` 只证明系统 OA 草稿和冻结产物已就绪；原生 OA 仅在 rollout 的 canary/allowlist Gate 通过后，才能由当前 owner 的最终确认触发，并须服务端 readback 核对；

申请人文本不映射到 OA 联系人控件，始终以最终业务员的 `open_id` 为准；审批附件上传权限、系统草稿与原生 OA 字段绑定在上线前完成联调。

## 10. P1-3：使用说明插入

P1-3 在生成的配券表与白名单中分别增加 `系统生成说明` Sheet。首期说明包含：草稿号、模板版本、生成时间、字段口径、用户需人工核对的项目和试点维护人。历史文件的说明不回写。

## 11. 验收标准

### 11.1 P1-1

1. 试点业务员在 Bot 单聊中收到常规满减券字段清单，并能用一条消息完成大部分填写。
2. 缺字段、冲突或歧义时，Bot 只追问具体字段，不自动猜业务值。
3. 对非试点券类型，Bot 明确拒绝，不生成错误模板。
4. 用户上传包含额外列的源白名单 Excel 后，可选择一个 Sheet 和一个 SKU 列，生成标准 `SKUID` 白名单。
5. 源白名单不会走现有“直接上传 OA 附件”链路。
6. 一个渠道生成一行；两个渠道生成两行，OA/模板渠道文案按固定映射输出。
7. 生成的常规满减券表和白名单可在 Excel/WPS 中打开，配券表保留模板既有表头、公式和格式。
8. 预览卡显示模板版本、券档、渠道、配券行数、白名单行数、GMV、费用和 ROI；业务员确认后，系统保存 `GeneratedConfirmed` 的两份冻结产物引用、hash 与自动填充字段的系统 OA 草稿。审批附件提升仅在 native-submit Gate 通过后进行。
9. 寄卖/pop 系统草稿仍需要业务员提供满减测算图片；正式 OA 仅在 rollout Gate 通过后由当前 owner 的最终确认创建并回读。
10. AI 失败、文件解析失败或生成失败时，输入不会丢失，业务员可以修正或重试。

### 11.2 试点前置条件

1. 业务 Owner 提供并确认常规满减券模板版本、首期字段含义、费用/ROI公式和舍入方式。
2. 试点阶段使用仓库中的 `商品明细白名单-自动填报演练.xlsx` 作为标准 SKU 白名单结构：一个 Sheet、一列 `SKUID`；正式业务模板发布后再以新版本替换。
3. 技术侧验证选定 Excel 库能够复制当前常规满减模板，保留公式、样式和数据验证，并生成可打开的文件。
4. 技术侧确认生成文件的 Drive 存储/下载方式、文件 hash 回验、资源权限以及显式 `draft-only` 阶段不会把**源白名单**上传到 OA 附件库或创建原生 OA；approval attachment upload/native instance 权限与即时提升仅在原生 OA canary Gate 前以隔离环境验证。
5. 使用脱敏样本完成：正常满减、双渠道、缺字段、列映射、重复 SKU、前导零、生成失败、重新生成和旧卡片点击的试点测试。

### A.4 已确认的首期口径与仍待确认事项

**已确认的试点口径：**

1. **预计费用公式沿用当前模板。** 即 `总申请数量 × 面额 × 预计使用率 × 平台承担比例`；预计领用率在首期仍采集并写入 R 列，但不参与 V 列费用计算。
2. **标准白名单先使用演练模板结构。** 使用 `商品明细白名单-自动填报演练.xlsx` 的“一个 Sheet、一列 `SKUID`”结构作为内网试点标准；它只适用于试点，正式业务模板发布后必须版本化替换。
3. **优惠券类型固定为东券。** 首期不开放京券选择。
4. **限品类型固定为限SKU。** 首期白名单仅支持 SKU。
5. **领券用户风控固定为“0级以下用户可领”。**
6. **平台承担比例每次由业务员填写。** Bot 只做格式校验，不为京东或拍拍猜默认值。
7. **OA 活动点位每次必须由业务员明确确认。** 优惠比例仅用于 Excel 中的券档展示，不能直接代替 OA 活动点位。

**仍需在试点前确认或通过人工填写处理：**

1. **推广字段的枚举。** 模板说明给出文字候选，但实际数据验证范围没有稳定覆盖示例行，因此不能把 Excel 下拉本身当作唯一规则来源。首期由用户填写/确认 AC、AD 字段。
2. **时间展示格式。** 模板示例使用 `12.7 0:00-12.8 23:59`，Bot 使用标准 ISO 风格输入；试点实现需确定写入 Excel 时采用的展示格式。
3. **总申请数量容量关系。** `总申请数量` 与 `单次到账张数 × 每日领取次数 × 可领天数` 的关系暂只做提示，不作为首期硬阻断；业务员在确认卡中核对。
4. **OA 汇总口径。** 双渠道时，OA 的 GMV/费用取全渠道合计还是单渠道值，仍必须由业务员在 P1-2 确认。

### A.5 P1-1 最小校验规则

```text
1. 模板：必须是已登记的常规满减券版本。
2. 券档：首期只允许一个券档；渠道为 JD、PAIPAI 或二者。
3. 金额：限额 > 面额 > 0；GMV > 0；费用计算结果 > 0。
4. 数量：总申请数量、单次到账张数、每日领取次数均为正整数；单次到账张数 ≤ 总申请数量。
5. 比例：预计领用率、预计使用率必须为 `(0, 1]` 的小数；平台承担比例允许为 `[0, 1]` 的小数。输入百分号时统一转换；若比例导致预计费用为 0，则停止生成。
6. 时间：活动日期、可领时间、可用时间均可解析；统一按 Asia/Shanghai 回显。
7. 渠道：一行一个 canonical 渠道；双渠道生成两行。
8. 白名单：只接受一个来源 Sheet 和一列 SKU；非空、单值、文本格式、无重复；否则要求修正源文件。
9. 回填字段：活动 ID、批次 ID、putKey、PC/M 链接始终为空。
10. 输出：两份生成文件均可打开，且配券行/公式/白名单行数与 `generationInput` 一致。
```
