## 1. 目标与不可变原则

目标是降低优惠券提单的重复录入成本，同时不替代现有 OA 的审批决定、审批路由或业务最终核对。

1. 未确认工作保存为系统业务草稿；飞书没有可 API 写入的客户端 OA 草稿。
2. 原生审批实例创建就是提交。系统绝不自动、静默或基于旧卡片创建 OA。
3. 只有当前草稿 owner 在当前 revision 的明确确认，且服务端阶段、allowlist、审批定义、材料、幂等和授权门禁均通过时，才可能由服务端创建实例并回读。
4. 服务端不设置节点审批人、抄送人或路由；AI 不得补造业务事实或越过确定性校验。
5. `OA优惠券审批` 的手工原生页面导航始终与程序化创建分开；人工提交不代表系统 native-submit 已开放。

## 2. 三路线合同

| 口令/路线 | 目的 | Draft-only | Native-submit 阶段 |
| --- | --- | --- | --- |
| `OA优惠券审批` | 返回既有原生 OA 发起入口 | 不写草稿/附件/实例 | 保持仅导航；用户手工提交是原生 OA 自己的行为 |
| `OA优惠券填报` | 收集结构化字段及材料，形成系统草稿 | 可校验、预览、修改系统草稿；禁止原生实例创建 | 仅 allowlist 用户在当前 revision 最终确认后可创建并回读 |
| `优惠券Excel试点` | 根据受限规则生成券表和白名单并交接草稿 | 冻结产物/哈希/引用，绝不自动创建 OA | 只由后续最终确认路径即时提升批准的产物；本流程不直接提交 |
| `/OA优惠券提报` | 单用户 P0 三源候选识别、第二轮确认与标准附件生成 | 默认关闭；第 5 步确认创建 OA 测试稿后直达合并后的「第 5 步：核对后确认发送」草稿卡（含放弃出口，全程仅此一次人工确认）；提交在 kill switch 处被明确拒绝；可放弃/取消本次交接草稿（[ADR-0013](../../../adr/0013-p0-bridge-coupon-oa-draft-action-passthrough.md)，该可继续范围随 P0 测试窗口结束失效） | 不授权 native-submit；真实创建仍需 R3 canary Gate |
| `/clear` | 结束当前用户所有未完成的 P0 三源提报并释放重新发起入口 | 把任务标记为 `Canceled`，并级联关闭本次试点交接、仍处可取消状态的 OA 草稿（其他路线草稿与 Submitting 之后状态不受影响）；不删除审计记录或文件 | 不调用 native-submit，也不影响其他用户或其他优惠券路线 |

## 3. 分阶段范围

| 阶段 | 允许能力 | 明确禁止 |
| --- | --- | --- |
| P0 导航 | 原生 OA 链接卡 | 代填、附件写入、草稿、实例创建、审批 |
| Draft-only 内网试点 | 系统草稿、受控文件解析/生成、hash、预览、人工补件 | `POST /approval/v4/instances`、自动/静默提交、扩大至未批准用户 |
| Native-submit canary | 对严格 allowlist 的一至两位用户，在值守窗口内创建/回读一次原生 OA | 批量、无监控、越过 revision/owner、未知结果盲目重试 |
| 严格 allowlist 试点 | 已通过 canary 的小范围同类能力 | 面向全员或生产 SLA/HA 承诺 |
| 生产 | 另行技术/合规/架构决策 | 将试点通过自动解释为生产批准 |

## 4. 服务端原生提交门禁

以下条件必须同时为真；卡片展示不能代替这些检查：

- launch stage 明确允许、global kill switch 打开、用户位于服务端 allowlist；
- 目标是批准的原生 `approval_code`，定义 hash 与确认时快照一致；
- 操作者是草稿 owner、action 属于当前 revision、确认仍有效；
- 必填字段、附件、产物 hash 与审批文件引用完整；
- 已原子占用持久 business idempotency key；
- 上一次提交不存在未对账的 `Submitting`、`SubmissionUnknown` 或 `CreatedNeedsReview` 状态。

任何条件不满足，服务端只返回安全的阻断/恢复提示，不调用创建实例 API。

## 5. 原生提交与异常状态

- `Submitted`：实例已创建且要求的 readback 比对通过。
- `CreatedNeedsReview`：已确认存在实例，但回读失败或字段存在差异；自动化停止，转 OA/运行 Owner 对账。
- `SubmissionUnknown`：创建请求结果无法证明；禁止创建第二笔，必须按 submission key/实例查询/审计证据对账。
- `Failed`：仅在确认没有创建原生实例时使用。

服务端保留确认人、时间、revision、schema、审批定义 hash、submission key、实例 code/link、readback 与差异证据。审批状态的后续同步与人工撤回/驳回由流程 Owner 明确负责。

## 6. 试点验收与非目标

试点验收以 rollout 的 R/Gate 为准，至少包括：fail-closed 配置、managed bridge 鉴权与去重、草稿/附件 E2E、Drive/Base/审批权限、重放/重启/故障测试、kill switch 和回滚演练。完成草稿阶段不自动授权原生 OA canary。

本版本不承诺生产数据库、队列、HA、跨区域恢复、全量审批生命周期、病毒/深度文件扫描、通用 AI 数据治理或全员开放。上述能力需另行实施和决策。

## 7. P0 三源 AI 候选识别合同

P0 三源一次提报只允许一种**券模板类型**，当前只支持常规满减券。同一常规满减模板中的多行满减金额属于同一提报的多个券档，不得误判为多种优惠券。源表格当前只接受 `.xlsx`；`.xls`、`.csv`、损坏、加密或空工作簿必须返回明确中文提示，不得错误进入测算图片处理。上传阶段只收集和确定性检查材料，不调用 DeepSeek，也不逐文件发送状态卡。当前 owner 在收集卡点击“材料已上传完毕，开始统一识别”后，服务端才冻结当前 revision 并由默认关闭的 DeepSeek worker 一次性识别该 revision 的全部来源候选。启用 AI-primary 时，DeepSeek 直接理解工作簿布局并优先提出模板、券档、标准字段和 SKU 区域候选；服务端必须核验来源 hash、坐标、类型和业务规则。AI 某一候选分区无效时只丢弃该分区；规则只对缺失或无效的职责分区降级，不得向有效 AI 优惠券集合追加规则行，也不得覆盖 owner 输入。AI 不是事实源，不得决定附件生成、权限、审批或 OA 路由。

材料角色与标识维度必须分层判断。角色仅为配券表、白名单、黑名单；标识维度判定集封闭为 SKU 或商家 ID，无第三种。无表头单列数字名单由 DeepSeek 做意图判定，判定依据为数值位数与格式模式、Sheet 名、文件名标注、活动上下文；文件名是低权重线索，不得单独决定判定。AI 判定与依据只作为系统推测候选展示，不改写任何单元格值。无表头来源或识别维度非 SKU 的名单，无论 AI 判定结果如何，一律由 owner 在第二轮卡从「商家 ID / SKU」中二选一显式确认，不要求填写确认依据——封闭枚举中的选择本身就是人的显式决定，确认记录保留 detectedDimension 与 confirmedAs 及来源 hash 构成完整审计链。owner 可把系统判定推翻为另一侧（含把商家 ID 按 SKU 使用）。系统始终重新读取原单元格并逐条校验，不允许 DeepSeek 改写任何名单值。名单确认为商家 ID 时生成忠实产物：表头为 `商家id`、文件名前缀「商家ID白名单/黑名单」、独立模板 id，配券表「限品类型」列写「限商家ID」；AI 越集返回或判定失败时按降级语义走人工二选一，不阻断不伪造。一个 Sheet 同时存在唯一 SKU 列和 SPU 列时只采用 SKU 列；白黑名单确认维度不一致时硬阻断。已有白名单后上传第三份用途不明名单时不得自动覆盖，只询问一次“替换白名单”或“作为黑名单”。单文件超过 10 MB 时停止解析和 AI，保留本 revision 的其他材料并发送转人工提报提示。

全部来源识别终态后，系统只发送一张汇总第二轮卡。第二轮必须由当前 owner 在当前 revision 一次确认：系统识别的券模板、缺失或低置信度字段、活动点位、名单异常，以及未上传黑名单时的“本次无黑名单”声明；白黑名单重叠仍须在确定性解析后单独决定。卡片只显示中文业务问题和摘要，不显示 Sheet、列号、单元格坐标、内部字段 key 或“映射”术语。已登记的白名单多 Sheet 按 Sheet 名自动对应全部券档，不要求从多个券档中只选一个。第二轮同时提供中文结构化字段和可编辑的“语音或文字补充说明”；业务员可使用系统输入法完成语音转写，检查文字后让 DeepSeek 只提取候选并回填，仍须由 owner 修改、确认后才进入生成。第二轮自由文本字段设服务端长度上限：活动名称 100 字符、活动背景 500 字符、领取规则 500 字符、超扣原因 200 字符；超限取值不入确认值、不做静默截断，按统一「输入校验」中文提示回横幅，由业务员精简后重填。卡片预填在源值超过 800 字符时整体丢弃并提示人工填写，不得以截断值冒充确认值。

每个 revision 只允许一张活动第二轮卡；相同上下文原位更新，材料或识别上下文变化后旧卡提交必须被拒绝。同一 `task/revision/action/context` 的确认动作使用耐久语义键串行化，重复 callback 只恢复“处理中”或既有结果，不重复冻结、上传或发卡。外部结果不明时进入待对账状态并停止自动重放。

只有第二轮 blocker 全部解除后，确定性模板引擎才按照已登记模板生成一份包含全部已确认券档的常规满减配券表、一份保留已登记多 Sheet 券档结构的白名单，以及可选的同结构黑名单。活动名称和活动背景由 DeepSeek 按版本化运行时文案合同提出可编辑候选：活动名称采用“日期 + 品类 + ID类型 + 优惠券申请”模板，日期只保留月日、不带年份也不重复“优惠券申请”后缀，品类和 ID类型 从配券表文件名、Sheet 名或优惠券名称/限品类型等列值中推理且必须可回溯，推理不出的组件省略，不得使用渠道名（如京东商城）或“正常活动”“测试活动”等占位语；活动背景采用“本期申请……，本期配置 N 档优惠券：全部券档；配合已证实活动主题或业务说明”的结构。背景必须覆盖全部券档，且不得编造预算、GMV、ROI、渠道、审批理由或超扣事实。只写月日而没有年份时，系统可按当前时间和默认关闭的公共活动日历提出“系统推测”候选，但 owner 必须在第二轮确认；公开促销主题同样只是软证据。候选不得冒充源事实。源文件、补充说明原文和 AI 响应均不得作为 OA 附件。当前终点是唯一的「第 5 步：核对后确认发送」草稿卡（含「放弃本次提交」出口）：第二轮确认后自动生成并交接 OA 测试稿，直达该卡，全程仅一次人工确认（链路：上传→解析→补充字段→草稿卡→确认即发送），但在 native-submit Gate 开启前，提交动作会被服务端 kill switch 明确拒绝，草稿保持已确认状态可放弃或等待 Gate；原生 OA kill switch 在本路线必须保持关闭。

若 P0 三源提报因材料、识别、卡片或运行时错误无法继续，用户只能看到稳定错误码对应的中文修复提示；TypeError、ExcelJS、飞书 SDK、Drive/Base 原始错误、堆栈和响应体不得进入卡片。兼容 schema 的旧 Base 草稿必须先规范化缺省数组和选择对象再进入卡片、名单或 callback；未知 schema fail closed。当前 owner 可发送精确 `/clear`。服务端必须幂等地把该 owner 的活动三源任务标记为 `Canceled`，保留 Base/Drive 审计证据，并允许重新发送 `/OA优惠券提报`；旧来源和旧产物不得自动带入新任务。没有活动任务时 `/clear` 仍返回成功状态。未启用或未配置存储的旧 OA/Excel 路线不得仅因冲突查询而阻断三源任务启动。

## 8. v1.6 变更（2026-10-16，基于 9 用例真发重放证据）

以下行为变更由 2026-10-16 桌面真实用例（case1-9）全链路重放取证驱动，方案详情见 `proposals/three-source/coupon-three-source-replay-findings-solution-v2.md` 与「模版缺项提醒设计 v1」：

1. **第二轮表单枚举字段一律选择项**：领取规则、是否允许转赠、推广途径、公开推广渠道等封闭枚举字段的补充/修正入口由自由文本改为下拉选择（选项=系统标准枚举原文），杜绝手打抄错导致的往返打回。默认值按 Owner 决定落为服务端行为：未选择时按卡片占位文案声明的默认值提交（领取规则默认「活动期间每天可领一次」、是否允许转赠默认「不允许」），默认值仅为可改预选，不改写表内原值；表内合法值始终优先。
2. **公开推广渠道条件必填**：生效推广途径=公开自动推广时该字段必填（公开自动推广、单品页购物车、领券中心、公开券池为可选项）；非公开推广时不渲染该字段。服务端在推进 revision 前预检镜像同一规则，失败留在原卡可改。
3. **恢复卡可达性**：确认失败后的表单恢复卡若与"待修正区"字段重复渲染同一组件名，会被飞书整卡拒收（ErrCode 11310）——两区互斥，同一字段一张卡只渲染一次；恢复卡投递失败不再静默，降级发送纯文字报错（含失败原因与重发口令指引）并留结构化日志。全部卡片形态增加"组件名全卡唯一"测试门禁。
4. **多文件角色队列推进**：一次提报中连续上传多份用途不明材料时，角色确认按接收顺序逐份推进（确认一份、自动问下一份），不再出现队列悬空死滞。
5. **测算明细图 v2**：生成规则改为像素预算内单张渲染全部行列（超出才按行分页），并内置 Noto Sans SC 字体（fontconfig 隔离注册），渲染结果不依赖运行环境系统字体，消除 Linux/Preview 环境中文豆腐块与"27 列拆 5 张、每页重复表头"的问题。

**不改变**：枚举系统标准本身（不做方言归一，按标准词填写由源头模板词表治理）；draft-only、附件 Gate、原生 OA kill switch、事件与控制面边界全部维持。

## 9. v1.7 变更（2026-10-21，新商真实提报 bug-fix 驱动）

1. **活动名称模板（bug-fix-5）**：AI 只推理品类/ID类型组件（必须逐字回溯于配券表文件名、Sheet 名或优惠券名称/限品类型列值），活动名称由服务端按「日期 + 品类 + ID类型 + 优惠券申请」确定性拼装；日期仅保留月日、不带年份，不重复「优惠券申请」后缀，渠道名（如京东商城）不得进入名称。已同步第 7 节上文。
2. **标识维度封闭集与二选一确认（bug-fix-3，ADR-0015）**：无表头单列数字名单由 DeepSeek 按 SKU/商家 ID 封闭集判定并展示依据；无表头或非 SKU 识别结果一律 owner「商家 ID / SKU」二选一确认（含 AI 判 SKU 时）；确认商家 ID 后生成忠实产物（表头 `商家id`、前缀「商家ID白名单/黑名单」、独立模板 id）且配券表「限品类型」写「限商家ID」。
3. **删除确认依据必填（bug-fix-4）**：第二轮卡不再出现「确认依据（至少 2 个字）」必填输入框及其提交校验、生成放行条件；确认审计链由 detectedDimension + confirmedAs + 来源 hash 构成。
4. **同批修复（bug-fix-1/2，实施细节见实施基线 v1.15）**：OA 创建后回读的金额比对按「分」归一化（小数精度差异不再误报需复核）；提交结果卡改为「创建成功（绿）+ 核对提示次级块」；双击「开始统一识别」不再重复发「AI 识别中」卡。
