## 1. 背景与目标

业务员当前需要重复完成三件容易出错的工作：整理配券规则、把不规范的商品名单改成标准附件、再将同一批数据填写到 OA。P1 的目标不是让模型自行决定优惠券业务规则，而是建立一个可审计的**受控数据链路**：

```text
业务员对话输入 + 源白名单 Excel
  → 受控字段提取与缺项追问
  → 确定性业务校验 + 白名单映射确认
  → 内置模板生成配券表/白名单
  → 人工确认冻结
  → 自动预填并核对 OA 草稿
  → 原生 OA 二次确认、提交与回读
```

最终效果：业务员只需提供活动、券规则和手头已有的白名单数据；系统生成符合规范的 Excel，并以同一份冻结数据自动填写和核对 OA 相关字段。审批人、审批流和最终提交权限仍完全属于飞书原生 OA。

## 2. P1 交付顺序与范围

| 顺序           | 交付项                                              | P1 目标                                                        | 首期范围                                                             |
| -------------- | --------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| **P1-1** | **配券表与白名单 Excel 自动生成、映射与校对** | 从受控数据生成两份可下载、可审计、待确认的 OA 附件             | `配券信息表-常规满减券.xlsx` + 一份业务 Owner 确认的标准白名单模板 |
| **P1-2** | OA 草稿自动填写与校对                               | 将 P1-1 冻结的 canonical 数据填入 OA 草稿，并显示字段/附件差异 | 已确认的“优惠券申请”路径                                           |
| **P1-3** | 使用说明插入                                        | 在生成文件中插入版本化、可追溯的使用说明                       | 每份生成 Excel 的独立说明 Sheet                                      |

### 2.1 P1-1 首期支持范围

1. 券活动类型固定为**限品类券（平台券）**；用户范围固定为**常规优惠券**；优惠方式固定为**满减券**。
2. 系统仅基于内置、版本化的“常规满减券”模板生成配券信息表；业务员不上传配券模板，也不能修改内置模板。
3. 业务员可上传其已有的 `.xlsx` 白名单源文件；源文件允许与标准模板不同，但必须在映射确认后生成新的标准白名单文件。
4. 支持一次对话输入多个券档和多个渠道；每个“券档 × 用券渠道”生成一行，且一行只能有一个渠道。
5. 生成前、确认前、上传 OA 前均必须进行人工确认；P1-1 不创建 OA、不自动审批、不自动撤回。

### 2.2 明确不做

- 不将 PLUS、兑换券、折扣券、大促神券、店铺券自动降级为常规满减券；遇到这些组合必须提示“当前模板暂不支持”。
- 不从满减测算图片、活动背景或不完整自然语言中猜测金额、券规则、商品范围或审批结论。
- 不伪造活动 ID、批次 ID、`putKey`、PC/M 领券链接等由配券人后续回填的信息。
- 不覆盖用户源文件、内置模板中的公式、固定标签、数据验证或样式。
- 不因为 AI 的抽取结果而绕过金额、日期、公式、模板、OA 权限或审批校验。

## 3. 核心原则

1. **AI 只负责理解，规则代码负责裁决。** AI API 用于字段提取、别名识别、缺项追问与白名单列候选识别；schema、枚举、公式、日期、模板选择、跨表关系和权限均由确定性代码校验。
2. **无确认不生成，无冻结不上传。** 业务员确认前，系统不生成正式附件、不上传审批附件、不创建 OA。
3. **一份 canonical 数据，多份一致产物。** 配券表、白名单、OA 草稿和预览必须来自同一个冻结修订，不能各自单独编辑后再拼接。
4. **Fail-closed。** 规则不完整、模板变化、白名单映射不唯一、公式异常或数据口径不一致时，阻断生成或提交，不用默认值猜测。
5. **源文件只读、产物可追溯。** 每次生成新建文件和修订，保存源文件、映射、模板版本、输入快照、校验报告和 SHA-256。
6. **保留飞书原生审批路径。** 不发送节点审批人/抄送人覆盖参数；以业务员本人身份发起，原流程决定审批人与条件路由。

## 4. P1-1 用户交互与确认门禁

### 4.1 引导式自然语言采集

1. 业务员发送 `OA优惠券填报`；Bot 先展示“常规满减券智能生成”说明和一段可复制的字段清单。
2. 字段清单按“活动/OA 信息”“常规满减券规则”“白名单文件”分组，明确日期、金额、百分比、渠道和单行规则，并提供 `字段：值` 示例。
3. 业务员可用一条自然语言、字段清单或两者混合的消息尽量填全；多个券档可按 `券档 1`、`券档 2` 分段输入。
4. AI API 将消息转成受 schema 约束的候选结构，同时返回每个候选值的来源文本、未识别文本、歧义和缺失项。
5. 服务端执行字段和业务校验。仅当字段缺失、冲突、单位不明或候选不唯一时，Bot 追问**具体字段**；不得重新让业务员填写已确认的完整信息。
6. 字段齐全后，Bot 展示“提取结果确认卡”：字段、标准化值、转换说明、未决项以及对配券表/OA 的影响。业务员确认后才进入白名单映射。

### 4.2 白名单源文件映射

1. 业务员上传手头已有的白名单 `.xlsx`。系统只读取源文件，不会改写或直接作为 OA 附件上传。
2. 系统解析 Sheet、表头、候选 ID 列、样例值、行数、空值、重复值和不可识别值。
3. 系统展示“源 Sheet/列/样例/行数 → 规范白名单 Sheet/列/ID 维度”的映射卡。
4. 当候选列、ID 维度或目标券档无法唯一确定时，必须由业务员选择；系统不得仅因列位置或模糊列名而静默映射。
5. 业务员确认映射后，系统执行白名单校验并生成新的规范白名单文件；原始文件继续保留为源材料。

### 4.3 生成、预览与冻结

1. 系统从未改动的内置模板复制并生成：
   - `配券信息表_{活动名称}_{草稿号}_v{n}.xlsx`
   - `商品明细白名单_{活动名称}_{草稿号}_v{n}.xlsx`
2. 预览卡必须显示：模板版本、券档数、渠道数、生成行数、预估 GMV/费用/ROI、白名单映射、各 Sheet 行数、重复统计、警告与阻断项。
3. 业务员确认的对象是“输入修订 + 白名单映射 + 两份输出文件 + 校验报告”的组合；确认后状态为 `GeneratedConfirmed`，输入和产物不可再静默修改。
4. 用户修改对话字段、重新上传源白名单或重新选择映射后，原修订失效并生成新修订；旧产物只读保留。

## 5. Canonical 生成数据模型

系统在 Base 草稿之外维护版本化的 `coupon-excel-generation-v1` canonical 输入。Excel 单元格不是业务事实来源；生成器和后续 OA 映射都以该输入为准。

| 分组       | 首期字段                                                                                                                                                       | 规则                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 活动/OA 级 | 业务模式、申请人、活动名称、活动背景、活动起止日期、OA 配置渠道、预估 GMV、预估费用、是否超扣点及原因                                                          | 与 OA schema 统一口径；条件必填按业务模式执行              |
| 模板选择   | 活动类型、用户范围、优惠方式、模板 ID/版本                                                                                                                     | 首期分别锁定为限品类平台券、常规用户、满减券；不匹配即阻断 |
| 券档级     | 券档标识、用券渠道、可领时间、可用时间、总申请数量、单次到账数量、每日领取次数、满减门槛、面额、预计使用率、平台承担比例、预计引入 GMV，以及模板要求的配置字段 | 一个券档与一个渠道生成一行；多渠道必须拆行                 |
| 系统派生   | 优惠券名称、优惠比例、预计费用、ROI、活动时长、按渠道/全渠道汇总                                                                                               | 服务端按模板版本规则计算，与 Excel 公式核对                |
| 白名单源   | 源文件引用/SHA-256、源 Sheet、源列、候选 ID 维度、原始行统计、映射配置                                                                                         | 源文件永不改写；映射必须经业务员确认                       |
| 白名单输出 | 标准 Sheet、标准列、已规范化 ID、行数、重复统计、未映射值                                                                                                      | 输出结构以业务 Owner 确认的标准模板为准                    |
| 配券后回填 | 活动 ID、批次 ID、`putKey`、PC/M 领券链接                                                                                                                    | OA 发起阶段留空，系统和 AI 均不得填充                      |

### 5.1 首期字段门槛

以下事项在业务 Owner 给出正式口径前属于**阻断条件**，而不是由 AI 推断：

- 标准白名单首期支持的 ID 维度（SKU、SPU 或商家 ID）、目标 Sheet 名、列头和最大行数；
- 同券档和跨券档重复 ID 的处理方式；
- 模板中尚未明确的枚举、默认值与组合限制；
- 满减预计费用是否纳入预计领用率、百分比与金额的精度/舍入规则、ROI 的容差；
- 工作日提前提单规则、节假日来源及其他需要业务数据源的限制。

## 6. 内置模板与生成契约

### 6.1 模板注册表

每个内置模板须维护以下元数据：

| 字段                                           | 说明                                                             |
| ---------------------------------------------- | ---------------------------------------------------------------- |
| `templateId` / `version` / `fingerprint` | 稳定模板身份、版本和 SHA-256/结构指纹                            |
| 业务 Owner 与生效日期                          | 变更责任人和启用范围                                             |
| 适用条件                                       | 活动类型、用户范围、优惠方式、业务模式和渠道约束                 |
| 工作表与数据区                                 | Sheet 名、表头行、数据起止行、最大可写行数                       |
| 列映射                                         | canonical 字段到列的唯一映射、字段格式、是否必填                 |
| 保护规则                                       | 固定标签、公式列、回填留空列、合并单元格、数据验证与样式保护策略 |
| 输出规则                                       | 文件名、公式重算策略、生成版本和兼容策略                         |

首期以 `docs/oa-ticket-reimbursement-materials/reference/templates/配券信息表-常规满减券.xlsx` 为候选来源；上线前必须由业务 Owner 固化实际版本与 fingerprint。

### 6.2 工作簿不变量

- 从内置模板副本生成新文件，绝不修改模板或源白名单。
- 保留工作表名、表头、格式、合并单元格、数据验证和受控公式。
- 仅写入注册表指定的数据区；模板演示行必须删除或明确排除，不能作为可提交券批次。
- 固定标签、公式和配券后回填列不可由业务员或 AI 写入；活动 ID、批次 ID、`putKey`、PC/M 链接保持空白。
- 服务端同时计算名称、优惠比例、预计费用和 ROI；输出前验证没有 `NaN`、`Infinity`、除零、负数、超精度、旧公式缓存或非预期空值。
- 模板版本或结构指纹与冻结修订不一致时，必须重新生成并确认。

## 7. P1-1 校验、边缘情况与反馈

### 7.1 错误分级

| 级别                 | 含义                                    | 系统行为                             |
| -------------------- | --------------------------------------- | ------------------------------------ |
| **硬阻断**     | 生成结果可能错误、不可提交或不可审计    | 不生成正式文件；只返回问题清单       |
| **需人工确认** | 有多个合理映射/口径，系统不能替业务决策 | 展示候选和影响，待用户选择后继续     |
| **警告可继续** | 不影响已确认的结构与公式，但需知情      | 在预览和审计中保留，用户确认后可生成 |

所有可定位问题都必须返回：文件名、Sheet、行、列、原始值、违反的规则和可执行的修复建议；不得只提示“校验失败”。

### 7.2 必须覆盖的边缘情况

| 分类           | 典型场景                                                                                                 | 默认级别                                         |
| -------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 对话提取       | 同字段相互矛盾、漏填、单位/百分比不明、日期表达不完整、多个券档边界不清、未识别文本                      | 硬阻断或需人工确认                               |
| 输入安全       | 以聊天/单元格内容伪造系统指令、超长输入、公式注入                                                        | 硬阻断；将源内容视为不可信数据而非指令           |
| 券规则         | 非首期模板组合、单行多渠道、面额不小于门槛、数量/次数非正或非整数、精度错误、可领晚于可用、ROI 除零      | 硬阻断                                           |
| 时间与管控     | 活动日期越界、未满足提前工作日、需要大促窗口/商品主数据但数据源不可用                                    | 硬阻断；已确认例外走人工凭据                     |
| 源白名单文件   | 非`.xlsx`、扩展名与内容不符、损坏/加密/宏/外部链接/压缩炸弹、空文件、超限文件                          | 硬阻断                                           |

| 模板与生成     | 模板缺失/指纹变化、固定标签/公式被破坏、超过格式化行数、文件无法打开、旧产物确认                         | 硬阻断                                           |
| 并发与外部服务 | 同草稿并发生成/确认、重复事件、Base/飞书上传/发卡失败、权限变化                                          | 使用 revision 与幂等键；失败必须可见、可安全重试 |

## 8. 修订、状态与审计

### 8.1 状态机设计原则

P1 使用**两层状态机**，并把“用户业务进度”与“后台任务执行结果”分离：

1. **草稿生命周期状态机**：决定用户看到什么、可以执行什么操作、哪一份数据可被后续 OA 使用；
2. **修订任务状态机**：记录 AI 提取、源表解析、Excel 生成、未来附件上传等异步任务的执行与重试。

`缺字段`、`缺白名单`、`存在警告`、`解析失败`均不是草稿的终态。它们分别以 `blockingIssues[]`、`missingFieldKeys[]`、`whitelistStatus` 和任务状态表达，避免“既缺日期又未上传白名单”无法归类的状态爆炸。

### 8.2 草稿生命周期状态机

```text
ActiveCollecting
  ├─（字段完整，待业务确认）→ AwaitingInputConfirmation
  ├─（源表已接收，待映射确认）→ AwaitingMappingConfirmation
  └─（用户取消）→ Cancelled

AwaitingInputConfirmation
  ├─（确认输入 + 白名单未准备）→ ActiveCollecting
  ├─（确认输入 + 映射已确认）→ GenerationInProgress
  └─（修改任意输入）→ ActiveCollecting

AwaitingMappingConfirmation
  ├─（确认映射 + 输入已确认）→ GenerationInProgress
  ├─（确认映射 + 输入尚未确认）→ AwaitingInputConfirmation
  └─（修改源文件/映射）→ ActiveCollecting 或 AwaitingMappingConfirmation

GenerationInProgress
  ├─（生成任务成功且二次验证通过）→ AwaitingOutputConfirmation
  ├─（输入修订被替代）→ Superseded
  └─（可重试/阻断失败）→ ActiveCollecting

AwaitingOutputConfirmation
  ├─（确认输出）→ GeneratedConfirmed
  ├─（返回修改）→ ActiveCollecting
  └─（输出引用/模板已过期）→ Superseded

GeneratedConfirmed
  ├─（P1-2：创建 OA 预填快照）→ OaDraftPreparing
  ├─（任何业务输入、源文件、映射、模板规则变化）→ Superseded
  └─（用户取消，且尚无 OA 外部副作用）→ Cancelled

OaDraftPreparing → AwaitingOaConfirmation → Submitting
Submitting
  ├─（创建并回读一致）→ Submitted
  ├─（创建结果不确定或回读不一致）→ SubmissionNeedsReview
  └─（确认未创建且可安全重试）→ AwaitingOaConfirmation

Superseded / Cancelled / Submitted / SubmissionNeedsReview 为只读状态；
需要继续业务时从最后一份可编辑输入复制出新的 revision，而不是回写历史版本。
```

| 生命周期状态                                      | 用户可执行操作                            | 禁止的操作                           | 必须满足的进入条件                                  |
| ------------------------------------------------- | ----------------------------------------- | ------------------------------------ | --------------------------------------------------- |
| `ActiveCollecting`                              | 补字段、上传/替换源白名单、重新提取、取消 | 生成、上传 OA、提交 OA               | 草稿 owner 身份有效；当前 revision 可编辑           |
| `AwaitingInputConfirmation`                     | 核对提取值、确认、返回修改                | 生成/上传/提交                       | 无硬阻断字段；候选值已完成确定性校验                |
| `AwaitingMappingConfirmation`                   | 选择源 Sheet/列/ID 维度并确认、返回修改   | 生成/上传/提交                       | 源白名单可安全解析；映射候选已生成                  |
| `GenerationInProgress`                          | 查看进度、取消后续使用、等待结果          | 修改当前 revision、重复生成、提交    | 输入与映射均已确认；生成任务已获得唯一幂等键        |
| `AwaitingOutputConfirmation`                    | 下载预览、确认输出、返回修改              | 修改输出文件后继续使用、上传/提交    | 两份输出均通过二次工作簿验证；无硬阻断问题          |
| `GeneratedConfirmed`                            | 查看冻结产物、进入 P1-2、取消             | 修改冻结输入/文件、替换附件          | 输入、映射、模板、输出 hash、校验报告和确认人已冻结 |
| `OaDraftPreparing` / `AwaitingOaConfirmation` | 查看 OA 预填差异、确认或返回修改          | 改写已冻结 Excel                     | P1-2 已使用同一`generationRevision` 生成 OA 快照  |
| `Submitting`                                    | 查看实时状态                              | 再次点击提交、编辑或上传不同版本文件 | 二次 OA 确认、定义 hash 与附件 hash 均有效          |
| `SubmissionNeedsReview`                         | 打开 OA、查看差异、按飞书原生流程处理     | 自动重提/自动撤回                    | 已发生或无法排除外部 OA 副作用                      |

**状态约束：**

- `Cancelled` 仅表示取消系统侧草稿或未上传的产物；一旦 P1-2 已创建 OA，系统不自动撤回，必须转 `SubmissionNeedsReview` 并由业务员在飞书原生页面处理。
- `Superseded` 不是失败：它表示旧 revision 被新的输入、源文件、映射、模板 fingerprint 或规则版本安全替代。它不可恢复为 `GeneratedConfirmed`。
- `ActiveCollecting` 可以同时拥有 `missingFieldKeys` 和 `whitelistStatus = notUploaded`；UI 应将两类待办同时展示。
- `AwaitingOutputConfirmation` 中的文件只能下载查看。若用户本地修改后想使用，必须作为新的源输入重新校验和生成，不能将手改文件重新挂回当前 revision。

### 8.3 修订与异步任务状态机

每个草稿至少包含 `inputRevision` 和 `generationRevision`：

- `inputRevision`：业务字段、源白名单文件和映射配置发生可见变化时递增；
- `generationRevision`：基于某一冻结 `inputRevision + templateFingerprint + generatorRuleVersion` 产生的不可变输出版本；
- 同一 `inputRevision` 可以因模板/规则变更失效，但不能修改其历史快照；新输出必须产生新的 `generationRevision`。

每个 revision 的任务独立维护状态，草稿生命周期状态只消费其已确认结果：

```text
AI 提取任务：      queued → running → succeeded
                              ├→ retryable_failed
                              ├→ blocked
                              └→ superseded

源表解析/映射任务： queued → running → needs_user_mapping → confirmed
                              ├→ retryable_failed
                              ├→ blocked
                              └→ superseded

Excel 生成任务：    queued → running → verifying → succeeded
                              ├→ retryable_failed
                              ├→ blocked
                              └→ superseded

未来附件上传任务：  queued → uploading → uploaded_and_readback_verified
                              ├→ retryable_failed
                              └→ uncertain_external_effect
```

| 任务状态                      | 含义与恢复策略                                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------- |
| `queued`                    | 已保存执行计划但未开始；可由调度器恢复，不可视为生成成功                                       |
| `running` / `uploading`   | 正在执行；记录开始时间、attempt、worker/correlation ID。超时后须先回读外部结果再决定重试       |
| `succeeded` / `confirmed` | 已通过该任务的输出校验；尚不等于用户确认或 OA 已提交                                           |
| `needs_user_mapping`        | 文件可解析但候选不唯一或需选择目标结构；等待映射卡回调                                         |
| `retryable_failed`          | 限流、网络、临时存储、AI 服务超时等未产生或已确认无外部副作用的失败；可按同一幂等键重试        |
| `blocked`                   | 违反输入/模板/安全/业务规则；必须修改数据或配置，不能盲目重试                                  |
| `uncertain_external_effect` | 例如附件上传响应超时，无法确认是否已成功；禁止直接再次上传，必须按 hash/幂等键查询或回读后处理 |
| `superseded`                | 任务对应的 revision 已被替代；即使后台稍后完成，也不得将输出写回当前草稿                       |

### 8.4 事件、守卫条件与副作用表

| 事件                                                         | 合法来源状态                                         | 守卫条件                                                           | 状态变化                                                    | 副作用                                    |
| ------------------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------- | ----------------------------------------- |
| `message_received`                                         | `ActiveCollecting`                                 | 事件去重通过、sender 为 owner                                      | 保持或更新`ActiveCollecting`                              | 保存原文，排队 AI 提取；不生成文件        |
| `extraction_validated`                                     | `ActiveCollecting`                                 | AI 输出通过 schema；确定性校验无硬阻断                             | `AwaitingInputConfirmation` 或继续 `ActiveCollecting`   | 发送字段确认/缺项卡                       |
| `whitelist_uploaded`                                       | `ActiveCollecting` / `AwaitingInputConfirmation` | 文件安全校验通过、owner 一致                                       | 保持现有生命周期状态                                        | 保存源文件 hash，排队解析；不上传审批附件 |
| `mapping_ready`                                            | 可编辑状态                                           | 解析任务成功                                                       | `AwaitingMappingConfirmation`                             | 发送映射预览卡                            |
| `input_confirmed`                                          | `AwaitingInputConfirmation`                        | nonce、owner、inputRevision 一致                                   | 等待映射或`GenerationInProgress`                          | 冻结输入快照；必要时排队生成              |
| `mapping_confirmed`                                        | `AwaitingMappingConfirmation`                      | nonce、owner、源文件 hash、候选配置一致                            | 等待输入或`GenerationInProgress`                          | 冻结映射；必要时排队生成                  |
| `generation_succeeded`                                     | `GenerationInProgress`                             | 任务 revision 等于当前 revision；两输出及二次校验成功              | `AwaitingOutputConfirmation`                              | 保存产物 hash/报告，发送预览卡            |
| `output_confirmed`                                         | `AwaitingOutputConfirmation`                       | nonce、owner、generationRevision、模板 fingerprint、输出 hash 一致 | `GeneratedConfirmed`                                      | 原子写入确认快照；不上传 OA               |
| `input_changed` / `source_changed` / `mapping_changed` | 所有可编辑或已确认状态                               | owner、版本检查通过                                                | 新 revision`ActiveCollecting`；旧 revision `Superseded` | 使旧卡片 nonce 和未完成任务失效           |
| `oa_prepare_requested`                                     | `GeneratedConfirmed`                               | P1-2 开启；generationRevision 仍完整                               | `OaDraftPreparing`                                        | 生成 OA 预填快照；不提交                  |
| `oa_submit_confirmed`                                      | `AwaitingOaConfirmation`                           | 二次确认、定义 hash、附件 hash、提交幂等键一致                     | `Submitting`                                              | 创建 OA；必须回读实例                     |
| `oa_readback_verified`                                     | `Submitting`                                       | 创建实例与确认快照一致                                             | `Submitted`                                               | 回发正式 OA 链接                          |
| `oa_result_uncertain` / `oa_diff_found`                  | `Submitting`                                       | 已创建或无法排除已创建                                             | `SubmissionNeedsReview`                                   | 回发差异和原生 OA 处理指引                |

任何事件的 `owner`、`expectedRevision`、`nonce`、`eventId` 或 `idempotencyKey` 不匹配时，服务端必须拒绝该事件并提示用户刷新最新卡片；不能尝试“帮用户合并”。

### 8.5 并发、重试、超时与恢复规则

1. **乐观锁**：草稿更新必须携带 `expectedRevision`。Base/存储返回版本不一致时，写入失败并要求客户端读取最新预览；不允许最后写入者覆盖先前确认。
2. **幂等键**：生成任务使用 `draftId:inputRevision:templateFingerprint:generatorRuleVersion`；审批提交继续使用确定性 `uuid`。同一键只能产生一个有效结果。
3. **失效写保护**：异步 worker 写结果前必须再次读取当前 revision。若任务输入已 `superseded`，仅记录任务审计，绝不更新当前草稿或发送“生成成功”卡。
4. **重试边界**：只对 `retryable_failed` 自动/人工重试；`blocked` 必须由业务修改；`uncertain_external_effect` 必须先通过 hash、外部查询或回读消除不确定性，禁止重复执行外部写入。
5. **租约与超时**：`running` 任务必须有租约/心跳和最大运行时间。租约过期时由恢复器先判断 worker 是否仍在执行、是否已有输出，再标记可重试或不确定；不能仅按时间直接启动第二个生成器。
6. **卡片更新顺序**：消息卡的 `update_multi` 仅用于视觉更新，不是状态真相。所有回调以服务端状态机为准；旧卡片、重复卡片、网络乱序到达均不能推进状态。
7. **取消边界**：任务未产生外部副作用时可标记取消/失效；已开始生成的本地文件可在回收策略中删除临时副本。OA 创建和附件上传进入不确定状态后不得假装已取消。

### 8.6 失败信息与恢复体验

每次失败或阻断必须同时保存机器可读错误码和用户可读恢复建议：

```text
errorCode: WHITELIST_AMBIGUOUS_ID_COLUMN
scope: sourceWhitelist
location: 商品名单.xlsx / Sheet1 / B 列
revision: 12
retryability: user_action_required
nextAction: 请选择“SKU 编号”或“SPU 编号”作为标准白名单来源列
```

Bot 卡片至少区分：

- **待补充**：缺哪些字段，用户可直接回复什么；
- **待确认**：有哪些候选映射/口径，选择会影响哪些输出；
- **可重试失败**：保留原输入，提供“安全重试”按钮；
- **需修改**：定位到文件/Sheet/行/列并说明规则；
- **需人工复核**：明确是否可能已上传附件或创建 OA，给出打开原生 OA 的入口；
- **已失效**：说明哪个新 revision 替代了当前卡片，并提供打开最新预览入口。

### 8.7 每个生成修订必须记录

- `generationRevision`、canonical 输入 JSON 与 schema 版本；
- 原始对话引用、源白名单文件引用与 SHA-256；
- 白名单映射配置、映射确认人/时间和未映射/重复统计；
- 模板 ID、版本、fingerprint 与生成器规则版本；
- 两个输出文件的名称、行数、SHA-256、文件引用和公式校验结果；
- 校验报告、警告、失败原因、生成/冻结时间及操作者；
- 以后续 OA 使用时，附加 OA 定义 hash、实例 code、附件 file code 和回读 diff。

相同输入修订的重试必须幂等；任一输入或映射变更必须创建新 revision。当前草稿保存会重置附件的实现风险不得被静默继承：未来任何影响生成的字段变更都必须明确让旧修订失效并告知用户重新生成。

## 9. P1-2：OA 草稿自动填写与校对

P1-2 只消费 `GeneratedConfirmed` 修订：

1. 将 canonical 活动级字段和受控汇总映射到 OA；ROI 继续由飞书公式控件计算，不写入公式值。
2. 显示“canonical 值 ↔ OA 控件值 ↔ 配券表汇总”的三方核对；OA 的 GMV/费用为按渠道还是全渠道合计不明确时，必须让业务员选择并记录口径。
3. 上传的附件只能是冻结修订生成的配券表和白名单，以及业务员提供的测算图片；不得误传源白名单。
4. 业务员确认后冻结审批定义 hash 与字段快照；提交前重读定义，定义变化时 fail-closed。
5. 以业务员 `open_id` 发起原生 OA，绝不覆盖审批/抄送节点；创建后回读逐字段比对。

真实审批定义读取、附件上传、实例创建和回读仅使用应用身份（tenant token）；本地草稿 Demo 继续禁止这些副作用。

## 10. P1-3：使用说明插入

P1-3 在两份生成 Excel 中分别创建/更新独立的 `系统生成说明` Sheet，不覆盖业务方已有说明页。说明至少包含：文件用途、草稿号、模板/规则版本、生成时间、字段口径、自动填充与人工核对项、常见错误、变更记录及维护人。历史产物保留生成当时对应的说明版本，不回写。

## 11. 技术边界、失败模型与非功能要求

本节规定 P1-1 的技术边界。它不是实现建议，而是上线前必须满足的行为契约；任何未满足项必须停止在“待补充/待确认”，不能生成可提交附件。

### 11.1 分层与事实源边界

```text
飞书消息/文件事件
  → 事件鉴权、去重、owner 校验
  → 对话会话状态（原始消息 + 已确认字段）
  → AI 字段提取候选
  → schema 验证与确定性规则引擎
  → canonical generation revision
  → Excel 模板生成/公式校验
  → 预览、人工确认、冻结
  → （P1-2）审批附件上传与 OA 创建
```

| 层                | 可以做什么                                               | 明确禁止什么                                                    |
| ----------------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| 原始对话/源文件层 | 保存经授权的原始输入、文件 hash、来源定位；供用户追溯    | 不直接作为 OA 字段、Excel 单元格或模型指令                      |
| AI 提取层         | 按固定 JSON schema 抽取候选字段、来源片段、缺项和歧义    | 不得决定业务规则、模板、公式结果、ID 真实性、审批结论或提交动作 |
| 规则层            | 校验/规范化输入，计算派生值，生成错误码和 canonical 数据 | 不得读取未经确认的模型猜测作为事实；不得把显示文本当数值计算    |
| 模板层            | 以已登记的模板和映射创建新工作簿                         | 不得按列号猜模板、覆盖固定/公式/回填列、改写源文件              |
| 草稿/审批层       | 管理 revision、确认快照、附件引用和原生 OA 生命周期      | 不得跨 owner 访问、绕过确认、以系统身份冒充用户提交             |

canonical revision 是唯一可被 P1-2 消费的事实源。任何“直接改 Excel 后上传”“直接从聊天原文填 OA”“把源白名单原样挂 OA”的路径均为禁止路径。

### 11.2 AI API 的严格边界

1. **调用触发**：只有业务员发送采集文本、补充字段或确认要求重新提取时才可调用 AI；文件上传本身不允许把整个工作簿无条件发送给模型。
2. **最小化数据**：用于白名单列识别时，默认只传 Sheet 名、表头、数据类型统计和脱敏样例；完整 ID 清单、文件二进制、审批 token、file code、其他人的草稿和业务密钥不得传给模型。
3. **结构化输出**：模型输出必须限定为版本化 JSON schema，字段包含 `value`、`sourceText`、`status`（`provided`/`missing`/`ambiguous`）和 `unparsedText`；服务端必须验证类型、未知字段和长度。无法通过 schema 验证的响应视为提取失败，不得降级为正则猜测后继续生成。
4. **提示注入隔离**：用户消息、Excel 单元格、文件名和 Sheet 名均是不可信数据。它们不能改变系统提示、工具权限、schema、模板版本或确认状态；模型不得拥有上传、写文件、发卡、发起 OA 等工具权限。
5. **歧义与低置信度**：模型未明确识别、一个值可映射多个字段、数值缺单位、日期缺年份、百分比含义不明、券档边界不清时，统一输出 `ambiguous` 并追问；不使用“最可能”的自动填充值。
6. **故障处理**：超时、限流、网络错误、服务拒绝、响应截断或 schema 不合法时，保存已确认字段和原始消息，回卡说明“本次未完成提取，可重试或补充字段”；不得丢失消息、重复扣减状态或进入生成队列。模型重试必须携带同一会话/消息幂等键，避免同一消息重复产生不同候选结果。
7. **供应商与数据合规**：正式环境须在应用配置中确定允许的 AI API、区域/留存策略、访问凭证和审计责任；未完成数据合规审批前，只能以脱敏 fixture 验证，不能将生产白名单数据用于模型联调。

### 11.3 对话会话、身份和回调安全

- 每个会话绑定 `ownerOpenId`、草稿 ID、当前 revision、会话过期时间和最后处理的消息 ID。跨会话引用旧卡片时必须检查 owner、状态、revision 和 nonce。
- 飞书事件必须校验验证 token/签名（按事件类型的官方方式），并按 `event_id`/`message_id` 去重。消息重复投递只返回已有进度，不得重复调用 AI、生成附件或上传 OA。
- 卡片回调必须校验操作者是草稿 owner 或经过显式授权的代办人；按钮中携带的 `draftRecordId`、模板 ID、映射列名等均不可信，服务端只以已存草稿和 revision 为准。
- 所有确认、重新生成、取消和未来的提交动作使用短期一次性 nonce；确认成功后 nonce 立即失效。旧预览卡、并发页面和重放回调不得修改新 revision。
- 对话输入超过单消息/会话上限时，系统应返回可继续填写的明确分段格式；不得截断后悄悄解释。会话超时只冻结进度，不删除草稿或源材料。

### 11.4 源 Excel 接收与 OOXML 安全边界

P1-1 仅接受标准 `.xlsx`，并在解析前完成下列检查：

| 检查项     | 要求                                                                                                 | 失败处理                                    |
| ---------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 文件类型   | 扩展名、MIME、ZIP/OOXML 文件签名和内容类型一致                                                       | 硬阻断，提示重新导出`.xlsx`               |
| 加密与宏   | 拒绝加密/密码保护工作簿、`xlsm`、VBA 二进制、DDE/外部数据连接和不受支持的嵌入对象                  | 硬阻断，不能尝试执行或转换                  |
| ZIP 安全   | 校验路径穿越、重复条目、解压后体积、压缩比、XML 深度/实体和条目数                                    | 硬阻断，记录安全错误码但不回显敏感文件内容  |
| 容量       | 上线前由业务/技术 Owner 配置单文件大小、Sheet 数、行/列数、非空单元格数和总解压体积的硬上限          | 超限即阻断，不部分读取后生成                |
| 工作簿结构 | 读取 workbook、Sheet、shared strings、styles、merged cells、hidden Sheet、relationships 和公式元数据 | 无法可靠解析即阻断；隐藏 Sheet 不能绕过审计 |
| 外部内容   | 禁止访问外部 URL、外部 workbook、宏、脚本和公式计算副作用                                            | 只把它们视为不支持内容，不执行              |

容量阈值必须配置化并写入模板/运行配置，不得由 AI 或用户消息覆盖。解析器应在受资源限制的后台任务中运行；同步机器人回调只负责接收、排队和返回进度，避免大文件阻塞后续飞书事件。

### 11.5 白名单映射与数据保真边界

1. **读取方式**：所有候选 ID 均按文本读取和存储，禁止 `Number()`、科学计数法格式化或自动去前导零。
2. **不可恢复的前导零**：若源 Excel 已把 `00123` 保存为数值 `123`，系统不能猜测原始零；必须标为待修正并让业务员提供准确文本值。
3. **列候选**：列名别名、数据样例和格式可用于提出候选，但不构成自动确认。多个候选列、多个非空 Sheet、多个可能 ID 维度或“SKU/SPU/商家 ID”混列时，必须显示映射卡。
4. **单元格语义**：标准输出一格只允许一个 ID。包含逗号、顿号、换行、空格拼接或公式生成多个 ID 的单元格必须拆分前人工确认，不能静默按分隔符拆开。
5. **公式与缓存**：源白名单 ID 列不接受公式作为最终值；没有可靠缓存值、依赖外部工作簿或结果类型不为文本的公式均阻断。公式结果不得用来绕过 ID 格式校验。
6. **重复与冲突**：同一源文件的重复、跨 Sheet 重复、跨券档重复、白名单与未来黑名单冲突都要独立统计。没有业务 Owner 已发布的处置策略前，重复不自动删除、不自动合并，按阻断或人工确认处理。
7. **主数据边界**：P1-1 可校验结构、类型、格式和已配置的正则/长度规则，但不能凭空证明 SKU/SPU/商家 ID 在生产系统存在、可售或属于某类目。若要做真实性、质检优品和商家承担比例校验，必须接入已授权且可审计的商品主数据接口；接口不可用时按规则阻断或明确降级为人工确认，不能由 AI 判断。

### 11.6 模板、公式与文件生成边界

- 模板识别只允许通过注册表的 `templateId + version + fingerprint`，不允许根据文件名、Sheet 名或列号模糊匹配。模板 fingerprint 变化后，冻结 revision 失效，必须重新验证映射和公式。
- 不同模板可能有不同 header 行、说明行、合并单元格、预格式化区和公式坐标；生成器只能使用该模板版本的 manifest，不能假设“第 1 行就是表头”。
- 数据行超过模板预格式化区时，只有 manifest 明确规定了行扩展、样式复制、数据验证/公式复制和最大行数时才可扩展；否则硬阻断，不能生成裸数据行。
- 对业务文本写入单元格时，必须防止 spreadsheet formula injection：用户文本以 `=`, `+`, `-`, `@` 开头时按纯文本转义，并保持单元格类型为文本；绝不把用户输入拼为公式。
- 名称、预计费用、ROI 等公式字段由服务端 canonical 计算和模板公式双重验证。生成库若不能执行 Excel 公式，必须：保留受控公式、记录计算依赖、以服务端结果校验、标记工作簿下次打开强制重算（如技术栈支持），并重新解析验证生成文件结构。不能仅依赖本地 Excel 打开后“看起来正确”。
- 公式使用的金额单位、百分比（`5`、`5%`、`0.05`）、小数精度、银行家/四舍五入策略和比较容差必须在模板规则版本中明确。计算结果为零、负数、非有限数、缺少依赖或超过精度时硬阻断。
- 生成后执行二次验证：新工作簿可打开；预期 Sheet/列/公式/数据验证存在；固定标签和回填留空列未被改写；数据行与 canonical 行一一对应；输出 SHA-256 生成成功。二进制文件不要求跨次完全相同（时间戳等可能变化），但相同 revision 的业务内容、模板 fingerprint、行数据和公式快照必须相同。

### 11.7 Revision、一致性、并发与副作用控制

| 场景                            | 必须行为                                                                                      |
| ------------------------------- | --------------------------------------------------------------------------------------------- |
| 同一消息/同一生成请求重复到达   | 以消息/请求幂等键返回同一会话结果或同一 revision，不新建多份附件                              |
| 两个设备同时修改草稿            | 使用 revision/ETag 乐观锁；后写入者发现版本冲突后重新读取并明确提示，不能覆盖先前确认         |
| 生成进行时源输入改变            | 旧任务只能标记为`Superseded`，不得把旧产物写入新 revision                                   |
| 生成成功但文件引用/草稿写入失败 | 使用可恢复的阶段性状态与事务式补偿；不把“文件可能存在”标为“已确认生成”                    |
| 生成失败后重试                  | 同 canonical 输入、模板 fingerprint 和映射配置使用确定性 idempotency key；只重试未完成步骤    |
| 用户确认后再修改                | 先显式创建新 revision，旧确认不可被自动带入；P1-2 只可消费当前`GeneratedConfirmed` revision |
| 未来附件上传超时                | 不假定请求失败即未上传；按内容 hash/幂等键查询或回读后再决定重试，避免重复附件/重复 OA        |

草稿存储、文件存储和飞书审批 API 之间没有可依赖的全局事务。实现必须以状态机和可回读外部引用组成 saga；每个外部副作用都先写计划状态、执行、再回读确认，失败时留下可诊断且可重试的状态，而不是吞掉异常。

### 11.8 运行、可观测性与审计要求

- 每次事件、AI 提取、解析、映射、生成、确认、上传和 OA 创建使用同一 `correlationId`，并记录草稿/revision/模板版本/owner 的最小必要关联。
- 日志中不得输出 token、Authorization、完整白名单、完整自然语言内容、文件二进制、file code 或未经脱敏的金额明细。错误日志只记录安全错误码和必要定位；完整审计数据进入受权限保护的草稿/审计存储。
- 必须有可查询的状态：排队、解析中、等待补充、等待映射确认、生成中、待输出确认、已冻结、失败/可重试。Bot 在耗时任务中应发送进度卡，而非长时间静默。
- 需采集最小运行指标：事件去重数、AI 提取失败率、字段追问轮数、映射人工确认率、生成成功率、文件解析/生成耗时、模板 fingerprint 不匹配、上传重试与 OA 回读差异数。指标不得包含业务明细。
- 产物、源文件 hash、映射、确认记录和输出文件的保留/清理期限必须在上线前由数据 Owner 确定。到期清理只能删除未被审批审计要求保留的副本，并记录清理事件。

### 11.9 测试与发布边界

1. Excel 生成必须使用脱敏的真实结构模板和 golden fixture 做结构性测试，至少比较 Sheet、表头、合并区域、数据验证、公式、数据行、回填空列和业务计算；不能只断言文件存在。
2. 安全测试覆盖损坏 ZIP、压缩炸弹、外部链接、宏/加密文件、公式注入、超限文件、恶意 Sheet/列名和 prompt injection 文本。
3. 状态机测试覆盖重复事件、并发确认、旧卡片回调、revision 冲突、生成中修改、外部 API 超时后回读和失败重试。
4. AI 测试用固定脱敏输入集评估提取、缺项追问、歧义拒绝、schema 不合法和拒绝响应；模型输出变化不能改变确定性校验的通过/阻断结论。
5. 本地 fixture-only 环境不允许调用审批创建、附件上传或生产 AI/商品数据接口；正式环境先以脱敏样本灰度，模板/规则/权限任一变化均需要重新跑冒烟验证。

### 11.10 权限、安全与数据边界

- 机器人不授予或绕过 OA 权限；无权限用户由飞书拒绝。
- AI API 调用仅传递完成字段提取所需的最小化数据；不得将 token、file code 或不必要的完整商品明细写入日志、卡片或 Base。
- 上传文件必须经过类型、大小、压缩内容和安全校验；禁止执行宏、公式、外部链接或文件中的指令。
- 所有人工确认、映射选择、模板变更、生成和上传操作均绑定 owner、revision、时间和 hash；只有草稿 owner 或被正式授权的代办人可确认。

## 12. 验收标准

### 12.1 P1-1 Excel 自动生成

1. Bot 能先发送完整字段清单；业务员以引导式自然语言输入后，系统只追问缺失、冲突或歧义字段，不能擅自补值。
2. AI 抽取结果必须通过 schema 与规则校验，并由业务员确认；确认前没有正式 Excel、OA 附件上传、OA 创建或审批副作用。
3. 首期仅命中常规满减券模板；PLUS、兑换、折扣和大促组合会被明确阻断，不会生成错误模板。
4. 一券档一渠道一行；双渠道生成两行；输出不含演示行、多渠道行或伪造的配券后回填字段。
5. 上传非标准白名单 Excel 后，系统能展示源列到标准模板列的映射；多个候选列/维度必须由业务员确认，且源文件不被改写。
6. 标准白名单保留 ID 文本格式和前导零；每格一个 ID，按已确认的维度/重复策略处理空值、混维、非法值和超限值。
7. 生成工作簿可打开，并保留模板工作表、格式、合并单元格、数据验证、固定标签和受控公式；服务端计算与公式核验一致，零费用等异常不会产生非法结果。
8. 预览展示模板版本、行数、GMV/费用/ROI、映射、白名单统计、警告和阻断原因；确认后产物审计字段完整。
9. 同 revision 的重复事件或重试不产生不同文件或重复副作用；输入/映射变化生成新 revision，旧版本可追溯。
10. 本地 fixture-only 测试不调用审批创建/附件接口；生产灰度中上传失败、权限失败、消息失败均有可见反馈和安全重试路径。

### 12.2 P1-2 / P1-3 后续验收

- OA 创建前的确认快照、审批定义 hash 和附件 hash 一致；回读无差异才标记成功。
- 使用说明 Sheet 与输出模板、规则版本和草稿 revision 一致，且历史文件说明不被回写。
- `pnpm test`、`pnpm typecheck:server` 和 `pnpm lint` 全部通过；真实 OA E2E 仅在应用身份权限发布后以脱敏样本执行。

## 13. 首期上线门槛

1. 业务 Owner 确认常规满减券模板的正式版本、Owner、fingerprint、字段字典、公式和舍入规则。
2. 业务 Owner 确认标准白名单模板、首期 ID 维度、列头/Sheet、行数上限、重复和跨券档重复处理方式。
3. 流程 Owner 确认 OA 与 Excel 汇总口径、附件上传边界和应用身份权限。
4. 使用脱敏 fixture 完成常规满减、双渠道、缺项追问、抽取歧义、白名单映射、前导零、重复/混维、模板变化、公式除零、修订幂等和可见错误的测试矩阵。

> 后续模板扩展必须逐模板登记版本、字段映射、固定标签、公式、测试 fixture 和验收案例；不得通过一个“通用 Excel 填写器”绕过模板差异。
