## 1. 背景与目标

P0 已上线"口令 → 原生 OA 入口卡"的导航能力，但业务员仍需在原生表单中手工录入全部字段并整理三类附件。P1 的目标是在机器人对话内完成**信息收集 → 系统草稿 → 人工确认 → 创建正式 OA → 回读核对**的完整闭环：

1. 业务员通过结构化表单卡片录入申请信息，系统保存为**自有业务草稿**（Base 表），可中断、可续传；
2. 业务员按文件名规则发送附件，系统下载、归类、校验并上传至飞书审批附件库；
3. 材料齐全后系统展示**预填确认卡**，业务员人工核对并点击确认；
4. 确认后系统重新读取正式审批定义（**定义哈希 fail-closed**），以业务员本人身份（`open_id`）创建**原生** OA 实例；
5. 创建后系统**回读**正式实例，逐字段比对提交值与实际值，一致才标记成功。

P1 严格保留飞书原生审批路径：不传节点审批人/抄送人覆盖参数，审批人、抄送、条件路由完全由正式审批定义和发起人身份决定，与业务员手工提交进入完全相同的审批流。

## 2. 用户、前提与原则

| 项目 | 说明 |
| --- | --- |
| 目标用户 | 已获授权发起优惠券 OA 的业务员（寄卖/pop/严选） |
| 发起人字段 | 无论调用凭证类型如何，创建实例均传入业务员本人 `open_id`，单据发起人显示为业务员本人 |
| 本地调试身份 | **用户身份仅用于草稿 Demo / Base 数据验证**。审批 v4 的定义读取与附件上传接口均拒绝 `user_access_token`，因此不能用于真实 OA 自动填单联调 |
| 正式 OA API 调用身份 | **应用身份（tenant token）是必需项**：读取定义、上传审批附件、创建与回读实例均依赖应用身份；须先完成应用权限开通与版本发布 |
| 存储 | 系统业务草稿存于飞书 Base 专用表「优惠券提单草稿」（`tblq0cZ9cW2AmDTH`），不写入飞书审批草稿箱 |
| 权限边界 | 机器人不授予、不绕过 OA 表单权限；无权限用户在创建实例时由飞书拒绝 |
| 审批判断 | 全部由原生审批流承担；系统不做任何审批动作 |

**核心原则**

1. **人工确认门禁**：不确认不提交；确认卡与提交卡分离，提交卡使用红色危险按钮二次确认。
2. **Fail-closed**：确认时冻结定义哈希与字段快照；提交前重读定义，哈希不一致立即阻断并标记失败。
3. **公式不写**：`ROI` 为 `formula` 控件，由飞书计算，系统永不写入。
4. **幂等**：创建实例携带确定性 `uuid`，重试不会产生重复单据。
5. **不覆盖路由**：绝不发送 `node_approver_list` / `node_cc_list`。
6. **可审计**：附件记录文件名、字节数、SHA-256；草稿记录字段快照、校验结果、实例引用与失败原因。
7. **身份边界**：用户身份只用于本地草稿/数据校验 Demo，且 token 不落盘至项目、Base、Vercel 或日志；真实审批 v4 API 的附件上传、定义读取、实例创建和回读使用应用身份，不得以用户 token 代替。

## 4. 触发与交互流程

### 4.1 触发词

| 触发词 | 说明 |
| --- | --- |
| `OA优惠券填报` | 主触发词 |
| `优惠券提单草稿` | 别名 |

归一化规则：忽略全部空白字符；允许前导 `/`、`!`、`！`（可组合）。`OA优惠券审批`（P0 口令）不会误触发 P1 流程。

### 4.2 交互步骤

| 步骤 | 用户动作 | 系统行为 | 用户可见结果 |
| --- | --- | --- | --- |
| 1 | 发送触发词 | 下发「智能填报」表单卡（明确标注"本页面不会创建 OA"） | 蓝色卡片，状态"填写中" |
| 2 | 填写表单并点击「保存草稿并上传材料」 | 校验字段 → 写入 Base 草稿（状态 `Draft`） | "草稿 COA-xxxx 已保存"+ 待补材料清单 |
| 3 | 逐个发送附件（顺序不限） | 按 message_id 回读原始消息 → 下载 → 按文件名归类 → 上传审批附件库 → 记录 SHA-256 → 更新草稿 | 每份回复剩余缺失清单 |
| 4 | （材料齐全后自动） | 展示「预填确认」卡：活动名称、GMV、费用、预估 ROI、渠道 | 橙色卡片，状态"待确认" |
| 5 | 点击「确认进入提交页」 | 校验附件齐全 → 冻结定义哈希 + 字段快照（状态 `Confirmed`） | 「确认提交正式 OA」卡，红色危险按钮 |
| 6 | 点击「确认提交正式 OA」 | 重读定义核对哈希 → 编码表单 → 创建实例（状态 `Submitting`） | 飞书向原生审批人发送待办 |
| 7 | （自动） | 回读实例逐字段 diff | 绿色"已提交"卡（含单据链接）或红色"需复核"卡 |

### 4.3 附件归类规则

| 文件名包含 | 归类 | 格式要求 |
| --- | --- | --- |
| `测算` 或图片消息 | 满减测算图片 | 图片（寄卖/pop 必填） |
| `配券` | 配券信息表 | `.xlsx`（必填） |
| `白名单` | 商品明细白名单 | `.xlsx`（必填） |
| `黑名单` | 商品明细黑名单 | `.xlsx`（选填） |
| `增加` / `剔除` | 修改路径明细 | `.xlsx`（P2 UI） |

无法归类的附件直接报错并列出可用的文件名关键词；同角色重复发送以最新一份覆盖。

### 4.4 字段校验规则（申请路径）

- 业务模式：`严选` / `寄卖` / `pop` 三选一；
- 配置渠道：至少一项，仅允许 `京东渠道`、`严选APP及小程序`，以 `；` 分隔；
- 活动结束日期不得早于开始日期；
- 寄卖/pop 必须填写：是否超扣点、预估 GMV、预估费用、测算图片；超扣点为"是"时必填原因；
- 严选模式自动省略以上财务字段与测算图片。

## 5. 草稿状态机

```
Draft ──(附件齐全+确认)──▶ Confirmed ──(提交中)──▶ Submitting ──┬─(回读一致)──▶ Submitted
  │                                                              └─(哈希变化/diff失败)──▶ Failed
  └──(业务员放弃)──▶ Canceled
```

- `Draft`：可继续追加附件、可重新保存表单；
- `Confirmed`：字段快照与定义哈希冻结，不再接受字段变更；
- `Failed`：记录失败原因（定义变化 / 回读差异 / API 错误），**需业务员手动撤回已创建的单据**（如已产生）；
- 同一业务员同一时刻仅一条活跃草稿（`Draft`/`Confirmed`/`Submitting`）。

## 6. 数据模型（Base 表「优惠券提单草稿」）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| Draft ID | 文本 | `COA-` 前缀业务标识 |
| Owner Open ID | 文本 | 草稿归属人，操作鉴权依据 |
| Status | 单选 | Draft/Validated/Confirmed/Submitting/Submitted/Failed/Canceled |

| Fields JSON | 文本 | 字段快照 |
| Attachments JSON | 文本 | 附件清单（角色/文件名/file code/字节数/SHA-256） |
| Validation Issues JSON | 文本 | 提交时回读差异 |
| Confirmed At | 日期时间 | 确认时间 |
| Approval Instance Code | 文本 | 正式单据 instance_code |
| Approval Instance Link | 文本 | 正式单据链接 |

## 7. 技术架构

| 模块 | 职责 |
| --- | --- |
| `server/lib/feishu/coupon-oa/approval-schema.ts` | 唯一提交 schema：控件绑定、选项解析、表单编码、定义哈希、回读 diff |
| `server/lib/feishu/coupon-oa/approval-client.ts` | 读定义、创建实例、回读实例、回读消息原始体、下载消息资源、上传审批附件（v4） |
| `server/lib/feishu/coupon-oa/draft-store.ts` | Base 草稿 CRUD 与活跃草稿查询 |
| `server/lib/feishu/coupon-oa/draft-service.ts` | 表单解析、附件归类/校验/挂载 |
| `server/lib/feishu/coupon-oa/submit-service.ts` | 确认冻结、fail-closed 提交、回读核对、状态落库 |
| `server/lib/feishu/coupon-oa/cards.ts` | 表单卡/待补材料卡/预览卡/提交卡/结果卡 |
| `scripts/long-connection-bridge.mjs` | 本地长连接桥：转发 `message_id`、串行转发事件（防并发覆盖） |

**关键机制**

- 附件事件先经 `GET /im/v1/messages/:message_id` 回读原始消息体获取 `file_key`（桥接层预渲染内容不含 key）；
- 附件上传使用官方 v4 接口 `POST /open-apis/approval/v4/files/upload`；
- 创建实例 `form` 仅包含业务字段对应控件；`部门`/`申请人` 由发起人信息派生；
- 回读 diff 比较控件 id、type、value、currency、open_ids；公式与默认值控件不参与比对，避免误报。

## 8. 调试模式、权限与上线预检

> ⚠️ **2026-09-29 实测结论**：审批 v4 的 `GET /approval/v4/approvals/:code` 与 `POST /approval/v4/files/upload` 均返回 `user access token not support`。因此，不能以用户身份完成真实 OA 自动填单的端到端联调。

### 8.1 两种联调模式（不得混用）

| 模式 | 可做内容 | 不可做内容 | 是否需要应用发版 |
| --- | --- | --- | --- |
| **本地固定字段 → Base Demo（当前选择）** | 机器人表单交互、固定字段校验、Base 草稿创建/更新、Owner 隔离、Base 回读核对 | 接收/处理附件、调用审批 v4、上传审批附件、创建/回读真实 OA | 否 |
| **真实 OA E2E 联调 / 正式上线** | 从附件接收直到原生 OA 创建、回读核对的全链路 | 绕过人工确认、节点覆盖、自动审批 | 是 |

本地 Demo 的运行时由机器人事件和**应用身份（tenant token）**完成发卡与 Base 草稿写入；`lark-cli --as user` 仅可选地用于建表、只读核对或清理本人的测试数据。user token、refresh token 或授权码不得写入仓库、环境变量、Base、日志或 Vercel；用户身份不能替代审批 v4 所需的应用身份。

### 8.2 本地固定字段 → Base Demo 验收范围

1. 设置 `FEISHU_COUPON_OA_MODE=draft-demo` 后，发送 `！优惠券提单草稿` 展示明确标注“本地草稿测试”的表单卡；
2. 填表并保存后，应用 tenant token 在 Base 表创建草稿；同一 `Owner Open ID` 重复保存时更新既有活跃草稿，而不是创建重复记录；
3. `Draft ID`、`Owner Open ID`、`Status=Draft`、`Fields JSON` 与卡片输入和操作者逐字段一致；审批实例字段和附件字段为空；
4. 图片/文件消息、确认 callback 和正式提交 callback 均只回复“仅草稿”提示，且不得调用审批 v4、附件下载/上传或实例创建；
5. 本地 Demo 失败只记录草稿校验问题，不触碰审批实例。

#### 8.2.2 本地 Draft E2E 自动填表测试计划（当前优先级）

**测试目标**：在不创建正式 OA、也不部署 Vercel 的前提下，打通“业务员填写机器人表单 → 本地服务解析与校验 → 自动写入飞书 Base 草稿表 → 机器人回执”的完整闭环。验收的数据库是 Base 表「优惠券提单草稿」，不是飞书审批草稿箱。

**身份与调用边界**：

| 参与者/凭证 | 在本计划中的职责 | 不得承担的职责 |
| --- | --- | --- |
| 测试业务员 | 在飞书单聊中发送触发词、填写并提交卡片；其 `open_id` 写入 `Owner Open ID` | 不直接调用审批 v4 |
| `lark-cli event consume --as bot` | 通过本机长连接接收消息和卡片事件 | 不以用户身份写草稿 |
| 本地服务的应用身份（tenant token） | 发送机器人卡片、写入和读取 Base 草稿记录 | 不调用 `approval/v4/*`，不创建 OA |
| `lark-cli --as user` | 可选：建测试表、只读核对 Base 记录、清理本人的测试数据 | 不作为机器人事件链或正式 OA API 的替代品 |

**本地拓扑**：

```text
飞书测试业务员
  → 本机 lark-cli 长连接（--as bot）
  → scripts/long-connection-bridge.mjs
  → http://localhost:3000/api/feishu/process
  → 本地 Nitro 服务（pnpm dev）
  → 飞书 Base「优惠券提单草稿」
```

桥接必须设置 `FEISHU_PROCESS_URL=http://localhost:3000/api/feishu/process`；不得使用脚本默认的 Vercel Production 地址。这样被验证的是当前工作区代码，而不是已部署版本。

**前置条件**：

1. 本地 `.env.local` 配置 `FEISHU_COUPON_OA_MODE=draft-demo` 以及 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_BASE_APP_TOKEN`、`FEISHU_COUPON_DRAFT_TABLE_ID`；密钥不得提交、打印或写入 Base；
2. 通过 `zsh scripts/check-coupon-oa-local-draft-demo.sh` 预检；使用 `lark-cli` 长连接时必须保持 `FEISHU_VERIFICATION_TOKEN` 未设置，因为 bridge 不携带 HTTP webhook verification token；
3. 应用拥有向测试业务员发卡片及对目标 Base 表读写的权限；仅 `lark-cli --as user` 能写表不能证明应用身份也有写表权限；
4. 运行 `pnpm dev`，并在另一终端运行 `FEISHU_PROCESS_URL=http://localhost:3000/api/feishu/process pnpm dev:events`；
5. 使用脱敏的活动名称、金额、日期和渠道数据；本阶段不发送附件，也不点击进入正式提交的操作。

| DRAFT-E2E-03 | 按寄卖或 pop 模式填写 GMV、费用、超扣点原因等字段并保存 | 财务字段被正确解析和持久化；缺少必填字段或超扣点原因为空时拒绝保存且不新增错误记录 |
| DRAFT-E2E-04 | 输入非法渠道、结束日期早于开始日期、非正数金额等 | 机器人给出可理解的校验错误；Base 中不产生不合法草稿 |
| DRAFT-E2E-05 | 同一业务员重复保存草稿 | 遵守“同一业务员仅一条活跃草稿”的业务规则；记录创建/更新行为与实现一致且可审计 |
| DRAFT-E2E-06 | 使用另一测试业务员发起并保存 | 两人的 `Owner Open ID`、草稿记录和后续可见状态互不混淆 |
| DRAFT-E2E-07 | 在保存成功后检查本地服务与 bridge 日志 | 日志中不存在 `approval/v4`、审批附件上传、创建实例或回读实例调用；Base 中 `Approval Instance Code`、`Approval Instance Link` 均为空 |

**结束条件**：DRAFT-E2E-01 至 DRAFT-E2E-07 均通过，且每次执行均未创建任何正式 OA 实例，即可判定“固定字段自动填表单并成功写入数据库（Base）”初稿联调完成。附件命名/格式校验、预填预览、确认提交和 OA 回读继续留在应用身份权限发布后的独立 E2E 阶段。

> `draft-demo` 已实现为独立的 Base-only adapter：文件/图片事件和确认/提交 callback 会明确回复“仅草稿”提示，且不进入现有 Vercel 正式附件链路或任何审批 API。

### 8.5 真实 OA E2E 上线顺序

1. 开通 `approval:approval` 应用身份权限；
2. 创建应用版本并发布，必要时等待管理员审批；
3. 运行应用身份探针：附件上传成功返回 `file_code`、审批定义可以读取；
4. 部署 Vercel：`npx -y vercel@latest --prod --yes`；
5. 桥代码变更时重启桥：`zsh scripts/restart-feishu-bridge.sh`；
6. 使用脱敏样本执行一次全链路，停在预填确认卡；只有业务员明确点击第二次确认，才创建真实 OA。

## 9. 异常处理

| 场景 | 系统行为 | 用户可见结果 |
| --- | --- | --- |
| 未开草稿先发附件 | 不创建草稿 | 提示先发送触发词 |
| 附件无法归类 / 非 xlsx | 拒绝该附件，草稿不变 | 错误说明 + 可用关键词列表 |
| 确认时附件缺失 | 阻断确认 | 待补材料清单 |
| 提交时定义哈希变化 | **阻断提交**，草稿标记 `Failed` | 失败原因说明，需重新确认 |
| 创建成功但回读不一致 | 标记 `Failed` 并记录差异 | 红色"需复核"卡，业务员手动撤回 |
| 上传/创建 API 无权限 | 抛错并保留草稿状态 | 联系管理员按 §8.1 检查 |
| 飞书事件重复投递 | 幂等键去重 | 不重复回复 |

## 10. P1 验收标准

1. 触发词（含别名与前缀变体）打开表单卡，非精确文本不误触发；
2. 表单保存后 Base 出现对应草稿记录，字段与快照一致；
3. 三份附件任意顺序发送均能归类落库，重复发送以最新覆盖；每份均有 SHA-256 审计记录；
4. 材料齐全后展示预览卡；点击确认后 Base 状态为 `Confirmed` 且哈希冻结；
5. 提交后正式 OA 创建成功，发起人为业务员本人，审批节点与手工提交一致（无节点覆盖参数）；
6. 回读 diff 无差异，结果卡为绿色"已提交"并附单据链接；
7. 提交前人为修改审批定义（如增删控件）后提交，系统阻断并标记 `Failed`；
8. 全程不自动审批、不撤回、不绕过任何飞书权限校验；既有报销流程与 P0 入口不受影响；
9. `pnpm test`（47+ 用例）、`pnpm typecheck:server`、`pnpm lint` 全部通过。

## 11. 联调故障复盘（错误 → 根因 → 修复 → 预防）

| # | 现象 | 根因 | 修复 | 预防 |
| --- | --- | --- | --- | --- |
| 1 | 发附件无任何回复 | 桥未转发 `message_id`，服务端无法定位消息 | 桥转发 `message_id` | 事件契约变更须同步桥与测试 |
| 2 | "did not include its original body" | 飞书接口返回 `msg_type`，代码检查 `message_type`；且误用了返回预渲染文本的批量接口 | 改用单条消息接口并按 `msg_type` 解析 | 以真实响应样例（只读探针）核对字段名，不凭文档记忆编码 |
| 3 | "approval file upload failed: No permission" | 应用身份未开通审批权限，且权限开通后**未发版**不生效 | 开通 `approval:approval` + 发版；上传切换 v4 接口 | §8.5 应用身份探针前置；权限变更必发版写入 PRD |
| 4 | 用户身份调用审批 v4 返回 `user access token not support` | 飞书审批 v4 的定义读取与附件上传接口不支持 user token | 用户身份仅用于本地草稿 Demo；真实 OA E2E 使用应用身份 | §8.1 明确两种模式与不可混用边界 |
| 5 | 并发发送附件可能互相覆盖 | 桥并发转发事件 | 桥改为串行转发 | 写共享状态的入口串行化 |
| 6 | 终端多行命令被拆分执行 | `!` 内联命令含换行无续行符 | 提供 `scripts/*.sh` 单命令封装 | 运维命令一律脚本化 |

## 12. 已知限制与后续门槛

- 用户身份本地 Demo 仅覆盖草稿侧，无法调用审批 v4；真实附件上传和正式 OA 创建必须等待应用身份权限发布；
- 修改路径（关闭批次/增加/剔除）schema 与编码已就绪，但机器人 UI 未开放（P2）；
- 草稿表存储函数暂无独立单测（依赖集成验收）；
- 服务端无法自动撤回已创建单据；`Failed` 且已创建的单据需业务员手动撤回；
- P2 门槛：业务 Owner 确认配券 Excel 模板、字段口径与生成规则。
