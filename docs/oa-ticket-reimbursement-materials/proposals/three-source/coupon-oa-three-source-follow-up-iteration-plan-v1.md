## 1. 背景与目标

2026-10-09 的本地三源演练证明了“配券表 + 白名单”的映射、标准附件生成、活动文案候选和二轮补充对话能够在不连接飞书的条件下运行。但演练将“未配置券档策略”、业务模式、活动日期、超扣点、名单模板层数和测算图片都以同一种 blocker 处理，不能准确反映本业务的实际口径。

本计划将它们拆分为三类：

1. **信息提示**：需要展示，但不要求业务员补充，也不能被错误表述为模板或文件异常；
2. **当前阶段二次确认项**：允许有默认/候选值，但必须由业务员在第二轮确认；
3. **后续自动化候选**：只可由受认证服务端读取配置并产出候选，仍需保留来源、回退和人工确认。

本文件记录已确认的产品方向、实现顺序和验收口径。它不授权连接飞书、创建 OA 或改变当前已发布流程；相应 PRD、Skill、字段字典和服务端实现须在各阶段交付时同步修订。

## 3. 目标交互与数据口径

### 3.1 未配置券档策略：信息提示而非待补充字段

当配券表出现券档、但活动文案上下文没有该券档的型号/券额策略时：

- 在候选背景中完整列出配券表中的所有券档，不能静默遗漏；
- 将该券档标记为 `unconfigured_coupon_tier`，展示例如“满2000减20：本期未配置单独型号/券额策略”；
- 二轮对话将其放入“异常提示/说明”，**不**生成 `couponTierStrategies.2000-20` 的 `missingField`，也不因它把候选状态降为 `needs_confirmation`；
- 该提示是本期业务的正常信息，不得被描述为源文件、白名单或模板损坏；
- 只有券档无法映射到已登记模板、存在多个映射候选、或券档金额/公式本身无效时，才继续作为 blocker。

活动背景仍须区分来源：券档来自配券表；“未配置策略”来自业务上下文/规则；不得由 AI 补造型号策略。

### 3.2 业务模式：当前人工确认，后续身份映射候选

**当前阶段**：

- 不从 Excel 中的申请人显示名推断业务模式；
- 第二轮明确展示“业务模式”，要求业务员确认；
- 未确认时不得进入最终提交快照。

**后续阶段**：

- 后台维护以飞书最终确认人 **`open_id`** 为主键的映射，不以可变的显示姓名作为主键；
- 每条映射至少记录默认业务模式、启用状态、配置版本、维护人和更新时间；
- 系统读取到映射后仅写入 `identity_mapping_candidate`，在第二轮回显“默认值来自何处”，并允许业务员显式确认或覆盖；
- 无映射、失效映射、身份无法唯一解析或覆盖时，一律退回当前人工确认路径；覆盖需记录操作者和原因。

### 3.3 活动日期：当前人工识别，后续配券节奏表候选

**当前阶段**：

- 不将无年份的可领/可用时间直接当作 OA 活动日期；
- 第二轮提示业务员参照已维护的配券节奏表，手动填写并确认含年份的活动开始/结束日期；
- 记录该值为 `user_confirmed`，并继续校验结束日期不早于开始日期及派生时长一致。

**后续阶段**：

- 由受认证服务端读取业务方维护的飞书配券节奏表，配置入口为：<https://atrenew.feishu.cn/wiki/wikcnCAKN6wDm1gVmMHbVmGGiYg?from=from_copylink&sheet=YyUKlE>；本地脚本、Skill 和客户端不得直接调用该接口；
- 依据配置的业务时区和“当前日期命中的节奏行”生成 `schedule_table_candidate`，不得仅凭配券表月日文本猜测年份；
- 每个候选保存节奏表行标识、读取时间、表版本/更新时间、匹配规则和服务端审计 hash；
- 没有命中行、命中多行、权限/API 错误或数据不完整时，自动回退到当前人工确认，不可猜测；
- 首次接入前由业务 Owner 明确节奏表的列结构、时区、跨年规则、优先级和配置责任人。

### 3.4 是否超扣点：默认“否”但必须二次确认

- 草稿和二轮界面可预填 `否`，其状态必须是 `defaulted_pending_unified_confirmation`，而非源表事实或已确认值；
- 第二轮展示该默认值和提醒；业务员通过既有的最终统一确认一并确认，不新增单独确认控件；
- 最终确认前若将值改为“是”，`overDeductionReason` 为必填；保留“否”时原因保持空白；
- 审计中分别记录默认规则版本、最终值、统一确认人、确认时间和覆盖原因（如有）。

### 3.5 券档子集与模板结构

正式模板可登记为可支持券档的**超集**。本期实际配置为四个券档，而非模板支持的所有券档时：

- 配券表中的每一个实际券档必须仍能唯一映射到模板规则、白名单 Sheet 和生成规则；
- 未配置的正式券档只记录在 `unconfigured_tiers`，不生成“模板不匹配”错误；
- 若正式模板要求保留未使用 Sheet，则该 Sheet 保持空白并保留 template fingerprint；若业务发布了与本期四券档对应的模板版本，则记录该版本；
- 不得因“物理 Sheet/蓝图行数量”和“本期实际券档数量”不同而误报源表异常；
- 未登记券档、多个 Sheet 同时可匹配一个券档、或任何实际券档没有对应 Sheet 时，仍须阻断。

### 3.6 以已填充标准配券表生成截图

“具体满减测算图片”位置的后续替代附件改为从**已验证的标准配券信息表**生成，而不是从原始配券表或用户上传截图生成：

1. 先按已登记模板写入标准配券表，并完成 Excel round-trip、公式缓存和模板 fingerprint 校验；
2. 将该生成文件完整渲染为单页/完整内容截图；若不能完整渲染，拒绝生成该截图；
3. 截图记录 `sourceArtifactSha256`、模板 ID/版本、生成器规则版本、渲染范围、页数、像素尺寸和自身 SHA-256；
4. OA 预填快照同时列出标准配券表与这张截图，明确截图来自同一 revision 的标准表；
5. 源配券表保持只读，不作为截图来源或正式 OA 附件。

该截图只证明已填充模板的可视化内容；费用、GMV 与 ROI 的业务口径仍须由已发布公式和确认流程决定。

## 4. 实施分期

### W1：本地流程语义与产物修正

1. 将未配置券档策略从 blocker 改为非阻断信息提示，并更新二轮对话、候选状态和草稿文本；
2. 将“本期四券档 / 正式模板五券档”从 blocker 改为已配置券档子集说明，保留实际映射异常的阻断；
3. 为“是否超扣点”增加 `defaulted_pending_unified_confirmation = 否`，在二轮回显提醒并纳入最终统一确认；
4. 调整日期提示文案，明确当前需要业务员人工参照配券节奏表确认；
5. 生成并验证标准配券表后，再从该产物渲染截图；替换原始配券表截图的角色、命名和审计字段；
6. 更新本地草稿、映射报告、运行清单和测试断言，使信息提示、确认项和 blocker 可区分。

### 后续改进需求（不在本次修复范围）

业务员 `open_id` → 默认业务模式候选、以及受认证服务端读取飞书配券节奏表并生成日期候选，均已移入 [跨产品需求排期 Backlog](../../../requirements-backlog.md)。

在 Backlog 项的配置、权限、时区/跨年规则、Owner 和 feature flag 未冻结前：

- 业务模式继续由业务员人工确认；
- 活动日期继续由业务员参照配券节奏表人工确认；
- 本地脚本、Skill 和客户端不得访问真实飞书节奏表；
- 不得因这两项规划改变 OA 创建或提交能力。

## 7. 后续需冻结的配置

W2/W3 开始前，业务/流程 Owner 需明确：

1. 允许的业务模式枚举、`open_id` 映射责任人、更新/失效流程与覆盖权限；
2. 配券节奏表的字段、时区、跨年处理、当前日期匹配规则、多个活动命中时的优先级及访问权限；
3. 正式模板中的可选券档集合、未使用 Sheet 的保留规则和每个券档映射；
4. 已填充配券表截图在 OA 中对应的附件控件、展示要求和保留期限。

在这些配置冻结前，系统保留人工确认与 fail-closed 行为；不得以本计划或本地演练结果宣称已具备真实飞书读取或原生 OA 提交能力。

## 8. 当前实现基线与迁移边界

本计划不得被误读为当前 P1 Excel 试点已经具备这些能力。实施前应以现有行为为回归基线：

- `server/lib/feishu/coupon-oa/excel-pilot-schema.ts` 当前仍要求业务模式、含年份日期和是否超扣点由输入提供；
- `server/lib/feishu/coupon-oa/excel-pilot-cards.ts` 当前仅收集显式“是/否”，不能把审批编码阶段的“否”回退值当作业务员确认；
- `server/lib/feishu/coupon-oa/excel-pilot-service.ts` 与 `server/lib/excel-template-engine/index.ts` 已能生成填充后的 Excel 字节，但尚无已填充工作簿截图/预览产物；
- `server/lib/feishu/coupon-oa/approval-schema.ts` 的编码回退不能代替本计划要求的二轮确认审计；
- 当前没有配券节奏表 API/日历适配器。W3 必须新增隔离的服务端模块和 mock fixture，不能将访问逻辑放进 Bot 客户端、本地案例脚本或 Skill。

因此，W1 先在三源领域模型与本地演练中固化行为和回归用例；只有相应 PRD 获批、模板/审批定义/权限前置完成后，才将同一规则迁移至当前 P1 或后续受认证 OA 服务端路径。
