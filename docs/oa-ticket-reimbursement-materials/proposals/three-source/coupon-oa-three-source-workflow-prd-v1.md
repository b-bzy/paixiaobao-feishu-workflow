## 1. 背景

业务员现有的优惠券提单材料通常来自三个任意布局的 Excel：配券表、商品白名单、商品黑名单。业务员需要手工判断哪些字段进入 OA、哪些商品范围生效，并把同一事实重复填入标准表与 OA，容易产生口径不一致、漏传黑名单和白黑名单冲突遗漏。

本方案以“**配券表为字段第一来源、标准数据包为唯一事实源、业务员两次确认后才发起 OA**”为原则，形成一条三源提单流程。

## 2. 目标

业务员在飞书 Bot 中完成：

```text
发送 /OA优惠券提报
  → 上传原始配券表 + 原始白名单 + 原始黑名单（或明确无黑名单）
  → 确认字段映射、名单映射与冲突处置
  → 系统生成标准配券表、标准白名单、可选标准黑名单
  → 系统生成 OA 预填确认单与现有 OA 测试稿
  → 业务员在当前 revision 上沿用现有明确“发送”动作
  → 仅当既有服务端 Gate 允许时，系统创建并回读飞书原生 OA
```

成功标准：业务员不需要手工重复录入已能从配券表识别的内容；OA、标准附件和名单处理结果来自同一 revision；系统不会因黑名单遗漏、名单重叠或字段歧义而静默发起错误 OA。三源实现不重建既有 OA 测试稿、最终发送或原生提交逻辑。

### 2.1 P0 与本文完整合同的关系

当前本地 POC 仍限定单用户、常规满减券、SKU 和 OA 测试稿。严选不写入测算图片；寄卖/POP 优先使用 owner 确认的 PNG/JPEG 图片，缺图时从最终标准配券工作簿的显示值生成分页 PNG。该增量不提供 SPU/商家 ID，也不创建原生 OA。

本文后续的截图、补充/覆盖、三种 ID 维度、完整二次确认和原生 OA 描述，是业务确认后才进入的 P1 合同；不能反过来阻断或扩大 P0。

## 3. 支持范围与前置条件

### 3.1 本期支持范围

| 项目 | 本期规则 |
| --- | --- |
| 入口 | 飞书 Bot 单聊中的拟议 `/OA优惠券提报` 入口；服务端实现和 R2 Gate 前不得注册为已上线能力 |
| 原始配券表 | 必传 `.xlsx`；允许任意 Sheet/表头布局，但业务语义必须能映射到已批准字段字典 |
| 原始白名单 | 必传 `.xlsx`；一个确认的 Sheet、一列、一个确认的 ID 维度 |
| 原始黑名单 | 可选 `.xlsx`；未上传时业务员必须明确确认“本次无黑名单” |
| 已填充标准配券表截图 | 当前 OA 表单必传；由系统生成 | 从同一 revision 已验证的标准配券表完整渲染；记录源产物/图片 hash，不解读图片业务内容 |
| ID 维度 | 仅支持经业务 Owner 发布的 SKU、SPU 或商家 ID 之一；同一笔提单的白/黑名单必须一致 |
| 业务模式 | 本地代码支持严选、寄卖、POP；严选无测算图，寄卖/POP 必须有 owner 确认的用户图或由最终标准配券表自动生成的分页图 |
| OA | 三源 canonical revision 转换为既有系统 OA 测试稿；仅由当前业务员在当前 revision 上沿用既有明确“发送”动作，且所有既有服务端 Gate 通过时，才创建并回读飞书原生 OA |
| 运行规模 | 内网低并发、单聊、同一业务员同一时刻一笔活动三源任务 |

### 3.2 上线前置条件

1. 业务 Owner 确认首期支持的券型、配券模板、字段字典、公式和舍入规则。
2. 业务 Owner 提供并确认正式白名单、黑名单模板：Sheet、列头、ID 维度、最大行数、重复策略和模板 Owner。
3. 流程 Owner 确认 OA 字段映射，尤其是活动点位、渠道、活动日期、业务模式、超扣点和附件规则。
4. 技术侧为每份模板登记版本和结构 fingerprint；当前已按 OA 截图创建结构相同的白名单、黑名单多券档 SKU 模板：`商品明细白名单-多券档SKU-v1.xlsx` 与 `商品明细黑名单-多券档SKU-v1.xlsx`。任一必需模板未登记时禁止提交原生 OA。
5. 应用管理员完成 Base、Drive、审批定义读取、审批附件上传、实例创建与读取权限发布。

### 3.3 本期不做

- 自动识别并支持未登记的券型、模板、ID 维度或业务公式；
- 通过文件名、AI 猜测或列位置静默决定源文件角色、列映射或名单优先级；
- 将任意格式的源文件直接上传为 OA 正式附件；
- 自动批准、自动撤回、绕过业务员身份或 OA 权限；
- 群聊、代办、批量提单、多业务员协作；
- 商品主数据真实性、可售性、类目归属校验；
- 正式模板未到位时用未经 Owner 确认的临时附件创建 OA；
- 重建既有 OA 测试稿、最终发送、审批创建/readback、bridge/worker 平台，或将三源路线重构为通用工作流框架。

## 4. 业务术语与事实来源

| 术语 | 定义 |
| --- | --- |
| 原始配券表 | 业务员上传的任意布局券规则 Excel；OA 字段的第一来源 |
| 原始白名单/黑名单 | 业务员上传的任意布局商品范围 Excel；只读输入材料 |
| 标准数据包 | 同一 revision 下的字段、名单、来源、决策、计算结果和模板版本；唯一业务事实源 |
| 标准附件 | 从标准数据包生成的标准配券表、标准白名单和可选标准黑名单 |
| OA 预填快照 | 标准数据包映射出的 OA 字段和附件引用；第二次确认对象 |
| 无黑名单确认 | 业务员确认本次没有黑名单，不等于文件错误或解析失败 |

### 4.1 来源优先级

```text
已确认的配券表字段
  > 业务员为缺项提供的补充值
  > 系统派生值

飞书身份字段（申请人/部门）
  > 表格中的同名文本
```

配券表与业务员补充值冲突时，系统展示原值、补充值、来源和影响。只有业务员显式确认覆盖并填写原因后，补充值才能进入标准数据包。

## 5. 用户流程

### 5.1 材料接收

Bot 告知业务员上传配券表、白名单和黑名单。标准配券表通过验证后，系统从该产物生成当前 OA 表单必传的图片附件；文件可乱序发送，系统依次回执已收到材料和当前缺项。

- 配券表或白名单缺失：不可进入解析确认；
- 已填充标准配券表无法完整渲染为图片：不可进入第二次确认；系统不得用原始源表或任意上传图片替代；
- 黑名单缺失：标记为“待确认无黑名单”，不可生成；
- 黑名单文件无效：标记为文件错误，不得视为无黑名单；
- 同类文件多份：业务员必须选择采用或替换，系统不得静默覆盖。

### 5.2 来源解析与第一次确认

系统展示：

1. 自动识别出的配券表 Sheet、表头、说明行、数据行、字段候选、样例和标准字段映射；
2. 自动识别出的白名单/黑名单 Sheet、候选列、可能 ID 维度、非空数、重复数、附加列和异常样例；
3. 配券表缺失的 OA 必填字段；
4. 配券表与业务员补充值的冲突；
5. 黑名单“已上传”或“待确认无黑名单”的状态。

系统应依据表头别名、单元格类型、样例值、结构关系和已发布字段字典主动识别任意布局源表；业务员不需要预先提供格式说明或手工标注 Sheet/列。AI 只能提出候选与识别理由，不能替代规则校验。只有唯一且符合已发布规则的候选可自动采用；多个合理候选、无法判断的说明/数据行、混合 ID 维度或业务语义冲突必须进入最小化追问。

第一次确认内容：

```text
配券字段映射与显式覆盖
白名单 Sheet / 列 / ID 维度
黑名单 Sheet / 列 / ID 维度，或“本次无黑名单”
缺失 OA 字段补充
```

### 5.3 名单重叠处理

白名单和黑名单确认相同 ID 维度后，系统计算精确交集。

存在重叠时，系统展示完整冲突表，业务员必须选择：

- 白名单优先；
- 黑名单优先；
- 返回修改源文件。

不允许默认优先级，也不允许在未经业务 Owner 另行批准的情况下保留同一 ID 于两份标准名单。

### 5.4 标准附件与 OA 预填

通过第一次确认和冲突处理后，系统生成并验证：

- 标准配券信息表；
- 标准商品白名单（当前已按截图设计多券档 SKU 模板 `商品明细白名单-多券档SKU-v1.xlsx`，每个券档对应一个 `sku` Sheet）；
- 黑名单已上传时的标准商品黑名单；
- 黑名单缺省时的明确缺省记录；
- OA 字段、附件、计算结果组成的预填快照；
- 由已验证的标准配券信息表完整渲染的图片附件，绑定源产物 hash、模板版本、渲染范围和图片 hash。

源文件不作为 OA 标准附件。生成文件必须记录模板版本、行数和 SHA-256，并在提升至审批附件前重新下载校验。

### 5.5 第二次确认、OA 测试稿与原生 OA

第二次确认页展示：OA 字段、标准附件、模板版本、行数、hash、黑名单状态、重叠决定、来源覆盖、计算结果、警告和当前 revision。

通过第二次确认后，三源服务把同一 canonical revision 的预填字段和冻结产物引用交接给**既有系统 OA 测试稿**。业务员在该测试稿中继续使用已经验证的明确“发送”动作；三源卡片不会自行创建 OA，也不复制或替代既有最终发送卡片。

当用户执行该既有发送动作时，服务端仍按既有路径：

```text
校验 owner + revision + 来源/产物 hash + 业务决定
  → 冻结/复核 OA 预填快照
  → 读取审批定义并验证 definition hash
  → 上传当前 revision 的标准附件至审批附件库
  → 创建原生 OA
  → 回读实例并逐字段核对
```

上述写入只有既有 allowlist、native-submit kill switch、审批定义和其他服务端 Gate 同时允许时才能发生。创建成功且回读一致时为 `Submitted`；创建后回读差异或不确定时为 `CreatedNeedsReview` / `SubmissionUnknown`。不得显示盲目重提按钮。

### 5.6 方案 A 的服务边界

| 三源 task / adapter 负责 | 既有 OA 草稿与发送路径负责 |
| --- | --- |
| 文件角色、字段/名单映射、补充值与原因、无黑名单和名单重叠决定、canonical revision、标准产物、截图和 OA 预填值 | 最终确认人的飞书身份、审批定义绑定、发送 Gate、批准附件上传、实例创建、提交幂等、未知结果处理和 readback |

任一源文件、映射、补充字段、无黑名单确认或重叠决定改变，都使三源 revision 和对应 OA 测试稿失效，必须重新生成。三源 adapter 只将服务端冻结快照交接给既有路径；不信任卡片回传的自由业务字段。

## 6. OA 字段与模板字段

当前已识别的 OA 字段包括：部门、申请人、申请类型、业务模式、活动名称、活动背景、活动点位、平台承担比例、是否超扣点、预估 GMV、预估费用、ROI、配置渠道、活动开始/结束时间、时长和附件。

配券模板可直接提供或计算活动名称、渠道、券规则、申请数量、平台承担比例、预计 GMV、预计费用、ROI 等；但部门、最终申请人、业务模式、活动背景、超扣点、活动日期等字段仍可能需要身份信息或业务员补充。

下列事项未确认前不得自动映射：

1. `活动点位(%)` 是否等于模板的 `优惠比例`；
2. OA 活动开始/结束时间与配券表可领/可用时间的关系；
3. 配券渠道文案与 OA 渠道枚举的映射；
4. 业务模式及超扣点字段在配券表中的来源；
5. 各折扣券公式和舍入规则。

当前已确认的本地三源规则：

- 配券表存在、但活动文案未配置单独型号/券额策略的券档，必须作为 `unconfigured_coupon_tier` 信息提示展示；它不属于缺失字段、不会阻断文案候选或标准附件。
- `是否超扣点` 源表缺失时预填“否”，状态为 `defaulted_pending_unified_confirmation`；在最终统一确认中确认，若改为“是”则原因必填。
- 本期实际券档可为已登记模板可支持券档的子集；仅因未配置某个支持券档不能报模板不匹配。实际券档无法唯一映射、未登记或结构无效时仍阻断。

## 7. 修改与审计

任意一个源文件、字段映射、显式覆盖、名单映射、黑名单缺省确认或重叠决策变化时：

```text
revision + 1
→ 旧标准附件失效
→ 旧 OA 预填快照失效
→ 旧确认卡不可提交
→ 重新生成并展示新的第二次确认页
```

每笔提交必须记录 owner、revision、源 hash、产物 hash、模板版本、映射版本、缺省确认、重叠决策、确认人/时间、审批定义 hash、实例 code、实例链接和回读差异。

## 8. 验收标准

1. 业务员可上传任意布局但语义可映射的三类 `.xlsx` 源表；配券表为第一字段来源。
2. 缺少白名单时阻断；缺少黑名单时只有在业务员明确确认“无黑名单”后才可继续。
3. 黑名单解析失败或空表不会自动被当成“无黑名单”。
4. 白黑名单重叠时必须展示冲突并要求业务员决策；无静默优先级。
5. 标准配券表、白名单、黑名单（如有）和 OA 预填快照来自同一 revision。
6. 源文件不会直接进入 OA 附件；只有冻结且 hash 校验通过的标准附件可上传。
7. 第二次确认页完整回显 OA 字段、附件、无黑名单状态、重叠决策和警告。
8. 第二次确认后只创建同 revision 的既有 OA 测试稿；只有当前 owner 随后在该测试稿执行既有明确“发送”动作，且服务端 Gate 允许时，才创建一次原生 OA，重复点击返回已有结果。
9. 审批定义变化、旧卡片、非 owner 操作、提交结果未知和回读差异均安全止损。
10. 配券表存在但未配置型号/券额策略的券档作为可审计信息提示展示，不生成缺失字段或 blocker；实际券档为支持券档子集时不报模板 mismatch。
11. 源表缺失“是否超扣点”时，预填“否”并在最终统一确认中审计确认；改为“是”时原因必填。
12. 测算图片必须属于同一 revision：用户上传图片需校验真实 PNG/JPEG、顺序与 hash；无用户图时只能从已验证、已填充的标准配券表显示值生成，并记录源产物/图片 hash、渲染器版本和范围。原始源表不得直接成为 OA 附件。
13. 现有 P1 Excel 试点和旧手工 OA 流程不受三源流程影响。
14. 三源实现复用既有 OA 测试稿和发送路径，不新建并行的审批创建或 readback 实现。
