## 问题 1：恢复卡「组件同名」被飞书整卡拒收（11310）

### 你的疑问：推广途径和公开推广渠道本来就是两个不同字段，为什么会出现同名？

同名**不是**这两个字段撞了，而是**同一个字段「公开推广渠道」在一张卡上被画了两次**：

1. 你提交时没填渠道 → 校验失败，系统把这个字段记入「待修正」清单，于是卡片**上方的待修正区**画了一次（名字 `owner_publicPromotionChannels`）；
2. 同时这个字段又在「可选补充区」的固定清单里，卡片**下方的补充区**又画了一次（同名 `owner_publicPromotionChannels`）。

两处的过滤条件各查各的，互不知道对方画过。飞书规定一张卡内表单组件名必须唯一，见到两个同名格子就整卡拒收（`ErrCode 11310`）。拒收之后发送失败的报错又被代码吞掉，于是表现为「卡在生成中、等不到新卡」的死局。

### 决定与方案

| 项 | 内容 |
| --- | --- |
| 决定 | 按既有方案 B 修复（本次重放的取证即其验收证据） |
| 修复 1（去重） | 可选补充区渲染前排除已在待修正区出现的字段——两区互斥，一个字段只画一次 |
| 修复 2（必达） | 恢复卡发送失败不再静默吞掉，降级发纯文字报错并打结构化日志 |
| 修复 3（防复发） | 新增测试门禁：全部卡片形态构建后遍历断言「组件名全卡唯一」，用本次事故的真实草稿做回归样本——以后任何人再画出重名组件，测试直接红 |
| 落点 | 已并入[整合实施计划阶段一](../../../docs/superpowers/plans/2026-10-16-coupon-three-source-gap-reminder-and-merchant-id-integrated.md)（Task B2/B4/B5），PRD v1.6 |
| 验收 | case1 最小填变体重放：不再出现死卡，用户能收到恢复卡并补填渠道走通 |

## 问题 2：一份材料里既有商家 ID 又有 SKU（case9 特殊场景）

### 你的决定

两个维度各自成表：**商家 ID 一张表、SKU 一张表**——不混在一张里。

### 方案

1. **短期（方案 A 落地即可覆盖）**：同一张白名单表内允许单维度（SKU 或商家 ID），由 owner 确认维度；跨维度材料请拆成两次提报或两张表。
2. **中期（多名单并行）**：case9 暴露的真实需求是「一次提报里同时存在 SKU 券和商家 ID 券两组名单」。管线现状是单白名单槽位，需要扩展为**按维度拆分的多个名单工件**：商家 ID 维度一张冻结表、SKU 维度一张冻结表，各自带维度标记与 hash。此项归入 scalable recognition 立项的范围（与多配券表、内嵌名单列一起设计），不在本轮实现。
3. **拆分规则（设计约束，供 scalable 立项参考）**：同一文件的多个名单 Sheet 按维度分组；同维度多 Sheet 合并为该维度冻结产物的多券档；跨维度不允许合并进同一产物。

## 问题 3：黑名单默认值与数字列的默认归属

### 你的决定

- 一般情况**默认没有黑名单**；
- 表名或表内容**没有说明用途**的一列数字，**默认按白名单**处理；
- 是商家 ID 还是 SKU，需要**结合 Excel 的文件名/Sheet 名**判断。

### 方案与现状对照

| 你的要求 | 现状 | 差距与动作 |
| --- | --- | --- |
| 数字列默认白名单 | ✅ 已实现（重放实测：未声明的名单文件自动归入白名单候选并提示） | 无 |
| 默认没有黑名单 | ✅ 基本满足：黑名单是可选项，映射卡上「本次无黑名单」随填表顺带确认（blacklistDecision），无单独确认轮 | 无需改动；保留内联确认（审计要求"未上传≠没有黑名单"留痕） |
| 维度判定结合文件名/Sheet 名 | ⚠️ 部分：方案 A（商家 ID 白名单）已把"文件名含商家ID/Sheet 名标注"设计为 AI 判定的**低权重线索**，最终由 owner 双选项确认 | 随方案 A 落地（整合计划阶段二） |

## 问题 4：表内用词与系统标准不一致（如「每天可领一次」）

### 你的决定

**按系统标准来**，不做方言兼容；「每天可领一次」属上传方未按标准填写，应从源头纠正。

### 方案

1. **不做**枚举方言归一层（此前测试报告里建议的"自动对号入座"方案**否决**，理由：枚举是审批与下游系统的契约，静默改写等于替业务员改申报内容）。
2. **保留但不扩**：系统标准枚举维持现状（「活动期间仅可领一次」「活动期间每天可领一次」等），校验继续严格拒绝。
3. **小改（体验，随阶段一顺带）**：校验被拒后，恢复卡上这类字段的修正入口从自由文本框改为**下拉框**（选项=合法枚举），点选即改，消除"照报错抄长串、抄错再打回"的循环。
4. **源头治理（运营动作，非代码）**：
   - 在配券表模板的填写说明中补一节「标准用词表」（领取规则、是否允许转赠、推广途径、是否超扣等字段的合法取值原文）；
   - 对已下发的旧模板做一次用词核对通知，明确新提报按标准词填写；
   - 排查现存高频错写：重放实测到的方言有「每天可领一次」「每天可领1次」「是（应填允许/不允许）」、业务模式取值不在 严选/寄卖/pop 内。
5. **验收**：同一份 case7 材料按标准词修正后一轮通过；恢复卡为下拉框。

## 问题 5：AI 识别配置缺陷——已解决

### 解决记录（2026-10-16 已完成并验证）

| 项 | 内容 |
| --- | --- |
| 问题 | 部署环境 `AI_PRIMARY_ENABLED=true` 但缺 `AI_RECOGNITION_ENABLED` 开关与 `DEEPSEEK_API_KEY`，点「AI 识别」按钮会直接报配置错误 |
| 修复 | 两个环境变量已补入 Preview（Secret 类型、绑定 p0 分支）并重部署；实测 case6/7：AI 两个槽位识别成功（primary），识别结果进入确认与生成链路 |
| 防复发（建议，未实施） | 启动时校验开关组合：`AI_PRIMARY_ENABLED=true` 而缺前置开关或 key 时，部署健康检查直接失败，而不是等用户点按钮才报错 |

### AI 路径使用说明（给排查的你）

- AI 不是自动跑的：文件收齐后，卡片上有「AI 识别」按钮（动作 `coupon_three_source_recognition_start`），点了才调 DeepSeek（约 30–90 秒），成功后映射卡会带 AI 判定更新（可能多暴露需要补充的字段，如实测中多出「使用时间」）。
- 排查入口：试点 Base「优惠券三源提报试点」表 → State JSON 内 `recognitions.<槽位>.ai.status`（pending/succeeded/failed）；AI 诊断端点只覆盖配券表槽位，白名单需直读 Base。
