# 三源第二轮表单「模版缺项提醒」与报错可达性修复 设计 v1

> **状态**：待评审。本文描述的是对现行 P0 三源流程（第二轮映射表单卡）的行为修复与补强；未获评审通过前不改任何代码。
> **日期**：2026-10-16
> **背景事故**：2026-10-16 11:16，草稿 `CTS-b5f7cd48`（record `reczz28NtbiBLSvW`，rev4）两次确认均被领域校验拒绝，恢复表单卡因组件重名被飞书整卡拒收（`ErrCode 11310, name(owner_publicPromotionChannels) duplicate`），投递失败被静默吞掉，用户只看到两张永久「标准附件生成中」死卡，无从知道流程已终止。

## 1. 需求口径（Owner 原话）

> 提交上来的表单跟模版上的操作写就好：**有缺失就提醒，没有缺失就不管。**

即：以配券信息表**模版的填写说明**为对账基准——

| 模版列 | 模版说明（原文） | 系统行为 |
| --- | --- | --- |
| 推广途径 | 根据业务需求填写（公开自动推广或者非公开推广） | 识别值照常上卡/预填 |
| 公开推广渠道 | 推广途径选择公开时填写（全网推广、单品页购物车、领券中心、公开券池）可多选 | 推广途径=公开自动推广且该列为空 = **缺失** → 第二轮卡片上亮出该字段、标必填、提示可选项；不缺或非公开 → 不出现、不管 |

「缺失」的判定只做**有无**检查，不做渠道值枚举校验（枚举封闭集不在本期范围）。缺的字段在**第二轮卡片上当场补**，不要求改 Excel 重传。

## 2. 问题陈述（三个独立缺陷，同一事故暴露）

1. **校验时机太晚（产品缺陷）**：「公开自动推广→公开推广渠道必填」规则存在于领域层（`server/lib/coupon-oa/calculation.ts:81-90`），但只在确认后的冻结/生成阶段才触发；第二轮表单卡把它渲染成**可选**输入（`required: false`），用户无从知道它此刻必填。同类条件必填「超扣=是→超扣原因必填」在表单预检（`assertMappingFormReady`，`server/lib/feishu/coupon-oa/three-source/dispatcher.ts:473`）已有先例，本规则漏了对称扩展。
2. **恢复卡组件重名（确定性 bug）**：确认失败后重投表单卡时，`validationIssues` 命中的字段进入「待修正区」渲染（`cards.ts` `fieldsForOwnerReview`），而「可选补充区」的过滤条件只查识别候选、不查是否已渲染（`cards.ts:940-949`）。`publicPromotionChannels` 恰好"列头在但值全空 + 无 AI 候选"，两区同时命中 → 同名 `owner_publicPromotionChannels` 出现两次 → 飞书 11310 整卡拒收。
3. **失败静默（可靠性缺陷）**：恢复链最后一步 `deliverMappingCard` 的失败被 `.catch(() => undefined)` 吞掉（`dispatcher.ts:595-597`），无降级、无提示、无日志出口。任何发卡失败都会让校验错误变成「无声死局」——用户只看到『生成中』，流程实际早已终止。

## 3. 方案设计

四个改动，前两个实现「缺了提醒、不缺不管」，后两个保证「提醒一定到达」。

### 改动 1：第二轮卡片条件必填渲染（cards.ts）

- 渲染「可选补充区」前，先按既有取值级联（owner 覆盖 → 文案候选 → AI 候选 → 确定性候选，即 `ownerDefaultValue` 同款逻辑）求**生效推广途径**：
  - 生效值 = `公开自动推广` 且公开推广渠道为空 → 该字段以 `required: true` 渲染，label 下带提示行：「推广途径为公开自动推广时必填：全网推广、单品页购物车、领券中心、公开券池，可多选」；飞书表单原生拦空值，点确认即提交不出去。
  - 生效值 = `非公开推广` → 不渲染该字段（模版要求不填）。
  - 生效值缺失/无法判定 → 维持现状（可选渲染），由改动 2 的服务端预检兜底。
- 修复重名：可选补充区过滤条件追加「排除已进入 `fieldsForOwnerReview` 的 key」。

### 改动 2：服务端表单预检镜像（dispatcher.ts `assertMappingFormReady`）

与「超扣原因」同款做法，预检在推进 revision 之前执行：

- 合并提交值后的生效推广途径 = 公开自动推广 且 公开推广渠道为空 → 抛友好错误「推广途径为「公开自动推广」时，公开推广渠道为必填（全网推广、单品页购物车、领券中心、公开券池，可多选）」，失败留在原卡可改（走既有恢复链，不产生 revision 死局）。
- 生效推广途径 = 非公开推广 且 公开推广渠道非空 → 抛「推广途径为非公开推广时，无需填写公开推广渠道」。
- 规则文本以模版说明为准，与 `calculation.ts` 领域规则语义一致（不复制实现，判定函数如需共享则从领域层导出）。

### 改动 3：恢复投递降级兜底（dispatcher.ts `restoreMappingFormAfterFailure`）

`deliverMappingCard` 失败时，不再静默：降级 `sendCard` 一条纯 markdown 报错消息（不走表单模板，不可能触发 schema 拒收）：

> 「本次确认未通过：<失败原因>。表单卡恢复失败，请重发 `/OA优惠券提报` 获取最新表单卡；已填内容已保留。」

同时补一条结构化错误日志（含 `draft_id`、`revision`、失败原因），保证可观测。降级消息仍失败则如实抛出，不再返回成功。

### 改动 4：schema 测试门禁（cards-schema.test.ts / audit:cards）

- 单测断言：对全部卡片形态矩阵构建结果做 walker 遍历，**同一张卡内表单组件 `name` 全局唯一**（本次 11310 的回归测试）。
- fixture 复用本次事故草稿导出（`.local/stuck-draft-export.json` 的脱敏版本入库为测试 fixture）：断言修复后 `owner_publicPromotionChannels` 恰出现一次、条件必填状态正确。

## 4. 修复后体验走查（今天场景重演）

1. 用户上传「推广途径=公开自动推广、渠道列空」的配券表 → 第二轮卡片上出现带红星的「公开推广渠道」+ 可选项提示；
2. 不填点确认 → 飞书原生拦截，提交不出去（用户零困惑）；
3. 填上（如「单品页购物车、领券中心」）→ 确认 → 直接进生成，不再走到冻结阶段才炸；
4. 推广途径=非公开推广 → 字段不出现，行为与今天一致；
5. 若用户绕过卡片改了推广途径导致预检失败 → 原卡恢复 + 顶部「上次确认未完成」提示（恢复链修好后必达）；
6. 极端情况下恢复卡仍发不出去 → 纯文字报错必达，用户明确知道流程停在何处、如何继续。

## 6. 上线与解锁

1. 实现通过上述验证后，经用户授权走 `pnpm p0:preview:up` 重新部署（bridge/worker 随新 SHA 重启）；
2. 死局草稿不自愈：部署后用户重发 `/OA优惠券提报` 复用 `CTS-b5f7cd48`（识别零损失），拿到恢复卡后补「公开推广渠道」提交即可；
3. 本方案不触碰 OA 原生提交 Gate、allowlist 与 draft-only 边界。

## 7. 非目标

- 不做公开推广渠道的**枚举值校验**（只查有无；模版括号里的四个选项作为提示文案展示）；
- 不改识别/投影/AI 链路，不改状态机与存储边界（无需新 ADR）;
- 不处理「高置信非法枚举值不上卡」类问题（`allowGift=是` 同款，另行立项）；
- 不强制 Excel 模版层校验（缺项允许在第二轮卡片补，正是本方案目标）。
