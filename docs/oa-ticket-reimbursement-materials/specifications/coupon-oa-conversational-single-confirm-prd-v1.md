# 优惠券 OA 智能填报：对话式一轮确认改造 PRD v1.1

> **状态**：待业务、流程与技术 Owner 评审；未替代当前 P1-1 试点基线
> **版本**：v1.1
> **日期**：2026-10-01
> **改造对象**：[优惠券 OA 智能填报 P1 PRD v1.5（内网试点版）](coupon-oa-p1-excel-pilot-prd-v1.5.md) 的多卡片、多次确认交互
> **本次更新**：根据业务讨论敲定最终发起、追问、附件替换、提交未知、任务续办、有效期与重算等边缘规则。
> **本次决策目标**：保留当前受控字段、Excel 模板、附件和 OA 审批边界，将业务员的正常路径收敛为“发起 → 一次输入/按需补充 → 一张完整确认单 → 明确确认并发起 OA”。

## 1. 背景与问题

当前 P1-1 将风险控制拆分为“字段确认、白名单上传、SKU 列映射、生成结果确认、系统 OA 草稿确认、正式 OA 提交”等多个节点。该设计便于逐步验证能力，但业务员在一次正常提单中需要反复阅读卡片、切换输入方式和确认中间结果。

这会造成以下问题：

1. **链路长且心智负担高**：业务员需要理解系统内部阶段，而非只关注“我还需要补什么、最终会提交什么”。
2. **同一事实被多次确认**：字段快照、Excel 输出和 OA 草稿被拆开确认，用户很难判断最终确认的业务含义。
3. **附件动作断裂**：白名单和满减测算图片在不同节点上传，容易出现“流程已走到后面才发现材料未齐”的体验。
4. **例外与正常路径混杂**：白名单列映射本应只在无法确定时追问，却成为正常路径的固定步骤。
5. **最终动作不清晰**：用户希望在一张确认单中同时核对 OA 字段和附件，并通过一次明确操作发起 OA，而不是在多个中间草稿卡间跳转。

本 PRD 的核心不是减少校验，而是把校验与中间状态收敛到 Agent 内部；只有缺失、歧义或不符合规则时才打断业务员。

## 2. 目标与成功标准

### 2.1 产品目标

为已授权的业务员提供一个单聊 Agent：

```text
业务员发起任务
  → Agent 告知本次所需字段与材料
  → 业务员一次填写、分多条补充或上传文件
  → Agent 仅追问尚缺/有歧义/不合规的内容
  → Agent 生成“附件 + OA 字段”统一确认单
  → 业务员点击“确认并发起 OA”
  → 系统以该业务员身份创建原生 OA，并返回结果
```

### 2.2 成功标准

正常的“常规满减券 + SKU 白名单”提单满足：

- 业务员只需理解一份首次输入清单和一张最终确认单；
- 字段和材料齐全、白名单可唯一映射时，不展示字段确认卡、SKU 映射卡、生成结果确认卡或系统草稿确认卡；
- 业务员可在任意顺序补充文字和材料，Agent 只追问尚未满足的最小集合；
- 最终确认单一次展示全部会进入 OA 的字段、全部会挂载到 OA 的附件、计算摘要和风险提示；
- 用户只有在点击明确标识的“确认并发起 OA”后，系统才创建原生 OA；
- 成功后返回 OA 单号/链接和回读核对结果；失败时保留同一版本的输入，不要求重新填写。

### 2.3 可量化验收目标

| 指标 | 目标 |
| --- | --- |
| 正常路径中的用户决策点 | 3 个：发起、提交输入与材料、确认并发起 OA |
| 中间确认卡 | 0 张 |
| Agent 对缺项的追问 | 每轮仅包含当前缺失/歧义/不合法字段，不重复完整清单 |
| 完整确认单 | 1 张，包含 OA 字段、附件、计算摘要、版本和最终按钮 |
| 无效输入恢复 | 用户补充后继续当前草稿；已确认的有效字段不丢失 |

“3 个决策点”不代表任何情况下只允许三条聊天消息。用户可以分多次上传附件或补充内容；此时 Agent 只追加必要追问，不重新启动流程。

## 3. 范围与前提

### 3.1 本次保留的业务范围

本改造只调整交互链路，不扩大 P1-1 的业务能力：

| 项目 | 本次约定 |
| --- | --- |
| 用户 | 已知且已获授权的业务员；仅 Bot 单聊；同一人同一时刻仅一个优惠券任务 |
| 优惠券 | 常规满减券、限 SKU、一个券档；京东、拍拍或双渠道 |
| 源白名单 | 单个 `.xlsx`、一个来源 Sheet、一个 SKU 列；建议不超过 2 MB、3,000 条有效 SKU |
| 输出附件 | 系统生成的常规满减券配券信息表、系统生成的标准 `SKUID` 白名单；寄卖/pop 还包含业务员提供的满减测算图片 |
| OA | 使用业务员 `open_id` 创建原生优惠券 OA；审批人、抄送人和审批路由完全由飞书 OA 原生定义决定 |
| 试点运行 | 低并发、同步处理；不建设队列、协作、批量和生产级恢复能力 |

现有字段定义、渠道映射、费用/ROI 公式、模板版本和白名单校验规则继续以 P1 PRD v1.5 为准，除非后续另行确认修改。

### 3.2 明确不做

- 让 Agent 猜测、补造或静默修改业务事实；
- 跳过必填字段、附件、金额/日期/枚举等规则校验；
- 将原始白名单直接作为 OA 审批附件；
- 折扣券、PLUS、兑换券、多券档、多 Sheet、SPU/商家 ID、群聊、代办、批量提单；
- 自动审批、自动撤回、绕过业务员身份或 OA 权限；
- 未经业务员最终点击而创建 OA。

## 4. 角色与职责

| 角色 | 职责 |
| --- | --- |
| 业务员（发起人） | 提供真实业务字段和材料；核对最终确认单；明确点击“确认并发起 OA” |
| 对话 Agent | 解释需要什么、提取用户输入、维护当前草稿、只追问缺项/歧义、生成确认单与附件 |
| 规则服务 | 进行字段、日期、金额、比例、模板、文件、SKU 和流程状态的确定性校验；不得由模型绕过 |
| Excel 生成服务 | 根据已确认的结构化数据生成两份冻结 Excel，并校验结果 |
| 飞书 OA | 校验发起人权限，承载原生审批定义、提交、审批和流转 |
| 业务/流程 Owner | 确认字段口径、模板、费用公式、OA 定义和应用权限 |

## 5. 目标用户流程

### 5.1 正常路径

```text
1. 业务员发送「OA优惠券填报」
   ↓
2. Agent 创建/恢复任务，并发出“本次需要什么”卡片
   ├─ 必填业务字段
   ├─ 白名单 Excel
   └─ 条件性材料：寄卖/pop 的满减测算图片
   ↓
3. 业务员提交字段，并上传白名单/测算图片
   （可以同一轮完成，也可以分多条消息；顺序不限）
   ↓
4. Agent 提取 + 规则校验 + 文件解析
   ├─ 缺项/歧义/不合规 → 仅追问相关项目，回到步骤 3
   └─ 齐全且可生成 → 自动映射白名单、生成两份 Excel、冻结版本
   ↓
5. Agent 返回一张“OA 提交确认单”
   ├─ OA 表单字段
   ├─ 将提交的附件
   ├─ 配券、费用、GMV、ROI、白名单行数等汇总
   └─ 异常/提示（如有）
   ↓
6. 业务员点击「确认并发起 OA」
   ↓
7. 系统再次校验版本，上传冻结附件，以业务员身份创建原生 OA，并回读核对
   ↓
8. Agent 返回“已发起”结果卡：OA 单号、链接、附件版本与核对结果
```

### 5.2 缺项或不合规的补充路径

```text
业务员的输入或附件到达
  ↓
Agent 累积已识别字段和已收到材料
  ↓
规则服务判定是否可以生成
  ├─ 可生成：进入统一确认单
  └─ 不可生成：展示最小补充卡
       ↓
     业务员只补本卡列出的字段或替换指定文件
       ↓
     Agent 合并更新、重新校验
```

Agent 不得因为用户一次只补一个字段，就重新发送完整字段清单。它应说明“已收集什么”和“还差什么”，并保留此前正确的值。

### 5.3 白名单列映射的例外处理

SKU 列映射不再是正常路径的固定确认点：

1. 若文件内只有一个可用非空列，或存在唯一且可信的 `SKU` / `SKUID` 列，系统自动选择；
2. 若存在多个等价候选列、列名与样例无法可靠判断、或选定列存在空值/重复值/多 SKU 单元格/前导零风险，则将“白名单列”作为一个待补充项；
3. Agent 仅展示 Sheet、候选列、样例和行数，请业务员选择一次；选择后直接进入生成；
4. 最终确认单必须回显实际采用的 Sheet 与列，以便用户核对；用户可点击“修改白名单”返回补充状态。

## 6. 对话与卡片设计

### 6.1 发起卡：一次说清所需内容

触发口令：`OA优惠券填报`。

Agent 返回的首卡不是需要用户逐项点击确认的表单，而是一份可复制的输入模板和材料清单：

```text
请一次性告诉我以下内容；可以分多条消息发送，已填写内容无需重复。

活动名称：
活动背景：
业务模式：寄卖 / pop / 严选
活动开始日期：
活动结束日期：
用券渠道：京东渠道 / 严选APP及小程序 / 两者
满减门槛（元）：
优惠面额（元）：
总申请数量：
单次到账张数：
每日领取次数：
可领时间：
可用时间：
预计领用率：
预计使用率：
平台承担比例：
预计引入 GMV（元）：
用户领券规则：
优惠券赠送：
推广途径：
公开推广渠道（公开时必填）：
是否超扣点：
超扣点原因（超扣点时必填）：

还需要：
1. 商品白名单 .xlsx；
2. 若业务模式为寄卖或 pop，请上传满减测算图片。
```

首卡提供“上传商品白名单”和“上传满减测算图片”入口；该入口使用 H5 文件上传或原生聊天附件发送，具体实现必须遵循单独的附件上传方案。用户也可直接发送文件到当前会话。

**申请人处理：** OA 发起人始终取最终点击人的 `open_id`。配券信息表中的“申请人”优先取该身份对应、经飞书用户信息接口验证的展示姓名；若应用没有可用的身份姓名映射，或业务员明确要求使用不同的申请人名称，Agent 必须将“申请人”作为最小补充项追问，不能自行编造。

### 6.2 最小补充卡

每次仅展示当前问题，使用业务文案而不是内部字段名：

```text
还差 3 项，补充后即可生成确认单：

1. 满减门槛（元）
2. 预计使用率
3. 商品白名单 Excel（.xlsx）

已收到：活动名称、活动时间、渠道、券面额等 18 项；无需重复填写。
```

若存在格式或规则错误，替代“缺少”文案，指出值和规则：

```text
“优惠面额 100 元”不能大于或等于“满减门槛 100 元”。
请只回复新的满减门槛或优惠面额。
```

### 6.3 统一 OA 提交确认单

只有结构化字段、必要材料和两份生成文件都有效时，Agent 才发送本卡。卡片必须包含：

| 区域 | 必须展示的内容 |
| --- | --- |
| 提交提示 | “确认后将以你本人身份发起原生优惠券 OA”；当前草稿版本和生成时间 |
| OA 表单字段 | 活动名称、背景、业务模式、活动日期、渠道、活动点位、平台承担比例、预估 GMV、预估费用、超扣点及其原因等会写入 OA 的字段 |
| 配券摘要 | 满减档、渠道数、配券行数、预计领用率、预计使用率、费用、ROI |
| 白名单摘要 | 来源文件名、采用的 Sheet/列、有效 SKU 行数、去重/异常结果 |
| 提交附件 | 系统生成的配券信息表、系统生成的商品白名单；寄卖/pop 的测算图片；每项的文件名、大小、生成/上传状态 |
| 风险提示 | 业务员仍需负责业务数据真实性；仅展示非阻断提示，不允许隐藏阻断错误 |
| 操作 | `返回修改`、`取消任务`、`确认并发起 OA` |

“确认并发起 OA”必须带二次确认弹窗，明确展示：

> 即将使用你的飞书身份创建并提交一条原生优惠券 OA。提交后会进入既有审批流，不能由机器人自动撤回。是否继续？

二次确认用于避免误触，但不另起一张需要再次核对的业务卡；用户确认弹窗即构成最终明确指令。

### 6.4 结果卡

成功后返回：

- 原生 OA 单号和可打开的链接；
- 发起时间、发起人和草稿版本；
- 已提交附件名称与冻结哈希摘要；
- OA 创建后回读的字段核对结果；
- 若回读存在不一致，明确标为“需人工复核”，不得伪装为完整成功。

## 7. 数据采集、校验与生成规则

### 7.1 输入为累积更新，不是一次性表单

每条文字、每个文件和每次卡片操作都视为对当前任务的增量更新：

- 新值仅覆盖其明确对应的字段；
- 未出现的字段保留上次已确认的有效值；
- 同一字段出现矛盾值时，标记该字段有歧义，要求用户明确选择，不能用模型猜测；
- 任一有效字段、附件或映射被修改时，生成版本递增，旧确认单和旧按钮失效；
- 业务员可用自然语言、`字段：值` 模板或对最小补充卡直接回复；Agent 负责结构化提取，但最终以规则校验为准。

### 7.2 Agent 与规则服务的边界

| 工作 | Agent 可做 | 规则服务必须做 |
| --- | --- | --- |
| 理解用户表达 | 提取“满 100 减 5”、日期、比例、渠道等候选值 | 对候选值格式化、枚举化和最终判定 |
| 缺项判断 | 基于字段字典组织对话 | 判断必填、条件必填、冲突和完整性 |
| 白名单 | 建议唯一可信 SKU 列 | 解析 `.xlsx`、检查大小、Sheet、空值、重复值、多值和前导零风险 |
| 计算 | 解释计算结果 | 根据已确认公式计算费用、ROI、名称和渠道汇总 |
| 附件 | 说明缺少哪个附件 | 检查类型、大小、哈希、来源和是否允许作为 OA 附件 |
| OA 发起 | 不自行决定发起 | 仅在业务员最终确认且 revision 一致时调用原生 OA 创建接口 |

任何阻断性规则不通过时，不生成最终确认单，也不能显示可执行的“确认并发起 OA”按钮。

### 7.3 附件处理规则

| 附件 | 来源 | 确认单展示 | OA 是否提交 |
| --- | --- | --- | --- |
| 源商品白名单 | 业务员上传 `.xlsx` | 展示来源名、Sheet、列、行数 | **否**，仅作生成输入 |
| 标准 SKU 商品白名单 | 系统由源文件生成 | 展示生成文件名、行数、版本 | 是 |
| 常规满减券配券信息表 | 系统由字段和模板生成 | 展示生成文件名、渠道行数、版本 | 是 |
| 满减测算图片 | 寄卖/pop 业务员上传 | 展示原文件名和上传状态 | 是 |

文件限制、源文件隔离、生成文件 hash 回验与附件上传权限继续遵循当前 P1-1 试点约束。

## 8. 简化后的状态机

```text
Gathering（收集字段与材料）
  ├─ 缺字段 / 歧义 / 规则错误 / 文件错误 → NeedsInput
  ├─ 输入齐全且可解析 → Generating
  └─ 最后一次有效输入超过 10 分钟 → Canceled（懒过期）

NeedsInput
  ├─ 用户补充或替换 → Gathering
  └─ 最后一次有效输入超过 10 分钟 → Canceled（懒过期）

Generating
  ├─ 生成成功 → AwaitingFinalConfirmation
  ├─ 可修正的数据/文件问题 → NeedsInput
  └─ 临时服务失败 → RetryableFailure

RetryableFailure
  ├─ 用户重试 → Generating
  └─ 最后一次有效输入超过 10 分钟 → Canceled（懒过期）

AwaitingFinalConfirmation
  ├─ 用户修改字段/确认替换附件 → Gathering（revision +1，旧输出失效）
  ├─ 用户确认并发起 OA → Submitting
  ├─ 用户取消 → Canceled
  └─ 确认单生成后超过 24 小时 → Canceled（懒过期，不发起 OA）

Submitting
  ├─ 创建并回读成功 → Submitted
  ├─ 创建成功但回读有差异 → CreatedNeedsReview
  ├─ 请求结果未知 → SubmissionUnknown
  └─ 可确认未创建的临时失败 → RetryableFailure

SubmissionUnknown
  ├─ 按提交幂等键查询到 OA → Submitted / CreatedNeedsReview
  └─ 尚无法判定 → 保持该状态，禁止盲目再次发起
```

以下中间状态从用户交互中移除，不再单独要求确认：

- 字段快照确认；
- 白名单上传确认；
- 唯一 SKU 列映射确认；
- 生成 Excel 输出确认；
- 系统 OA 草稿确认。

它们仍可作为内部处理事件、审计记录或例外状态存在，但不能成为正常路径的额外用户步骤。

| --- | --- |
| FR-01 | 业务员发送 `OA优惠券填报` 后，Agent 创建或恢复唯一活跃任务，并一次告知字段与条件性附件要求。 |
| FR-02 | Agent 支持文字和附件的任意顺序到达；每次只对当前任务做增量合并。 |
| FR-03 | Agent 必须保存已通过校验的字段；追问时只展示尚缺、歧义或不合规项。 |
| FR-04 | 白名单 `.xlsx` 进入独立源文件处理链路，绝不直接上传为 OA 附件。 |
| FR-05 | 系统仅在映射唯一可信时自动选择 SKU 列；否则将映射作为最小补充项请求人工选择。 |
| FR-06 | 所有必填字段、条件必填字段、文件、模板与计算规则通过后，系统自动生成并冻结两份 Excel。 |
| FR-07 | Agent 只能发送一张最终 OA 提交确认单；卡片必须完整回显 OA 字段、附件、摘要、版本与风险提示。 |
| FR-08 | 最终按钮文案固定为“确认并发起 OA”；点击前必须进行服务端 owner、revision、状态、附件和规则复核。 |
| FR-09 | 确认成功后，系统以业务员的 `open_id` 创建原生 OA，不传入或覆盖审批人、抄送人和审批流。 |
| FR-10 | OA 创建后必须回读关键字段和附件引用；不一致时进入 `CreatedNeedsReview` 并提示人工复核。 |
| FR-11 | 所有卡片回调、文件消息和 OA 创建调用必须幂等；旧卡、重复点击和并发事件不得重复创建 OA。 |
| FR-12 | `返回修改`、替换附件或补充字段会递增 revision，废弃旧生成物和旧确认单，并重新生成。 |
| FR-13 | 同一用户不得同时存在旧 Excel 试点流与新对话式流；迁移期间必须明确引导继续旧任务或结束后重新发起。 |
| FR-14 | 已存在白名单或测算图片时收到同类新文件，系统必须先获得业务员的明确替换确认；确认后才递增 revision 并自动重新生成确认单。 |
| FR-15 | 最终确认单仅可在生成后 24 小时内由当前 owner 通过卡片按钮提交；收集状态按最后有效输入 10 分钟懒过期。 |
| FR-16 | OA 创建请求结果未知时，系统必须按最终提交幂等键查询；在未确定原 OA 是否存在前，禁止暴露重新发起按钮。 |

## 10. 异常与提示策略

| 场景 | Agent 行为 |
| --- | --- |
| 缺一个或多个字段 | 仅列出缺失的业务名称和可接受格式；保留已收集内容 |
| 字段互相矛盾 | 指出冲突的值并要求用户明确一个值 |
| 日期、金额、比例、数量不合法 | 解释规则并要求仅回复对应字段 |
| 非试点优惠券或超出范围 | 明确拒绝，说明当前仅支持的场景；不静默转成常规满减券 |
| 白名单不是 `.xlsx`、过大或不可打开 | 指明文件问题并要求替换文件 |
| 多个无法自动判断的 SKU 列 | 展示候选并要求选择一次 |
| SKU 数据异常 | 展示数量和有限样例行，要求修正源文件；不把异常数据写入标准白名单 |
| 缺少寄卖/pop 测算图片 | 仅提醒“满减测算图片”这一项；严选不提示该材料 |
| Agent 提取失败或超时 | 保留原始输入与此前有效值，提示重新发送相关内容或使用字段模板 |
| Excel 生成/Drive/OA 临时失败 | 保留当前 revision，提供“重试”；不要求用户重新输入或重新上传 |
| 最终确认卡过期 | 拒绝发起 OA，提示用户查看最新确认单 |
| OA 创建后回读差异 | 不展示“已完整提交”，标记人工复核并展示 OA 链接与差异摘要 |

## 11. 权限、安全与审计边界

1. **显式最终确认**：Agent 生成确认单不是提交；只有业务员点击“确认并发起 OA”并通过二次确认，才允许创建原生 OA。
2. **身份边界**：OA 发起人固定为最终点击人的 `open_id`；不能代替他人发起，也不接受申请人文本覆盖联系人控件。
3. **审批边界**：机器人不修改审批人、抄送人、审批路线、审批结论或原生 OA 权限。
4. **版本边界**：最终调用前重新读取草稿，校验 owner、revision、状态、字段、附件 hash 和模板版本。任意变化都要求重新展示确认单。
5. **文件边界**：源白名单与生成白名单严格区分；仅冻结后的系统生成文件可以提升为 OA 附件。
6. **审计内容**：保存草稿版本、字段快照、字段来源、源/生成附件 hash、映射、模板版本、操作人、确认时间、OA 单号和回读结果。
7. **数据保留**：源文件和生成物的存储位置、访问权限与保留期限在试点上线前由业务/安全 Owner 明确；不得将真实业务附件提交到仓库。

## 12. 交付与迁移方案

### 12.1 分阶段实施

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| A：会话收敛 | 统一入口、累积字段收集、最小补充卡、单活跃任务 | 不再出现字段确认的固定步骤 |
| B：附件收敛 | 白名单/测算图片统一接收，唯一可信映射自动化，例外最小追问 | 正常白名单不再要求人工选择 SKU 列 |
| C：统一确认单 | 自动生成附件并展示 OA 字段 + 附件的单卡确认 | 用户可在一张卡中完整核对提交内容 |
| D：最终发起与回读 | 明确确认后创建原生 OA、回读核对、结果卡 | 不重复提交，失败可恢复，差异可见 |

### 12.2 灰度与回退

- 采用独立功能开关，例如 `FEISHU_COUPON_OA_CONVERSATION_MODE=single-confirm`；
- 仅对约定试点业务员启用；
- 已处于旧 `优惠券Excel试点` 或旧 OA 草稿流程中的任务继续按旧流程完成，或由业务员明确结束后重新发起；不自动迁移半途数据；
- 出现异常时可切回现有 P1-1 多步骤流程，不删除草稿或附件；
- 新旧流程始终共享“同一人仅一个活跃优惠券任务”的互斥规则。

### 12.3 需要同步更新的资产

实施获批后，应同步修订：

1. P1 PRD v1.5 的用户流程、状态机、验收标准与“确认后提交”边界；
2. 机器人卡片文案与事件路由；
3. 草稿 schema：字段来源、材料状态、自动映射证据、确认单版本与最终提交幂等键；
4. 测试用例：正常路径、分次补充、文件先到/文字先到、自动映射、映射歧义、旧卡、重复点击、提交失败与回读差异；
5. 飞书应用权限和 OA 提交联调清单。

## 13. 验收标准

1. 业务员发送 `OA优惠券填报` 后，只收到一张包含字段与材料要求的发起卡。
2. 业务员一次性提供完整字段并上传所需材料时，系统不再要求确认字段、确认白名单上传、确认唯一 SKU 列映射或确认 Excel 生成结果。
3. 业务员分多次提供信息时，每次只收到缺失/错误项的最小补充提示，之前已通过校验的字段保持不变。
4. 当源白名单存在唯一可信 SKU 列时，系统自动映射；最终确认单清晰回显该映射。
5. 当映射不唯一或源数据异常时，系统只追问列选择或文件修正，不生成错误附件或 OA 确认单。
6. 最终确认单完整展示将写入 OA 的字段、将上传的附件、费用/GMV/ROI、白名单行数、模板版本和关键风险提示。
7. “确认并发起 OA”前有明确二次确认；未点击该按钮不会创建原生 OA。
8. 确认后系统仅使用点击人的身份创建 OA，不覆盖既有审批流；成功后返回 OA 链接与回读核对结果。
9. 原始白名单永远不作为 OA 附件上传；OA 附件只能是冻结后的系统生成文件及条件性测算图片。
10. 修改任何输入、附件或映射后，旧确认单不能提交；系统生成新 revision 并要求核对最新确认单。
11. 重复点击、飞书回调重投和并发事件不会生成重复 OA。
12. 常规成功路径的业务员只需完成“发起、提交输入与材料、确认并发起 OA”三个决策点；所有额外互动必须由缺项、歧义、规则错误或服务失败触发。

## 14. 待业务/流程 Owner 确认

以下事项影响最终实现，但不应阻塞本 PRD 的交互收敛原则：

1. “确认并发起 OA”是否在试点中直接创建原生 OA，还是在权限联调完成前降级为“确认并创建系统 OA 草稿”；本 PRD 的目标态是前者。
2. 寄卖/pop 满减测算图片的精确格式、是否允许多张，以及严选是否始终免该材料。
3. 双渠道时 OA 的 GMV/费用使用全渠道合计还是单渠道值；未确认前必须在最终确认单中明确选择，不可静默默认。
4. 自动选择 SKU 列的允许规则：唯一非空列、唯一标准列名和样例特征的阈值需经业务 Owner 认可。
5. 试点阶段原始文件与生成文件的保留期限、Drive 文件夹权限和清理责任人。
6. 飞书应用是否具备以用户身份创建 OA、上传附件并回读实例的正式权限；权限未就绪时不得将“已发起 OA”作为已实现承诺。

## 15. 已敲定的边缘规则（2026-10-01）

本节是业务讨论后确认的产品决定；后续实现、卡片文案、状态机、测试和上线验收必须以此执行。

| 场景 | 已敲定规则 | 用户可见行为 |
| --- | --- | --- |
| 最终发起 | 最终按钮固定为“确认并发起 OA”。用户点击当前 revision 的卡片按钮并通过二次弹窗后，系统直接以其 `open_id` 创建原生 OA。 | Agent 不接受“确认”“好的”等聊天文本作为提交指令，而是引导点击最新确认卡。 |
| 同时缺多个输入 | 每轮汇总所有当前阻断项，而不是逐字段往返追问。 | 显示最小清单，例如“还差预计使用率、白名单 Excel、满减测算图片”，此前有效输入无需重发。 |
| 寄卖 / pop 测算图片 | 这是最终确认前的阻断材料；严选不要求该材料。 | 图片未到时只提示缺少图片，不生成“可发起 OA”的确认单。 |
| SKU 列映射 | 仅在唯一可信时自动选择；多候选、列名/样例不可靠、或数据异常时必须追问。 | 正常文件无额外步骤；例外时只询问“选哪列/修哪个文件”，确认单回显最终映射。 |
| 同类附件再次到达 | 不静默替换。Agent 先问是否将新文件替换为当前白名单或测算图片。 | 业务员确认替换后，旧确认单立即失效，系统自动重算并发送新版本。 |
| 确认单后字段变更 | 用户明确修改字段、确认替换附件或改变映射时，系统不再要求“是否重算”。 | 自动递增 revision、废弃旧生成物、重新校验并推送新的完整确认单。 |
| 重复发送发起口令 | 同一业务员存在未完成任务时，默认继续该任务；不自动删除已填内容。 | Agent 返回当前进度、缺项或最新确认单；用户必须明确选择“结束当前任务并新建”才能开始另一条。 |
| 收集阶段无操作 | `Gathering`、`NeedsInput`、`RetryableFailure` 在最后一次有效输入后 10 分钟懒过期。 | 下一次操作到达时提示旧任务已结束；未向 OA 发起任何动作。 |
| 最终确认单无操作 | 已生成附件的确认单可提交 24 小时；到期后懒过期。 | 到期卡不可提交，用户重新发起或继续任务后需获得新的确认单；系统绝不因到期自动发起 OA。 |
| 提交请求超时/断连 | 禁止盲目重试。系统必须以最终提交幂等键查找原生 OA 是否已创建。 | 查到即展示结果；查不到且无法判定时显示“提交状态未知”，只可查询/人工核验，不能再次发起。 |
| 已发起 OA 后发现业务变更 | 已提交 OA 不做机器人侧修改。 | Agent 创建关联原 OA 的“修订 / 重提任务”，并提示业务员按既有流程处理原 OA。 |
| 旧卡、重复点击、跨设备并发 | 服务端以 owner、revision、状态和最终提交幂等键复核。 | 旧操作只提示打开最新卡；不会覆盖新输入、不会生成重复 OA。 |
| 用户发送无关文件 | 活跃任务中收到与当前所需材料不匹配的文件时，不把它自动归类或替换。 | Agent 说明该文件未被采用，并提供明确的“作为白名单/测算图片处理”操作；未确认前不改变草稿。 |

### 15.1 由上述规则导出的实现约束

1. 草稿必须记录：最后有效输入时间、确认单生成时间、确认单有效期、当前 revision、最终提交幂等键、OA 查询状态及原 OA 引用。
2. “确认并发起 OA”的回调必须是唯一允许进入 `Submitting` 的入口；自然语言消息只能更新草稿，不能提交。
3. 生成确认单后收到新的文本或文件，必须先判断它是否为明确字段更新、明确替换意图或无关输入；不得将一份新 Excel 静默视作白名单替换。
4. 生成与 OA 创建过程必须可重入：生成可按 revision 重做；OA 创建仅可按最终提交幂等键查询，不允许重新发送未知结果的创建请求。
5. 任务超时仅改变系统草稿的可操作状态，不撤回、修改或提交任何原生 OA；审计记录和已冻结文件按既定保留策略保存。
6. 自动映射的依据（唯一候选、标准列名、样例检查结果）必须写入草稿审计，以支持确认单回显和事后排查。
