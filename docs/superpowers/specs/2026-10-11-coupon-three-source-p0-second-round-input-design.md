# 优惠券三源 P0：第二轮中文输入、多 Sheet 名单与 AI 文案设计

**日期：** 2026-10-11  
**状态：** 已确认设计；待实施计划  
**范围：** 当前单用户 P0 三源飞书测试流程  
**目标分支：** `p0-three-source-direct-http`

## 1. 背景

当前第二轮来源确认卡把内部字段 key 直接展示给业务员，并把名单中的多个 Sheet、配券表中的多个券档行误当成“多券”异常。业务员需要逐项填写大量字段，活动名称和活动背景也没有按已登记配券模板形成可编辑候选。

本设计修正六项用户可见行为：精简黑名单提示、多 Sheet 名单解析、活动文案候选、全中文字段、结构化选择与语音/文字补充、业务模式三选一。

以下边界不变：

- 配券表、名单文件和 owner 确认仍是事实源；
- DeepSeek 只提供候选，不能决定券型、名单映射、审批结果或权限；
- 标准 Excel 仍由确定性模板引擎生成并回读验证；
- 当前 P0 保持 `draft-only`，不得创建或提交飞书原生 OA；
- 源文件不得直接成为 OA 附件。

## 2. 已确认的产品决定

1. 第一轮材料卡删除“未上传黑名单时……”和“源文件不会直接成为 OA 附件”的长说明，只展示需要上传的材料、当前材料状态和“开始统一识别”按钮。
2. 未上传黑名单仍必须在第二轮由当前 owner 明确确认“本次无商品黑名单”；精简文案不改变 fail-closed 规则。
3. 白名单和黑名单允许包含多个有效 Sheet。系统读取所有可映射的 Sheet，并按券档保留 SKU，而不是要求业务员从中只选择一个 Sheet。
4. `满999减60`、`满1999减120` 等不同数字表示同一优惠券类型下的多个券档，不构成“多券型”异常，也不触发“选择本次唯一优惠券”。
5. 只有材料同时匹配不同已登记配券模板类型时，才进入券型歧义。例如常规满减券、PLUS 满减券、常规折扣券或大促神券属于不同模板类型。
6. 券型识别同时参考文件名提示与模板结构相似度，但文件名不能单独决定券型；确定性模板字段指纹优先，DeepSeek 只能提供候选。
7. 生成必须使用 `.claude/skills/OA优惠券提报/SKILL.md` 登记并允许的模板。未登记模板或模板指纹不匹配时 fail closed，不能选择“最相近模板”继续生成。
8. DeepSeek 根据已验证的配券表事实生成活动名称和活动背景候选。业务员可在第二轮修改；未经 owner 确认的候选不得进入 canonical revision。
9. 第二轮全部使用中文字段名、中文占位说明和中文错误信息，不再向业务员展示 `activityBackground`、`businessMode` 等内部 key。
10. 第二轮提供两种互补填充方式：结构化选择/输入，以及一段可编辑的中文补充文本。业务员可以使用手机键盘、电脑听写等外部语音输入把语音转成文字，再在文本框中修改。
11. P0 不接收、不下载、不保存音频，也不接入新的语音识别供应商。内置录音或服务端 ASR 作为后续独立架构能力，不包含在本次实现中。
12. 点击“识别并填入”后，DeepSeek 只解析该段已确认文字并返回字段候选；系统重新渲染同一轮确认卡。该过程属于第二轮澄清，不增加第三次业务确认。
13. 业务模式改为三个中文选项：`严选`、`寄卖`、`POP`。业务员明确选择的值优先于 AI 从补充文字中提取的候选。

## 3. 模板合同

### 3.1 名单模板

P0 名单生成必须使用：

- `docs/oa-ticket-reimbursement-materials/reference/templates/商品明细白名单-多券档SKU-v1.xlsx`
- `docs/oa-ticket-reimbursement-materials/reference/templates/商品明细黑名单-多券档SKU-v1.xlsx`

两个模板均包含以下五个已登记 Sheet：

```text
满999减60
满1999减120
满2999减120
满3999减240
满4999减300
```

每个 Sheet 的首列标题为 `sku`，SKU 从第 2 行开始。P0 必须校验模板 ID、版本和 SHA-256，再按来源券档写入对应 Sheet。未使用的已登记 Sheet 保留空数据区，不得因为为空而伪造 SKU。

来源名单可包含上述券档的任意子集。每个有效来源 Sheet 必须满足：

- 能唯一映射到一个已登记券档；
- SKU 列能唯一识别且维度为 SKU；
- SKU 为文本，一格一个值；
- 无公式、前导零风险、非法分隔符和未解决重复；
- 同一 SKU 的来源 Sheet、单元格和 source hash 可审计。

一个来源 Sheet 无法唯一映射到券档时，只追问该 Sheet 的券档映射；不得让用户从整个工作簿中只保留一个 Sheet。

### 3.2 配券模板类型

当前参考目录中的配券模板通过确定性结构指纹区分，至少包括：

- 券种：满减券或折扣券；
- 用户范围：常规或 PLUS；
- 业务标签：普通或大促神券；
- 发放方式：普通领取或兑换；
- 关键列集合，例如面额/限额，或折扣力度/折扣限额/最高减额；
- 固定提示列，例如特殊业务标签、领券用户、兑换类型。

同一模板内多行不同门槛、面额、折扣力度或最高减额属于多个券档/批次，不等于多个模板类型。系统应把这些行作为一个已识别模板下的券档集合处理。

P0 当前只能生成已经在运行时 manifest 中登记、拥有字段映射、公式规则和回读校验的模板。参考目录中存在文件不等于该券型已经开放。识别到未开放模板时必须展示中文阻断原因。

## 4. 券型与券档识别

识别分两层进行：

1. **模板类型识别**：确定性代码根据表头集合、固定列和值域计算与已登记模板的匹配结果；文件名只作为低优先级提示。DeepSeek 可返回模板候选及来源坐标，但不能选择最终模板。
2. **券档识别**：在已确认模板类型内解析所有有效业务行，形成券档集合。门槛和面额不同不会产生多个券型候选。

模板类型状态：

| 状态 | 含义 | 第二轮行为 |
| --- | --- | --- |
| `unique_template` | 唯一匹配一个已登记且已开放模板 | 显示模板类型和全部券档供整体确认 |
| `ambiguous_template` | 同时合理匹配多个模板类型 | 让业务员选择正确模板类型 |
| `unknown_template` | 无法匹配已登记模板 | 要求更换或修正配券表 |
| `unsupported_template` | 匹配参考模板但该模板未开放生成 | 中文说明暂不支持并阻断生成 |

只有 `ambiguous_template` 才显示券型选择。多个券档、多个名单 Sheet 或多个 SKU 列候选不得复用“多券型”错误。

## 5. 多 Sheet 名单解析与生成

名单解析结果从“单个已选 Sheet + 单列”改为券档集合：

```text
list role
  → source hash
  → tier mappings[]
      → source Sheet
      → confirmed template Sheet
      → identifier column
      → SKU entries[] + provenance
```

第二轮只展示真正存在歧义的映射：

- 所有 Sheet 都唯一匹配时，显示“已识别 5 个名单 Sheet、共 N 个 SKU”，不展示 Sheet 选择器；
- 某个 Sheet 有多个 SKU 列候选时，仅让业务员确认该 Sheet 的 SKU 列；
- 某个 Sheet 无法唯一匹配券档时，仅让业务员确认该 Sheet 对应的模板券档；
- 未登记 Sheet、重复券档映射或数据问题为 blocker。

白黑名单重叠按相同券档和相同 SKU 维度计算，并保留现有“白名单优先、黑名单优先、替换源文件”决定。名单内容变化会创建新 revision，并使旧映射、重叠决定和产物失效。

生成器不再删除模板的其他 Sheet。它对每个已确认券档分别写入对应 SKU，随后重新打开产物并验证：Sheet 集合、表头、文本格式、SKU 顺序、每 Sheet 行数、总行数和文件 hash。

## 6. 活动名称与活动背景候选

DeepSeek 文案输入只能包含当前 revision 中已经验证的配券表事实，包括：

- 已确认模板类型和券档集合；
- 活动日期、渠道、业务模式等已识别值；
- 配券表中的活动名称、活动说明或相邻业务描述；
- 每项事实的来源坐标。

输出为严格 JSON：

```json
{
  "activityName": {
    "value": "候选活动名称",
    "evidence": [{ "sheetName": "满减券", "cells": ["J2", "L2"] }]
  },
  "activityBackground": {
    "value": "候选活动背景",
    "evidence": [{ "sheetName": "满减券", "cells": ["J2", "L2"] }]
  }
}
```

活动背景必须完整概括当前模板中的全部券档，不得只描述第一行。模型不得编造预算、GMV、日期、渠道、商品范围或审批理由。候选缺少有效来源坐标、超长、包含未提供事实或 schema 不合法时丢弃，并回退到业务员补充。

候选在卡片中显示为可编辑中文文本。业务员修改后的值记录为 `ownerConfirmed`；未修改但点击来源确认的值记录为“owner 确认 AI 候选”，不得标记为配券表原值。

## 7. 第二轮中文组合输入

第二轮仍是一张来源确认卡，按以下顺序展示：

1. 已识别模板类型和券档摘要；
2. 真正存在时的模板类型歧义；
3. OA 活动点位；
4. 业务模式三选一：严选、寄卖、POP；
5. 活动名称和活动背景候选；
6. 活动开始日期、活动结束日期、是否超扣点及条件字段；
7. 名单自动识别摘要和仅有歧义的映射项；
8. 未上传黑名单时的“确认本次无商品黑名单”；
9. “语音或文字补充说明”多行文本框；
10. “识别并填入”和“确认来源并生成标准附件”两个动作。

所有用户可见标签使用中文映射，例如：

| 内部 key | 卡片标签 |
| --- | --- |
| `activityName` | 活动名称 |
| `activityBackground` | 活动背景 |
| `businessMode` | 业务模式 |
| `activityStartAt` | 活动开始日期 |
| `activityEndAt` | 活动结束日期 |
| `overDeduction` | 是否超扣点 |
| `overDeductionReason` | 超扣点原因 |
| `channels` | 用券渠道 |
| `estimatedGmvYuan` | 预计引入 GMV（元） |

补充文本框提示为：“可以键盘输入，也可以使用手机或电脑的语音输入；提交前请先检查转成的文字。”系统不会接收原始音频。

点击“识别并填入”时：

1. 服务端校验 owner、当前 revision 和卡片 action；
2. 保存业务员提交的文字和文本 hash；
3. 通过 durable effect 调用 DeepSeek，不在卡片回调同步等待；
4. DeepSeek 只提取当前仍缺失或可编辑的字段候选；
5. 本地 schema 校验类型、枚举、日期和数值；
6. 返回更新后的同一轮卡片，展示候选值与中文来源说明；
7. 业务员可继续编辑或执行最终的来源确认。

结构化明确选择优先于文字候选。文字候选不得覆盖已确认的配券表事实；若存在冲突，卡片显示原值、候选值和中文提示，只有业务员显式选择并填写覆盖原因后才能采用。

## 8. 状态、幂等与失败处理

自然语言补充使用独立 AI effect，语义幂等键至少绑定：

```text
draft_id + revision + supplement_text_hash + model + prompt_version
```

同一 key 不重复外发。AI 终态先持久化，再投影 Base 和卡片。重复点击返回现有结果；旧 revision 或非 owner 操作被拒绝。字段、文件、名单映射或补充文字发生变化时创建新 revision，旧候选和确认失效。

| 场景 | 行为 |
| --- | --- |
| 外部语音转录错误 | 业务员在文本框中修改后再识别 |
| DeepSeek 超时、限流或网络失败 | 保留原文字和结构化字段，显示中文失败提示，允许人工填写 |
| DeepSeek 返回无效 JSON | 丢弃候选，不修改任何已确认字段 |
| 候选与源表事实冲突 | 显示冲突并要求显式覆盖，不自动采用 |
| 名单多 Sheet 均唯一 | 自动采用全部有效 Sheet，不显示单选器 |
| 某个 Sheet 映射歧义 | 只追问该 Sheet 的券档或 SKU 列 |
| 模板指纹不匹配 | 阻断生成，不使用近似模板 |
| 重复点击或旧卡片 | 幂等返回或提示使用最新卡片，不重复调用 AI/生成附件 |

## 9. 代码与文档影响范围

实施预计涉及：

- `server/lib/coupon-oa/three-source/recognition.ts`：模板类型与券档分层识别；
- `server/lib/coupon-oa/three-source/ai-recognition.ts`：活动文案和补充文字候选 schema；
- `server/lib/coupon-oa/three-source/lists.ts`：多 Sheet 券档名单解析；
- `server/lib/coupon-oa/three-source/types.ts`：模板状态、多 Sheet 映射与候选类型；
- `server/lib/coupon-oa/three-source/workflow.ts`：多 Sheet canonical package 和产物生成；
- `server/lib/excel-template-engine/`：按登记 manifest 写入并回读多 Sheet；
- `server/lib/feishu/coupon-oa/three-source/cards.ts`：精简第一轮、全中文第二轮、组合输入；
- `server/lib/feishu/coupon-oa/three-source/dispatcher.ts`：中文表单解析与“识别并填入”动作；
- durable effect / repository 适配：补充文字识别的持久执行与幂等投影；
- 当前产品、实现和运行手册：同步用户行为、模板边界和回归步骤。

该变更不修改事件入口、控制面/执行面职责、PostgreSQL 事实源、原生 OA Gate 或审批时机，因此不新增 ADR。若后续加入音频上传、服务端 ASR 或新的音频供应商，必须单独设计并评估权限、数据保留、外发和删除策略。

## 10. 验收标准

1. 第一轮卡片不再显示用户指出的黑名单和源文件长说明，但第二轮仍强制确认无黑名单。
2. 五个已登记白名单 Sheet 可一次解析、一次确认并原样写入五个输出 Sheet。
3. 多个 `满 X 减 Y` 券档不会显示“检测到多券，请选择唯一优惠券”。
4. 同时匹配不同模板类型时才显示券型选择；未知或未开放模板 fail closed。
5. 活动名称和活动背景候选覆盖全部券档，并在业务员确认前保持 `aiProposed`。
6. 第二轮所有用户可见字段、提示和错误均为中文。
7. 业务模式只能选择严选、寄卖或 POP，不能自由输入非法值。
8. 业务员可在补充文本框中修改外部语音转录文字；点击识别后只回填候选，不直接生成附件。
9. DeepSeek 失败时不丢失文本、不清空结构化输入，也不阻断人工继续填写。
10. 多 Sheet、模板歧义、AI 失败、重复点击、旧 revision、worker 重启和投影重试均有回归测试。
11. 生成产物通过模板 SHA-256、Sheet 集合、字段、SKU、公式、文本格式和 hash 回读验证。
12. `FEISHU_COUPON_OA_NATIVE_SUBMIT_ENABLED` 保持关闭，测试不创建飞书原生 OA。

## 11. 非目标

- 不在本次实现内置麦克风按钮、上传语音或保存音频；
- 不接入新的 ASR 服务或语音插件；
- 不开放所有参考配券模板；
- 不让 DeepSeek 直接生成或修改 Excel 二进制文件；
- 不把多券档拆成多笔 OA；
- 不改变原生 OA 审批人、抄送人、路由或提交 Gate。
