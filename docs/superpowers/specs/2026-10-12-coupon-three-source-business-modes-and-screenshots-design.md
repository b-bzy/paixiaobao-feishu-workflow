# 三源优惠券三业务模式与测算图片设计

> **状态**：设计已获需求方确认；代码已完成本地实现与自动化验证，尚未提交、部署或开放
> **日期**：2026-10-12
> **适用入口**：`/OA优惠券提报`
> **运行边界**：仅扩展系统 OA 测试稿链路；不授权创建或提交飞书原生 OA

## 1. 目标与成功标准

当前三源卡片和优惠券领域模型已经允许业务员选择 `严选`、`寄卖`、
`POP`，但服务和 OA 交接仍硬编码拒绝非严选模式。本次改造需要让同一条
三源流程完整支持三种业务模式，并按模式处理满减测算图片：

- `严选` 不需要测算图片，也不向 OA 测算图片字段写入图片；
- `寄卖`、`POP` 必须有至少一张测算图片；
- 用户上传的图片优先；用户没有上传图片时，系统根据最终确认的数据自动
  绘制简洁表格图片；
- 用户可以直接发送飞书图片消息，也可以上传 PNG/JPEG 文件；
- 支持多张用户图片，按确认后的顺序全部进入 OA；
- 后续上传可选择追加到现有图片末尾，或替换整组已有图片；
- 自动图片与标准配券 Excel 使用同一份最终数据模型，关键数值不得漂移；
- 任何图片缺失、损坏、顺序不确定或 hash 不一致都必须阻止 OA 测试稿交接。

成功不代表能力已部署、已通过 rollout Gate 或可提交原生 OA。当前成功终点
仍是生成可审计的标准产物并创建既有系统 OA 测试稿。

## 2. 产品行为

### 2.1 图片收集

活动三源任务存在时，事件入口接受以下两种图片消息：

1. 飞书 `image` 消息：读取 `image_key`，以消息资源 `type=image` 下载；
2. 飞书 `file` 消息：只把实际内容为 PNG 或 JPEG 的文件识别为图片，读取
   `file_key`，以消息资源 `type=file` 下载。

扩展名和事件声明都不能单独作为格式事实。服务端必须检查文件签名、实际
MIME、字节数和图片尺寸。SVG、动态图片、损坏图片、空文件及超过限制的图片
均被拒绝。图片不得进入 Excel/AI 识别流程。

两种入口归一成相同的 `UserCalcImageSource`。每条记录至少保存：

- 稳定的消息 ID、资源 key 和资源类型；
- 规范化文件名、真实 MIME、字节数、宽高和 SHA-256；
- 接收序号和接收时间；
- 当前 revision 及操作者 `open_id`；
- 来源类型 `feishu_image` 或 `feishu_file`。

同一消息 ID 必须幂等；同一任务中内容 hash 相同的图片不得重复加入列表。

### 2.2 追加与替换

新收到的有效图片先按消息顺序进入一个 pending 批次。首次任务还没有已确认图片
时，该批次在来源确认时默认追加；已有已确认图片后再次收到 pending 批次，确认卡
必须让 owner 选择：

- **追加**：新图片保持消息顺序，接在现有列表末尾；
- **替换已有截图**：清空当前图片选择，使用本批新图片及其顺序。

该决定绑定当前图片集合 hash、当前 revision 和 owner。任何 Excel 来源替换、
图片追加/替换或影响 OA 的业务字段修改，都必须递增 revision，清除旧的来源确认、
最终确认、标准产物和 OA 预填快照。

材料收集阶段可继续沿用“材料已上传完毕”作为批次结束动作；映射卡已经存在时，
新图片到达后应原位更新该卡的 pending 数量和追加/替换选项，避免要求用户操作
过期卡片。

### 2.3 模式规则与优先级

业务模式完成确定性确认后，服务端使用以下唯一规则：

| 业务模式 | 用户图片存在 | 最终 OA 测算图片 |
| --- | --- | --- |
| `严选` | 否 | 无 |
| `严选` | 是 | 无；确认卡明确提示已上传图片不会进入 OA |
| `寄卖` / `POP` | 是 | 使用确认后的全部用户图片，保持顺序 |
| `寄卖` / `POP` | 否 | 从最终结构化配券数据自动绘制一张或多张图片 |

用户图片优先意味着只要确认后的用户图片集合非空，就不再额外生成自动图片，
避免 OA 中同时出现两套口径不明的图片。

## 3. 自动绘图

自动图片不模拟 Excel 界面，也不调用桌面截图、Office 或 LibreOffice。它直接
读取已经生成并校验通过的标准配券 `.xlsx`，按工作簿中的最终显示值绘制结构
简单、便于核对的 PNG 表格。

### 3.1 单一数据投影

图片生成器必须从最终 `couponTable` 产物中读取已登记工作表的表头和全部数据行，
使用单元格的最终显示文本，不得重新计算金额、比例或 ROI。生成前重新校验工作簿
bytes 的 SHA-256 与冻结候选元数据；生成后记录显示值的确定性 hash 和标准配券表
SHA-256。图片不通过 OCR 反向比较；一致性由“只读取最终工作簿显示值”、hash
绑定和单元测试保证。

### 3.2 图片版式

- 固定标题、字段顺序、列宽、数字格式和渲染器版本；
- 中文文本可读，金额、数量、比例和日期使用确定性格式；
- 表格过宽时允许按列分区，但每张图必须保留券档/行标识；
- 数据行过多时自动分页，所有页面按页码进入 OA，禁止裁掉尾部数据；
- 每页显示 `第 N/M 页`、业务模式、revision 和短 hash，方便人工核对；
- 不显示 token、完整 `open_id`、内部存储地址或其他敏感信息。

每张自动图片记录：图片 SHA-256、结构化数据 hash、标准配券表 SHA-256、
渲染器版本、页码、总页数、渲染行范围和字节数。

## 4. 冻结产物与 OA 交接

用户图片和自动图片在生成来源不同，但只有完成 owner 确认、冻结并校验的图片
才能进入 OA 附件链路。

1. 三源服务先生成标准配券表和名单产物；
2. 按第 2.3 节决定用户图片或自动图片；
3. 将选定图片作为 `calcImage` 冻结产物上传到受控 Drive；
4. 在任务中保存每张图片的 Drive token、bytes、SHA-256、顺序和 provenance；
5. `buildOaPrefillSnapshot` 把有序图片列表纳入快照 hash；
6. OA 交接重新从 Drive 下载每个冻结文件并校验 bytes 与 SHA-256；
7. Excel 以审批 `attachment` 类型上传，图片以审批 `image` 类型及真实 MIME
   上传；
8. 图片 `file_code` 按确认顺序写入 `calcImageFileCodes`。

`FrozenCouponOaArtifact` 需要扩展为支持多个同角色图片，不能继续用“角色必须
唯一”判断图片重复。Excel 角色仍必须唯一；图片使用稳定 `artifactId` 和顺序
去重。

`mapThreeSourcePrefillToOaValues` 必须允许三种业务模式，并再次执行模式守卫：

- 严选存在 `calcImage` 时拒绝或在更早阶段清除，不能静默写入 OA；
- 寄卖/POP 缺少 `calcImage` 时拒绝；
- 预填快照、冻结产物和审批上传结果的图片数量、顺序、hash 必须一一对应。

## 5. 组件边界

### 5.1 事件与调度层

`events.ts` 和三源 dispatcher 只解析消息类型、下载资源并调用服务。它们不决定
图片是否用于 OA，也不绘图。

### 5.2 领域与任务层

三源 task 保存图片集合、追加/替换决定、revision 失效规则和冻结产物元数据。
模式图片规则是确定性领域规则，不由卡片显示或 AI 输出决定。

### 5.3 图片校验与渲染层

新增独立模块负责：

- 图片格式、尺寸、字节和 hash 校验；
- 从最终标准配券工作簿的显示值生成分页 PNG；
- 输出不含外部副作用的图片 bytes 与审计元数据。

该模块不得调用飞书、Base、Drive、Approval 或 AI。

### 5.4 飞书文件与 OA 适配层

飞书适配层负责下载图片消息资源、上传冻结图片、交接审批图片和错误转换。
外部调用必须有超时、明确错误并支持重复请求下的语义幂等。

## 6. 错误处理与安全边界

- 图片消息没有资源 key、资源下载失败或格式无效：保留原任务，提示用户重传；
- 用户选择替换但新批次包含无效图片：整批替换失败，保留旧集合；
- 自动绘图失败：任务保持可重试状态，不创建不完整 OA 测试稿；
- Drive 上传部分失败：不保存半套最终快照，重试使用稳定 artifact key；
- 冻结图片回读 hash 不一致：停止审批附件上传与 OA 草稿创建；
- 审批图片上传结果未知：记录失败/未知状态，禁止盲目重复创建草稿；
- 重复消息、重复点击、旧卡片或 worker 重试不能重复追加图片、重复生成页面、
  重复上传审批图片或重复创建草稿；
- 原始图片和完整 payload 不写日志；日志只记录任务、revision、artifact ID、
  hash 前缀、数量和稳定错误码。

本设计不改变 native-submit Gate、审批路由、申请人身份、allowlist、Base/Drive
数据边界或源 Excel 不得直接作为 OA 附件的规则。

## 7. 测试与验收

至少覆盖：

1. 严选无图正常生成，不调用图片渲染或审批图片上传；
2. 严选收到用户图片时给出忽略提示且 OA 无图片；
3. 寄卖/POP 的飞书图片消息和 PNG/JPEG 文件都能归一化；
4. 多图保持消息顺序，追加和整组替换行为正确；
5. 重复 message ID、重复 hash 和重复 callback 不重复加入；
6. 寄卖/POP 有用户图片时不调用自动绘图；
7. 寄卖/POP 无用户图片时自动绘图，全部行和全部分页进入 OA；
8. 自动图片只读取最终 Excel 显示值，金额、数量、比例、GMV、费用和 ROI 的
   格式化值一致且不发生二次计算；
9. 非图片伪装、损坏图片、超限图片、空文件和不支持格式被拒绝；
10. 图片集合或业务字段变化使旧 revision、确认和产物失效；
11. Drive 回读 bytes/hash 不一致时不上传审批图片；
12. 部分上传失败、超时、结果未知、重复重试和 worker 重启不会产生重复副作用；
13. 寄卖/POP 缺图、严选意外带图及快照/产物顺序不一致均 fail closed；
14. 最终只创建系统 OA 测试稿，测试证明未调用原生 OA 创建 API。

实现后应运行受影响的 Vitest 套件、`pnpm lint`、`pnpm typecheck` 和
`pnpm build`。涉及真实飞书、Drive、Base 或 Approval 的验证必须另经环境 Owner
授权，并记录环境、revision 和回读结果；本设计和本地测试不构成外部写入授权。

## 8. 文档与发布影响

实现时必须同步更新：

- 三源产品 PRD 中 P0 仅严选、无截图的旧边界；
- 当前实现基线中的 strict-only 描述和模块映射；
- 本机长连接 POC runbook 的模式、图片输入、验证步骤与回滚条件；
- 三源 Base state/schema 版本及兼容读取策略；
- 相关环境变量示例（仅在引入新配置时）。

文档只能描述“代码具备并经本地测试验证”的范围。没有部署、Owner Gate 和真实
回读证据时，不得写成已上线、已获权限或可自动创建原生 OA。

## 9. 非目标

- 不支持用户上传 SVG、GIF 或其他动态/矢量图片；
- 不追求自动图片与 Microsoft Excel 像素级一致；
- 不用 OCR、AI 或视觉模型判断图片内容是否正确；
- 不改变券型、SKU/SPU/商家 ID 范围或名单重叠规则；
- 不部署新环境、不修改生产配置、不开放原生 OA 提交。
