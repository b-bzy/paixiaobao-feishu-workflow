# 优惠券三源 P0：补充活动信息暂存与安全续办设计

**日期：** 2026-10-12  
**状态：** 待书面确认  
**范围：** 当前单用户、allowlist 限制的 P0 三源飞书测试流程

## 1. 背景与目标

当前“检查并补充活动信息”卡片把提交动作绑定到渲染卡片时的三源
`revision`。业务员在卡片中修改活动信息后，如果后台 revision 已变化，提交会被
统一拒绝，并提示“当前三源提报版本已变化，请使用最新卡片”。业务员无法可靠
保留刚填写的内容，容易误以为只能执行 `/clear` 后重新开始。

本设计的目标是：

1. 业务员可以暂存补充活动信息，稍后从当前三源任务继续；
2. revision 变化但三源材料未变化时，系统自动把人工修改合并到最新 revision，
   并继续后续生成流程；
3. 三源材料已经变化时，保留仍然安全的人工业务字段，但必须基于最新识别结果
   再确认一次；
4. 同一任务持续更新同一张第二轮卡片，避免多张“最新卡片”并存；
5. 不放宽 owner、来源、状态、幂等、附件和原生 OA Gate。

成功标准是：正常的临时修改和非材料型版本漂移不再要求 `/clear`；材料变化时
不会把旧候选映射静默套用到新材料，也不会直接生成附件。

## 2. 产品行为

### 2.1 暂存修改

“补充活动信息”表单增加“保存修改，稍后继续”动作。点击后：

- 保存当前 owner 输入的活动点位、业务模式、活动名称、活动背景、活动日期、
  渠道、超扣选择及其他业务字段；
- 不确认来源、不生成标准附件、不创建 OA 测试稿；
- 继续保留当前活动三源任务；
- 再次发送 `/OA优惠券提报` 或打开更新后的同一张卡片时，已保存内容作为默认值
  回填。

暂存允许字段尚未全部填完。最终“确认信息并生成标准附件”仍执行完整必填、
类型、枚举和业务规则校验。

### 2.2 最终确认

“确认信息并生成标准附件”继续作为第二轮最终动作。提交时先保存本次表单内容，
再根据卡片上下文与当前草稿状态决定是否可以继续生成。

是否超扣及超扣原因并入同一表单：

- 是否超扣使用明确选择；
- 选择“是”时，服务端要求超扣原因非空；
- 选择“否”时，服务端清除旧的超扣原因；
- 不再依赖表单外的按钮刷新卡片，避免刷新时丢失尚未保存的输入。

## 3. 卡片上下文指纹

第二轮卡片除 `recordId` 和 `revision` 外，还携带一个服务端生成的
`mappingContextHash`。该 hash 只用于并发与续办判断，不向业务员展示。

指纹至少绑定：

```text
task_id
+ owner_open_id
+ couponTable source SHA-256
+ whitelist source SHA-256
+ blacklist source SHA-256 或“本次无黑名单”状态
+ 各来源对应的识别 run/source hash
+ 当前 schema / mapping context version
```

指纹不包含表单明文、员工敏感信息、token、文件 key 或完整 AI 响应。生成时使用
稳定序列化和 SHA-256，确保相同材料上下文得到相同结果。

`revision` 继续承担严格的任务并发控制；`mappingContextHash` 只允许在确认“材料
上下文没有变化”时安全续办，不能替代 revision、owner 或持久 CAS。

## 4. 续办决策

服务端收到暂存或最终确认回调后，重新读取当前草稿，并按以下顺序处理：

1. 校验运行时开关、allowlist、当前 owner、record ID、任务状态和 action 格式；
2. 解析并校验卡片携带的 revision 与 `mappingContextHash`；
3. 对当前草稿重新计算 `mappingContextHash`；
4. 根据下表决定处理方式。

| 场景 | 暂存动作 | 最终确认动作 |
| --- | --- | --- |
| revision 与指纹均一致 | 保存到当前 revision | 保存后继续校验和生成 |
| revision 已变化，但指纹一致 | 基于最新 revision 合并并保存 | 基于最新 revision 合并，继续校验和生成 |
| 指纹不一致，即三源材料或识别上下文已变化 | 只保留安全的人工业务字段，刷新最新卡片 | 只保留安全的人工业务字段，刷新最新卡片；不生成，要求再确认 |
| 非 owner、任务已结束或 action 无效 | 拒绝，不写入 | 拒绝，不写入 |
| 无法证明上下文一致 | fail closed，并刷新可用的最新卡片 | fail closed，不生成附件 |

这里的“基于最新 revision 合并”只适用于当前 owner、当前活动任务和仍处于第二轮
可编辑状态的草稿。其他卡片动作继续保持严格 revision 校验。

## 5. 字段合并规则

### 5.1 可以跨材料变化保留的字段

以下由业务员直接输入、且不引用旧识别候选 ID 的字段可以保留：

- OA 活动点位；
- 业务模式；
- 活动名称与活动背景；
- 申请人、活动日期、渠道和领取/使用规则；
- 数量、比例及其他 owner 直接填写的业务字段；
- 是否超扣及超扣原因；
- 语音或文字补充说明原文。

保存后仍须通过现有字段类型和业务规则校验。保留不等于确认，也不等于来源事实。

### 5.2 材料变化后不得直接沿用的字段

以下值与旧来源或旧识别结果绑定，材料变化后必须丢弃或重新计算：

- coupon candidate ID；
- 字段候选 ID 与旧坐标；
- 白名单、黑名单 Sheet/列候选；
- 白黑名单交集决定；
- 已确认来源快照；
- canonical package、标准附件、OA 预填和最终确认；
- 旧来源对应的 AI 候选及 provenance。

系统刷新最新第二轮卡片后，由业务员检查保留下来的人工输入与最新识别结果，
再次点击最终确认。

### 5.3 空值与清除

暂存和最终提交必须区分“字段未出现在表单中”与“业务员明确清空字段”：

- 未出现：保留已有值；
- 明确清空：删除已有 owner 值，让最新来源/AI 候选重新成为可编辑默认值；
- 最终确认时清空必填字段：返回中文校验提示，不生成附件。

## 6. 单卡片更新

同一三源任务只维护一条第二轮卡片消息：

- 首次进入第二轮时发送卡片并保存 `messageId`；
- 人工暂存、AI 补充说明回填、非材料型状态变化和 revision 变化均 PATCH 同一条
  消息；
- 持久记录更新后的 revision 与 `mappingContextHash`；
- PATCH 失败时保留草稿事实，不伪造成功；可重试更新卡片，但不得重复 AI 外发、
  重复生成附件或重复创建 OA 草稿。

如果飞书端仍提交了 PATCH 前已打开的旧表单，服务端按照第 4 节的上下文指纹
规则处理，而不是仅凭旧 revision 统一报错。

## 7. 幂等、并发与错误处理

暂存与最终确认使用不同的语义动作，幂等键至少绑定：

```text
task_id + submitted_revision + mapping_context_hash + action + callback_delivery_id
```

要求：

- 重复暂存不得反复创建卡片或清空字段；
- 重复最终确认不得重复生成、上传标准附件或创建多个 OA 测试稿；
- 后台在处理期间再次发生材料变化时，最终生成前必须重新校验当前 revision 和
  指纹；
- 无法完成持久写入时，不得告诉业务员“保存成功”；
- 无法判断外部生成/上传结果时沿用现有 effect/readback 规则，不盲目重试副作用；
- 错误卡应说明“已保留人工填写内容”“材料已更新，需重新确认”或具体校验失败，
  不再笼统要求 `/clear`。

Base 仍只是当前 POC 投影，不能把本设计解释为已经解决 Base 缺少真正 CAS 的
问题。实现必须复用现有服务端状态守卫；后续耐久 PostgreSQL 路径仍按 ADR-0007
收敛。

## 8. 安全与能力边界

以下边界不变：

- 只有当前 owner 可以暂存、修改和确认；
- AI 候选不能决定字段事实、权限、附件生成或审批结果；
- 来源变化会使旧确认、旧候选映射和旧产物失效；
- 源白名单和源文件不能直接成为 OA 审批附件；
- 标准附件仍须由确定性模板生成并完成 hash/readback 校验；
- 当前流程保持 `draft-only`，不创建或提交飞书原生 OA；
- 不修改审批人、抄送人、审批路由或原生 OA Gate；
- 不新增外部 AI、存储或生产配置。

本变更不改变事件入口、事实源归属、审批时机或部署平台，因此不新增 ADR。实现
时需要同步当前产品基线和实施基线，不能只修改卡片代码。

## 9. 预计影响范围

实现预计涉及：

- `server/lib/feishu/coupon-oa/three-source/cards.ts`：暂存按钮、统一表单、默认值和
  中文状态提示；
- `server/lib/feishu/coupon-oa/three-source/dispatcher.ts`：解析暂存/最终动作、
  上下文校验、安全 rebase 和材料变化分支；
- `server/lib/feishu/coupon-oa/three-source/service.ts`：部分字段保存、清除语义、
  最新 revision 合并和生成前复验；
- `server/lib/feishu/coupon-oa/three-source/mapping-card-delivery.ts`：跨 revision
  更新同一张第二轮卡片；
- `server/lib/feishu/coupon-oa/three-source/store.ts`：如有需要，保存卡片上下文版本
  与 hash；
- 对应单元测试与 dispatcher/service 回归测试；
- 当前产品与实施基线中的第二轮确认、旧卡片和 `/clear` 行为说明。

实现不修改原生 OA 提交模块、审批定义、审批附件提升规则或部署配置。

## 10. 验收标准

1. 业务员可以暂存未完成的补充活动信息，再次进入当前任务时内容仍在。
2. 三源材料未变化、只有 revision 漂移时，旧表单提交会自动基于最新 revision
   继续，不出现“请 `/clear` 重来”。
3. 三源材料变化时，人工业务字段被保留，旧候选映射、确认和产物被清除；系统
   展示最新卡片并要求重新确认，不直接生成附件。
4. 是否超扣及原因与其他活动字段在一次表单提交中保存，不因独立按钮刷新而
   丢失其他输入。
5. 同一任务只维护一张第二轮卡片；AI 投影、暂存和 revision 变化更新同一消息。
6. 明确清空的字段可以删除旧 owner 值；未提交的字段不会被意外清空。
7. 非 owner、已结束任务、非法 action 和无法证明上下文一致的请求继续 fail
   closed。
8. 重复暂存、重复确认、并发回调和卡片更新重试不会重复生成或上传附件。
9. 换源、同源 revision 漂移、AI 回填并发、旧卡片回调、空值清除和恢复续办均有
   回归测试。
10. 受影响测试、`pnpm lint`、`pnpm typecheck` 和适用构建通过。
11. `FEISHU_COUPON_OA_NATIVE_SUBMIT_ENABLED` 保持关闭，测试不创建飞书原生 OA。

## 11. 非目标

- 不实现浏览器式实时自动保存或字段级 change event；
- 不允许旧来源候选静默覆盖新来源识别结果；
- 不把 `/clear` 改成删除审计记录；
- 不引入新的卡片框架、数据库、队列或 AI 服务；
- 不解决 POC Base 存储的全部并发和事务限制；
- 不开放原生 OA 创建、自动提交或生产发布。
