# 优惠券三源可扩展识别与单卡交接整改设计

> 日期：2026-10-15  
> 状态：需求方已确认，待实施  
> 目标分支：`p0-three-source-direct-http`  
> 环境边界：受保护 Preview、本机飞书 bridge/worker、`draft-only`  
> 原生 OA：`FEISHU_COUPON_OA_NATIVE_SUBMIT_ENABLED=false`

## 1. 背景

当前三源流程存在三个相互关联的问题：

1. 无表头单列名单在 DeepSeek 批量识别前，就可能被确定性角色门禁拒绝；
2. 一次确认可能出现多张处理中、成功和失败卡片，用户无法判断哪个结果有效；
3. 标准附件生成成功后，OA 测试稿交接失败会产生互相矛盾的成功与失败反馈，
   再次点击也不能稳定找回当前 revision 的测试稿。

本次整改不是放宽 Excel 校验。它把“上传时必须识别成功”改为“先安全保存来源，
再分层提出候选，最后由确定性代码和必要的人确认形成事实”，并让一次操作只产生
一个可追踪的卡片结果。

## 2. 用户目标与成功标准

业务员可以随意命名文件，并上传布局不同的三类材料：

- 一份配券表；
- 一份 SKU 白名单；
- 可选的一份 SKU 黑名单。

系统需要做到：

- 三组本地真实测试材料都能进入统一识别，不因无表头名单在 AI 前失败；
- 配券表、白名单和黑名单角色可结合文件名与工作簿内容判断；
- SKU、SPU、商家 ID 是三个独立维度，不因值都是数字而混淆；
- 当前产品只生成 SKU 名单，SPU 和商家 ID 不转换、不写入标准附件；
- 绝大多数“配券表 + 单列名单”场景自动把名单作为白名单候选；
- 第三份用途不明名单只有在综合判断仍不明确时，才要求选择替换白名单或作为黑名单；
- 第二轮卡说明系统默认判断、识别困难和需要确认的原因；
- 一次点击只对应一个处理中状态和一个终态结果；
- 标准附件与 OA 测试稿始终绑定同一 task、revision 和 snapshot hash；
- 单文件超过 10 MB 时不调用 Excel 解析或 DeepSeek，只提示转人工提报；
- 全程不创建或提交飞书原生 OA。

## 3. 为什么采用分层识别

### 3.1 采用方案

采用“规则识别明确事实 + DeepSeek 提出候选 + 服务端回读校验 + owner 处理歧义”的
分层框架。

规则适合确认文件可读性、表头、坐标、数据类型、唯一性、大小和 SKU 安全；
DeepSeek 适合理解不稳定文件名、标题行、表格语义和数据区域。二者都不能仅凭一列
数字证明它是 SKU、SPU 还是商家 ID。最终标准附件必须从原始单元格确定性复制，
不能采用模型生成或改写的 ID。

### 3.2 不采用：继续增加文件名和表头别名

业务员命名不可控，无表头文件没有别名可加。继续追加字符串条件会让一个案例通过，
但不能覆盖新命名、标题行和新布局。

### 3.3 不采用：完全相信 DeepSeek

模型会受到文件名误导，也可能返回超时、无效坐标或错误 ID 维度。模型结果只能是
候选，不能直接成为名单事实。

### 3.4 不采用：所有文件都让业务员手工选择

这会把高频的“配券表 + 白名单”退化为重复填表。明确场景应自动识别，只把真实
歧义集中到第二轮卡。

## 4. 两轴识别模型

材料识别拆成两个互不替代的轴。

### 4.1 材料角色

```text
couponTable | whitelist | blacklist | unknown
```

角色回答“这份材料在本次提报里做什么”。

### 4.2 ID 维度

```text
SKU | SPU | MERCHANT_ID | UNKNOWN
```

维度回答“名单单元格里的数字代表什么”。名单角色不能证明 ID 维度，文件名也不能
代替原表证据。

### 4.3 当前产品支持范围

- `SKU`：通过确定性校验并确认后可生成标准白名单或黑名单；
- `SPU`：阻断生成，提示改传 SKU；
- `MERCHANT_ID`：阻断生成，提示改传 SKU；
- `UNKNOWN`：在第二轮卡要求 owner 确认该列实际为 SKU，确认动作写入当前 revision
  的审计快照。

文件名含“商家ID”，但工作簿本身无表头时，文件名只构成冲突提示，不直接把整列
定为 `MERCHANT_ID`。第二轮卡应显示：原表无表头、文件名包含商家 ID、系统无法从
原表证明 ID 类型；只有 owner 明确确认“该列实际为 SKU”后才可继续。

若工作簿明确存在 `SPU` 或“商家 ID”表头，系统不得静默改判为 SKU。业务员认为
表头写错时，必须在当前 revision 明确覆盖为 SKU；覆盖保留原表头、确认人和时间。

## 5. 来源接收与统一识别

### 5.1 上传阶段

合法 `.xlsx` 只执行：

1. 类型和大小 Gate；
2. 计算 source SHA-256；
3. 保存 canonical bytes 与飞书消息引用；
4. 以 `pending` 来源槽位记录上传顺序；
5. 更新 revision。

上传阶段不得调用 `selectUniqueRole()` 作为接收前置条件。损坏、加密、空工作簿或
伪装格式仍然 fail closed。

### 5.2 识别批次

用户点击“开始统一识别”后，系统对当前 revision 的全部 `pending` 来源创建一次
识别批次。批次按 source hash 去重，同一 source hash 不重复调用 DeepSeek。

每份工作簿先运行确定性结构探针。只有规则不能给出完整结论的分区才调用 DeepSeek。
DeepSeek 可提出：

- 材料角色候选；
- 配券表业务行、字段和券档区域；
- 名单数据区域与表头位置；
- ID 维度候选；
- 白名单或黑名单语义候选；
- 困难原因。

服务端随后根据原始 bytes 验证 source hash、Sheet、坐标、数据区域、单元格类型和
候选完整性。无效分区单独丢弃，其他有效分区继续保留。

### 5.3 DeepSeek 超时与失败

- 每个模型请求有显式超时；
- 超时、网络失败、无效 JSON 和越界坐标分别记录稳定错误码；
- 不自动无上限重试，也不因某一分区失败丢弃整个批次；
- 规则已有充分证据的分区继续完成；
- 剩余歧义进入第二轮卡；
- 同一识别批次的投影重试不得再次调用 DeepSeek。

## 6. 文件数量和角色决议

### 6.1 两份材料的常规场景

一份被验证为配券表，另一份为名单形态且没有明确黑名单证据时：

- 名单角色默认候选为白名单；
- 若 ID 维度为 SKU，可直接进入第二轮摘要；
- 若 ID 维度未知，在第二轮确认“该列实际为 SKU”；
- 若 ID 维度为 SPU 或商家 ID，阻断并提示更换材料或明确纠正错误表头。

“默认白名单”只决定名单角色，不自动把未知 ID 维度改成 SKU。

### 6.2 第三份材料

已有配券表和白名单后上传第三份表，系统先结合以下证据重新判断：

- 文件名和 Sheet 名中的白名单/黑名单语义；
- 明确表头；
- 工作簿结构与有效数据区域；
- DeepSeek 候选及其来源坐标；
- 当前 revision 已占用的角色；
- 上传顺序仅作为展示信息，不作为角色事实。

决议规则：

- 明确是黑名单：作为黑名单候选；
- 明确是新的白名单：要求确认是否替换现有白名单；
- 明确是新的配券表：要求确认是否替换现有配券表；
- 是 SKU 名单但黑白用途仍不明确：在当前第二轮卡增加一个必选项，选择
  “替换当前白名单”或“作为黑名单”；
- ID 维度不是 SKU：先处理维度 blocker，不显示黑白名单选择。

该问题作为当前第二轮卡的一个条件字段出现，不单独并行发送另一张卡。

### 6.3 黑名单缺省

未上传黑名单是正常主路径。第二轮卡显示“系统判断本次未提供黑名单”，owner 对
整张第二轮卡确认时一并确认无黑名单，不再增加独立确认轮次。

## 7. SKU 确定性校验

- 文本 SKU 按单元格显示值复制；
- 安全范围内的整数可接受，但输出强制文本格式；
- 文本或格式保存的前导零必须保留；
- 超过 Excel 可靠精度的数值型 ID 阻断；
- 公式、错误值、外部链接和一个单元格多个 ID 阻断；
- 空值忽略并计数；
- 同一 Sheet 重复值按首次出现去重并在卡片说明；
- 不同 Sheet 的相同 SKU 分别保留；
- 隐藏或筛选行仍纳入读取并在摘要说明；
- SKU、SPU、商家 ID 候选列并存时，只选择经过确认的 SKU 列，其他列不进入产物。

## 8. 第二轮确认卡

每个 revision 最多有一张活动中的第二轮卡。识别进度、补充候选和失败恢复都 PATCH
这张卡，不新发并行版本。

卡片至少展示：

- 每份文件的判断角色、ID 维度和证据摘要；
- 默认判断，例如“无明确黑名单证据，已按白名单候选处理”；
- 识别困难，例如“原表无表头，文件名含商家 ID，无法证明 ID 类型”；
- Sheet、数据区域、有效 SKU、空值和重复数；
- 第三份用途不明名单的条件选择；
- 未上传黑名单的整体确认；
- 需要修正的 blocker。

owner 提交后生成 `mappingContextHash`。来源文件改变时保留安全的业务字段输入，但清除
旧角色候选、名单映射、确认快照、冻结产物和 OA 测试稿引用。旧卡回调返回“请使用
最新卡片”。

## 9. 超过 10 MB 与人工提报

单文件上限保持 10 MB。大小 Gate 优先使用可信资源元数据；无法取得元数据时，在
下载到受控内存后、进入 Excel 解析和 AI 前校验。

超过上限时：

- 不解析工作簿；
- 不调用 DeepSeek；
- 不占用配券表、白名单或黑名单槽位；
- 不改变已有有效来源和 revision；
- 记录稳定拒绝 receipt，重复事件不重复发卡；
- 发出一张“文件超过 10 MB，当前自动流程无法处理，请转人工提报”的卡片；
- 卡片说明已接收的其他材料仍保留。

当前仓库没有已验证的人工提报 API 或正式入口，因此首版卡片只提供明确指引，不声称
已经自动转交，也不自动取消当前提报。后续只有在正式入口和权限边界确认后，才能新增
跳转或转交动作。

## 10. 单卡操作、幂等与错误终态

每个回调使用稳定语义键：

```text
taskId + revision + actionName + mappingContextHash
```

收到确认后：

1. 持久记录 operation receipt；
2. PATCH 当前卡为处理中并收起按钮；
3. 通过 effect/outbox 执行冻结、生成、上传和 OA 测试稿交接；
4. 成功时 PATCH 同一张卡为成功终态；
5. 可恢复失败时 PATCH 同一张卡为失败终态并提供重试；
6. 未知外部结果进入对账，不得同时发送绿色成功卡和红色失败卡。

重复点击只读取既有 operation/effect 结果，不重新生成文件、不重复上传、不重复创建
OA 测试稿，也不再次发送处理中卡。

## 11. 标准附件与 OA 测试稿交接

标准附件由当前确认快照确定性生成并回读验证。源文件永不直接成为 OA 附件。

OA 测试稿使用语义身份：

```text
taskId + revision + confirmationSnapshotHash
```

交接时只查找这个身份对应的测试稿，不使用“当前 owner 是否存在任意活动草稿”作为
唯一判断。若测试稿已创建但 link 或投影回写失败，系统执行 readback/reconcile 并补写
引用，不创建第二份。无关活动草稿冲突时，卡片明确提示冲突，冻结附件仍保留。

最终确认卡只读取当前 revision 的精确测试稿引用。整个交接阶段只允许一个终态卡片。

## 12. 状态与兼容

新增或扩展状态包括：

- `pendingSources[]`：未分配角色的来源与上传顺序；
- 每份来源独立的 `roleCandidates` 和 `identifierDimensionCandidates`；
- `recognitionBatchId`、模型状态、错误分类和分区 provenance；
- `mappingContextHash`；
- operation/effect receipt 与卡片 message ID；
- OA 测试稿 semantic identity 和 reconcile 状态。

历史草稿经统一 normalization 入口补齐默认结构。无法安全迁移的状态 fail closed，不
猜测角色或 ID 维度。持久化仍以 PostgreSQL 为耐久事实源；Base/Drive 继续是投影和
飞书可见资料。本设计不扩大事实源或原生 OA 权限。

## 13. 测试设计

### 13.1 真实材料基线

真实业务文件只保留在 Git 忽略目录或临时目录。用三组本地材料验证：

- case 1：六券档配券表 + 无表头单列名单；
- case 2：四券档配券表 + 四 Sheet、SKU/SPU 并存的白名单；
- case 3：六券档配券表 + 无表头单列名单。

预期：

- case 1/3 的单列名单不在 AI 前失败，角色默认白名单，ID 维度困难在第二轮展示；
- case 2 只复制 SKU 列，SPU 列不进入标准附件；
- 所有配券表的多行满减档位属于同一常规满减券模板，不被误判为多种优惠券；
- 文件名与表内日期冲突时以原表事实为准，并在卡片提示。

### 13.2 脱敏自动化 fixture

至少新增以下脱敏 fixture 和回归：

- 无表头单列数字；
- 文件名含商家 ID、内容无表头；
- 明确 SKU、SPU、商家 ID 表头；
- SKU/SPU 并列；
- 第三份明确黑名单；
- 第三份明确替换白名单；
- 第三份用途不明 SKU 名单；
- 超过 10 MB；
- DeepSeek 成功、部分失败、超时、无效 JSON、越界坐标；
- 重复消息、重复点击、worker 重启和投影重试；
- 附件成功但 OA 测试稿交接失败；
- OA 测试稿已创建但 link 回写未知；
- 旧卡和 source replacement。

### 13.3 验证命令

实施计划必须至少包含：

```bash
pnpm test:coupon-three-source:offline
pnpm test:control-plane
pnpm audit:workbook -- <脱敏文件>
pnpm audit:cards
pnpm lint
pnpm typecheck
pnpm build
git diff --check
```

DeepSeek 真测只在明确测试窗口执行，保存脱敏状态摘要，不提交完整请求、响应或真实
工作簿。飞书 CLI 真测保持 `draft-only`，确认没有原生 OA instance code/link。

## 14. 当前基线证据

2026-10-15 对三组本地材料执行当前确定性审计：

- 三份配券表均能识别 18 个字段和对应券档；
- 两份无表头单列名单均无角色候选，证明当前入口仍会在 AI 前失败；
- 多 Sheet 白名单能识别每个 Sheet 的 SKU 与 SPU 列；
- 当前配券确认探针仍把多券档提示为“多个优惠券”；
- case 1 的 DeepSeek 在线探测能读取材料，但受文件名影响把无表头列提议为
  `MERCHANT_ID`，证明模型候选不能直接决定 ID 维度；
- case 2 的在线探测长时间无响应后被终止，证明模型超时需要显式降级；
- 在线探测未调用飞书，未创建 OA。

这些结果是整改前基线，不代表修复已完成。

## 15. 文档与架构影响

实施时同步：

- 当前产品基线：两轴识别、默认白名单、第三份材料和 10 MB 人工分流；
- 当前实现基线：pending 来源、分层识别、单卡 operation/effect 和 OA reconcile；
- P0 本机运行手册：真实材料矩阵、AI 超时判读和 draft-only 验证；
- 脱敏 fixture 与卡片审计。

本设计落实 ADR-0012 的 AI-primary 候选边界和 ADR-0007 的耐久幂等要求，不改变事件
入口、持久事实源或原生 OA 创建时机，因此不新增 ADR。若实施中发现必须改变这些边界，
立即停止并新增 ADR。

## 16. 完成标准

只有同时满足以下条件才算整改完成：

1. 三组真实材料都能通过统一识别并生成正确候选；
2. 无表头名单不会在 DeepSeek 前被拒绝；
3. SKU、SPU 和商家 ID 不混淆，所有标准名单只含已确认 SKU；
4. 第三份用途不明名单只出现一次条件询问；
5. 超过 10 MB 只出现一张人工提报提示卡；
6. 一次点击只有一个处理中状态和一个终态；
7. 标准附件与当前 revision 的 OA 测试稿可稳定回读；
8. 重复点击、重试和 worker 重启不产生重复附件、卡片或测试稿；
9. 所有受影响测试、lint、typecheck、build 和真实材料回读通过；
10. `FEISHU_COUPON_OA_NATIVE_SUBMIT_ENABLED=false`，没有原生 OA 创建请求。
